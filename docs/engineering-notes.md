# 알아두면 덜 헤매는 것

각 항목은 증상 → 원인 → 대응 순서다.

## 시험과 CI

- **Windows CI가 간헐적으로 시간 초과로 실패한다.** 원인은 러너 속도 편차이고 코드 문제가 아닌 경우가 많다. 실패한 작업만 다시 돌린다. 같은 시험이 다시 실패하면 그때 코드를 의심한다. Linux 작업은 영향이 없다.
- **날짜 근처에서만 깨지는 시험.** 24시간 신선도 규칙, 시행일·종료일 경계, 한국 달력 날짜 계산 때문이다. `SHE_TEST_NOW=<ISO 시각> npx vitest run`으로 시계를 옮겨 재현한다. `vitest.config.ts`가 시계 어긋남(`SHE_TEST_CLOCK_OFFSET_MS`)을 한 번 계산해 모든 시험 워커와 자식 Node 프로세스(`NODE_OPTIONS`로 선행 로딩)에 같게 넘기므로, 자식 프로세스를 띄우는 시험도 같은 시계를 본다. 시험 안에서 `Date`를 직접 바꾸면 자식 프로세스와 어긋난다. 확인은 `date-matrix.yml` 수동 실행으로 한다.
- **고정 자료의 `fetchedAt`이 하루 지나면 시험이 깨진다.** 근거 원문 확인이 24시간을 넘으면 빈틈이 생기고 규칙이 작동하지 않기 때문이다. 시험 자료의 시각은 현재 시계에서 상대적으로 만들거나 고정 시계를 쓴다.
- **`work/` 아래 격리 빌드 복사본의 시험이 같이 도는 것처럼 보인다.** 시험 범위는 `tests/**/*.test.ts`뿐이다. 복사본은 산출물이다.

## 서버 동작

- **변경 요청이 갑자기 409로 거절된다.** 서버는 한 번에 변경 작업 하나만 허용하고, 검토·갱신 같은 백그라운드 작업이 도는 동안은 `/api/auth/` 외의 변경 요청도 막는다. 오류가 아니라 의도된 동작이다. 응답이 끝난 뒤가 아니라 작업이 끝난 뒤 잠금이 풀린다. 화면은 진행 중 상태를 보고 다시 시도해야 한다.
- **서버를 재시작했더니 `running` 검토가 `failed`가 되어 있다.** 시작할 때 `running`으로 남은 검토를 모두 실패 처리하기 때문이다(서버가 중간에 꺼졌다고 본다). 다시 요청해야 한다.
- **`/api/…`가 퍼센트 인코딩된 주소로 보안 검문을 건너뛴다.** 원본 URL의 접두어로 판단하면 `/%61pi/…`가 통과한다. 보안 결정은 `routedPath`(라우터가 맞춘 경로)로만 한다. 새 검문을 만들 때 `req.url`을 직접 쓰지 않는다.
- **시작 순서를 바꾸면 안 된다.** 외부 통신 가드가 가장 먼저 설치되어야 이후 모든 호출이 허용 목록을 거치고, 저장 암호 키가 열린 뒤에야 저장소를 열 수 있다. 설치판은 실행 토큰이 없으면 포트를 열기 전에 종료한다.
- **공개 번들(약 28MB)을 시작할 때마다 다시 가져오면 대략 90초 걸린다(코드 주석 기준).** 설치판은 번들 파일이 지난 가져오기와 다를 때만 가져온다(`importPublicOnce`). 개발 실행은 시작할 때마다 가져오므로, 개발 중 시작이 느린 것은 이 때문이다.
- **암호화 백업이 복원 한도를 넘는다.** 앱에 들어 있는 공개 번들 근거까지 백업에 넣으면 약 340MB가 되어 복원 한도(요청 본문 200MB)를 넘는다. 그래서 번들에서 가져온 근거는 백업에서 뺐다(검토에 쓰인 근거는 검토 기록 안의 사본으로 함께 간다). 번들 가져오기 표시(`공개 데이터 수입: 현장 검증 별도`)를 바꾸면 이 제외 기준이 깨져 백업이 다시 커진다.
- **`confirmed=true` 사실을 서류로 증명된 것으로 읽으면 안 된다.** `confirmed`는 입력이 끝났다는 옛 플래그다. 증빙 수준은 `provenance.verificationStatus`가 나타낸다.
- **옛 화면 기능은 `/api/…` 옛 경로를 쓰고 베타 화면은 `/api/beta/…`를 쓴다.** 같은 일을 하는 경로가 두 벌이다(예: 백업). 설치판에서는 옛 경로 일부(평문 백업 등)가 꺼져 있으므로 베타 경로를 쓴다.

## Store 설치판

- **앱을 제거하면 저장된 자료가 사라진다.** Windows가 제거 때 앱 데이터 폴더를 지우고 사용자에게 먼저 묻지 못한다. 그래서 화면 고지문이 "먼저 백업하세요"를 안내한다. 같은 Windows 사용자로 다시 설치한 뒤 암호화 백업을 가져오면 복원된다(설치 시험으로 확인).
- **다른 Windows 사용자나 다른 PC에서 암호화 백업·저장 자료가 열리지 않는다.** 데이터 키를 Windows 사용자 보호(DPAPI)로 감쌌기 때문이다. 오류가 아니다.
- **Store 업로드가 거절된다.** 버전의 마지막 자리가 0이 아니거나 이미 올린 같은 버전을 다시 올린 경우다. 제출 직전 `packaging/msix/identity.json`의 버전을 확인한다.
- **패키지 스캐너가 새 파일에서 실패한다.** 스캐너는 시크릿·개인 경로 같은 흔적을 찾는다. 정당한 파일이면 예외 목록에 이유와 함께 추가한다(승인 필요). 흔적이면 파일을 고친다.
- **MSIX 설치 시험은 PR·main CI에 들어 있지 않다.** Windows 시간이 두 배로 세어지기 때문이다. `msix-test/<이름>` 브랜치로 푸시하거나 수동 실행한다.
- **패키지의 `node.exe`가 CI에서 공식 `SHASUMS256.txt`와 다르면 빌드가 멈춘다.** 의도된 확인이다. 로컬 Node 버전이 바뀌었으면 해당 버전의 목록을 다시 받는다.

## 공개 법령 자료

- **새 앱 버전 전에 번들이 낡아 있다.** 매주 자동 갱신은 2026-10-15에 껐다. 새 버전 전에 `public-law-sync` 워크플로를 수동 실행하거나 `npm run sync` 후 `npm run publish:check`를 돌린다. 이 워크플로는 저장소 비밀값 `LAW_OC`가 있어야 법제처를 부를 수 있다. 구현이 끝나면 이 값을 지울 계획이므로, 그 뒤의 갱신 방법은 정해져 있지 않다.
- **번들 검사(`publish:check`)가 실패한다.** 사용자 자료나 개인 흔적이 번들 후보에 섞였다는 뜻이다. 공개 수집기가 격리 DB를 쓰는지부터 확인한다. 검사를 완화하지 않는다.

## 문서 폴더

- `docs/` 아래의 `implementation-v2`~`v8`, `development-history`, `specifications`와 날짜가 붙은 보고서·인계 문서는 과거 작업의 기록이다. 숫자와 상태가 현재와 다를 수 있으므로 규칙의 근거로 삼지 않고, 코드와 시험으로 확인한다.
- **그러나 일부는 시험과 스크립트가 읽는 입력이다.** 이동·삭제·이름 변경 전에 `docs/`를 읽는 곳을 먼저 찾는다. 확인된 입력: `implementation-v3/api-registry.json`, `implementation-v5/official/`(공문 원본), `implementation-v6/`(`baseline.json`, `api-registry.json`, `operation-specimens.json`, `official/`, `official-contract-tables.json`), `implementation-v8/`(`ui-freeze-v8.json`, `security-review-plan.md`, `stage4-msix/install-test.json`, `stage5-store/`). 화면 잠금 스크립트는 `implementation-v6/baseline.json`에서 잠글 옛 화면 파일 목록을 읽는다.
