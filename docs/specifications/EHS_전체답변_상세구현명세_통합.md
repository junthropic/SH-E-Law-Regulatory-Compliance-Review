# 제1부. 채팅 답변 전체

# EHS 실무 기준·로직 조사: 채팅 답변 전체

인터넷의 공식 법령·기관 안내·공포 원문을 조사해 **실무 판정 기준, 데이터 구조, 판정 알고리즘, 완료 기준, 48개 인수 테스트 제안**으로 정리했습니다.

**결론부터 말하면, 이 프로그램은 ‘법령 검색 챗봇’이 아니라 ‘증빙 기반 준수평가·변경관리 시스템’으로 설계해야 합니다.** 법적 기준과 제가 제안하는 프로그램 설계 규칙은 구분했습니다.

전체 구현 명세는 이 통합 문서의 제2부에 포함되어 있습니다.

## 1. 실무 판단의 기본 순서

EHS 관리자는 다음 순서로 판단해야 합니다.

```text
무엇을 하는 사업장·시설인가?
→ 어떤 사실이 어떤 증빙으로 확인됐는가?
→ 언제 발생한 행위인가?
→ 그 시점의 법령·별표·부칙은 무엇인가?
→ 어느 기관의 권한인가?
→ 적용 대상인가?
→ 예외·유예·기관 승인 조건이 있는가?
→ 어떤 의무가 언제까지 발생하는가?
→ 이행 또는 불이행이 확인됐는가?
→ 누가 검토하고 어떤 조치를 할 것인가?
```

핵심은 **‘적용 대상 확인’과 ‘의무 이행 확인’을 분리하는 것**입니다.

- 적용 대상이지만 허가 상태를 모를 수 있습니다.
- 허가증이 있어도 현재 시설·물질·용량을 포괄하지 않을 수 있습니다.
- 설치허가가 확인돼도 가동 신고나 정기검사는 별도입니다.
- 법규 준수가 확인돼도 현장 위험이 없다는 뜻은 아닙니다.

산업안전보건법은 위험성평가와 개선대책 이행을 요구하고, 산업재해가 발생할 급박한 위험이 있으면 작업중지·대피 등의 조치를 요구합니다.([S02](https://www.law.go.kr/LSW/lsSideInfoP.do?lsiSeq=283449&joNo=0036&joBrNo=00&docCls=jo&urlMode=lsScJoRltInfoR), [S04](https://www.law.go.kr/LSW/lsLawLinkInfo.do?chrClsCd=010202&lsId=001766&lsJoLnkSeq=900388530&print=print)) 따라서 **법률 판정 상태와 현장 위험·긴급 조치 상태도 별도로 관리**해야 합니다.

## 2. 사실 확인은 단일 상태값으로 처리하면 안 됩니다

제가 권하는 구조는 다음과 같습니다.

```text
사실값
+ 대상
+ 시간
+ 수량·측정 기준
+ 사용자 주장/확인
+ 확보한 증빙
+ 증빙 검토 결과
+ 현장 확인 결과
+ 충돌 여부
```

예를 들어 사용자가 “800L가 맞습니다”라고 확인 버튼을 눌렀다면:

```text
사용자가 확인함 = 예
객관적 증빙으로 검증됨 = 아직 아님
```

**버튼 클릭으로 ‘자료로 확인됨’까지 승격하면 안 됩니다.**

미확인 처리 원칙도 모든 업무에 동일하게 적용해야 합니다.

- 허가증 미업로드 → **허가 상태 미확인**
- 교육자료 미업로드 → **교육 실시 여부 미확인**
- 검사 API 검색 0건 → **그 검색 범위에서 결과 없음**
- 조회 실패 → **조회 실패**
- 적용 조건·기한·불이행 증거까지 확인 → **불이행 근거 검토 가능**

특히 **기록 미제공과 법정 기록 미보존은 다릅니다.** 기록 보존 의무 위반은 실제 기록관리 상태를 확인한 뒤 별도로 판단해야 합니다.

### 입력 충돌의 비교키

```text
대상 + 사실 종류 + 산정 기준 + 범위 + 단위 + 시간 구간
```

따라서 다음은 충돌이 아닙니다.

- 이전 500L, 변경 후 800L: 시간에 따른 변화.
- 탱크A 500L, 탱크B 800L: 다른 대상.
- 허가량 800L, 현재 재고 500L: 다른 사실 종류.

동일 탱크·동일 시점·동일 실재고가 500L와 800L로 들어왔을 때 비로소 충돌 후보입니다.

## 3. 기준일은 ‘오늘의 최신 법령’ 하나로 해결되지 않습니다

행정기본법 제14조는 신청에 따른 처분은 원칙적으로 처분 당시 법령, 위반행위와 제재처분은 원칙적으로 행위 당시 법령을 적용하도록 하며, 특별 규정과 변경된 유리한 제재 기준 등의 예외를 둡니다.([S01](https://www.law.go.kr/LSW/lsSideInfoP.do?lsiSeq=269955&joNo=0014&joBrNo=00&docCls=jo&urlMode=lsScJoRltInfoR))

프로그램에서는 최소한 다음 날짜를 분리해야 합니다.

```text
행위일 / 설치일 / 변경일 / 신청일 / 처분일
공포일 / 조항 시행일 / 경과조치 기준일 / 의무 기한
```

또한 다음을 구분해야 합니다.

- 의무 자체의 시행.
- 제재 조항의 시행.
- 기존 시설 경과조치.
- 신규 신청에 관한 적용례.
- 별표·서식·고시의 개정.

**실제 조사에서도 차이가 확인됐습니다.**

2026년 산안법 개정은 기본 시행일, 일부 조항 시행일, 규모별 위험성평가 관련 제재 시행일이 서로 다르고, 위험성평가에 관한 적용례도 별도로 둡니다.([S03](https://www.law.go.kr/LSW/lsRvsDocListP.do?chrClsCd=010102&lsId=001766))

현재 시행규칙의 위험성평가 기록·보존 조항은 제37조의4이며, 해당 자료의 3년 보존을 규정합니다.([S06](https://www.law.go.kr/LSW/lsSideInfoP.do?lsiSeq=288431&joNo=0037&joBrNo=04&docCls=jo&urlMode=lsScJoRltInfoR)) 과거 매뉴얼의 ‘제37조’를 그대로 현재 규칙에 연결하면 잘못된 조문을 참조하게 됩니다.

**구현 기준:** 법령 문서 버전뿐 아니라 **조항별 시행일·부칙·대상 조건**까지 연결해야 합니다.

## 4. 화성시 출처 충돌은 구체적으로 확인했습니다

공식 시보 첨부 PDF와 국가법령정보센터 레코드를 대조했습니다.

- **제2412호:** 2025년 6월 일부개정 건.
- **제2509호:** 2025년 12월 31일 전부개정 건. 시보 제244호 PDF의 공포문·부칙에서 **2026년 2월 1일 시행**을 확인했습니다.
- 국가법령정보센터 현행 레코드는 머리에 제2412호·일부개정으로 표시하면서, 부칙에는 제2509호 전부개정을 포함하고 있습니다.([S08](https://www.hscity.go.kr/www/user/bbs/BD_selectBbs.do?q_bbsCode=1030&q_bbscttSn=20251231173033231), [S09](https://www.hscity.go.kr/www/user/bbs/BD_selectBbs.do?q_bbsCode=1030&q_bbscttSn=20250630175357659), [S10](https://www.law.go.kr/LSW/ordinInfoP.do?ordinSeq=2048299))

즉, **두 개정 건이 실제로 존재하며 현행 레코드의 메타데이터가 공포 원문·부칙과 불일치하는 상황**입니다. 오류가 기관 등록·연계·수집 중 어디서 생겼는지는 아직 확인하지 못했습니다.

처리 기준은 다음과 같습니다.

1. 두 출처와 원본을 모두 보존.
2. 번호·개정구분·시행일·본문·별표의 충돌을 각각 기록.
3. 공포문·부칙·후속 정정 자료를 대조.
4. 검토자가 정규화 값을 근거와 함께 승인.
5. 재수집·복원 후에도 충돌 이력을 유지.

**메타데이터를 정리했다고 실제 EHS 담당 기관까지 확인된 것은 아닙니다.** 개별 위임 별표의 해당 업무 행을 추가 검토해야 합니다.

## 5. 예외·회신·기술지침은 자동 면제 근거가 아닙니다

예외는 다음처럼 나눠야 합니다.

```text
조건 충족 시 자동 제외
증명서·인증·검사로 대체 인정
기관 승인·재량이 필요한 예외
기존 시설 경과조치
다른 의무로 전환되는 특례
```

각 예외에는 **조건, 증빙, 승인기관, 유효기간, 적용 대상, 남는 의무**가 필요합니다.

‘인정할 수 있다’는 문장을 발견했다고 ‘면제됨’으로 바꾸면 안 됩니다. 필요한 기관 승인이 없거나 대상이 다른 승인서라면 예외 적용을 확정할 수 없습니다.

출처의 법적 성격도 구분해야 합니다.

- 안전보건공단은 KOSHA GUIDE가 법적 구속력 없는 기술적 권고 지침이라고 안내합니다.([S11](https://portal.kosha.or.kr/archive/resources/tech-support/guide/overview))
- 법제처는 정부유권해석의 법적 구속력과 행정 운영상의 사실상 구속력을 구분하고, 구체적 사실인정은 해석 대상이 아니라고 설명합니다.([S12](https://www.moleg.go.kr/menu.es?mid=a10106010000))

따라서 과거 회신은 **당시 법령·질문 원문·핵심 사실·지역·기관·후속 개정**을 비교한 뒤 사용해야 합니다. 키워드 유사도는 검색 후보를 찾는 기준이지 현재 사업장 적용 기준이 아닙니다.

## 6. ‘명확한 법률 리스크’는 다음 조건식으로 정의하는 것이 맞습니다

다음은 **제가 제안하는 프로그램 판정 게이트**입니다.

```text
대상·행위·범위 확인
AND 적용 시점·지역 확인
AND 구속력 있는 의무 근거 확인
AND 필수 본문·별표·부칙·결정 수치 검증
AND 적용 조건 충족
AND 예외·유예·대체 의무 검토 완료
AND 기한 도래
AND 업무별 불이행 증거 기준 충족
AND 결론에 영향을 주는 충돌 없음
AND 승인된 판정 규칙 사용
```

하나라도 결정적으로 부족하면 **확정 대신 판정 보류와 부족한 항목을 표시**해야 합니다.

결과도 세 가지로만 강제 분류하지 않는 것이 좋습니다.

- 의무 이행 확인.
- 검토 범위 내 비대상.
- 향후·진행 중 의무.
- 불이행 근거 확인.
- 판정 보류.

기존의 `자료 부족 / 해석 쟁점 / 명확한 리스크`는 **쟁점별 복수 태그**로 사용하면 됩니다. 자료 부족과 해석 쟁점은 동시에 존재할 수 있습니다.

## 7. 물질·수량·API에서 반드시 지킬 기준

### 물질과 수량

- CAS는 성분 탐색키이지 실제 혼합제품 동일성 보증키가 아닙니다.
- 공급자 제품 MSDS, 제품코드·grade, 조성·물성, 규격서·COA 등을 연결해야 합니다.
- 허가량, 설계 최대량, 운영 최대량, 시점 재고, 일평균·연간량은 별도 사실입니다.
- kg↔L 변환에는 밀도·조건이 필요합니다.
- 합산 범위는 법규별로 확인해야 합니다.

위험물법의 합산은 같은 장소에서 각 위험물 수량을 각각의 지정수량으로 나눈 값의 합이 1 이상인지 판단하는 방식입니다.([S13](https://www.law.go.kr/LSW/lsInfoP.do?lsiSeq=259933))

지정수량 미만 위험물의 저장·취급 기술기준은 시·도 조례로 정하므로, 합산값이 1 미만이라고 모든 의무가 없다고 종결하면 안 됩니다.([S13](https://www.law.go.kr/LSW/lsInfoP.do?lsiSeq=259933))

소방청도 DB 미검색 물질은 비위험물이 아니라 미확인·미등록일 수 있고, DB는 참고용이라고 명시합니다.([S19](https://hazmat.nfa.go.kr/faq.do))

### API 완료 기준

API별로 다음 경로를 검증해야 합니다.

```text
정상 데이터 → 상세 → 다음 페이지 → 첨부
→ 동일 대상 연결 → 오류 → 한도 → 중단·재개 → 변경·삭제
```

제공하지 않는 기능은 ‘미제공’, 제공하지만 시험하지 못한 기능은 ‘미검증’입니다.

- A01 0건은 **빈 결과 처리 검증**일 뿐 상세 처리 검증이 아닙니다.
- A07은 실패·복구·재시도 종료·재개를 각각 확인해야 합니다.
- HTTP 200도 응답 내부 오류일 수 있습니다.
- 조회 실패·0건·부분 수집·법적 비대상은 서로 다른 상태입니다.

## 8. 원본·승인·배포의 완료 기준

**OCR:** 두 OCR의 일치만으로 승인하지 않습니다. 판정에 쓰는 숫자·단위·경계값·머리글·각주·예외를 원문과 대조해야 합니다.

**수집:** 첨부 2,623개 연결 기록과 고유 파일 수·별표 수·검토 완료 수를 따로 집계해야 합니다. 종료 기준은 선언한 업무 범위의 필수 근거 연결이 완결됐는가입니다.

**승인:** 다음 세 승인을 분리합니다.

1. 원문 추출 승인.
2. 판정 규칙 승인.
3. 특정 사업장·기준일의 판단 승인.

변경이 생기면 영향을 받는 승인만 재검토합니다. 이는 **프로그램 승인 재사용 제한**이지 법적 허가 자체의 무효 선언이 아닙니다.

**배포:** 다음 상태를 따로 표시합니다.

```text
작성 → 빌드 → 같은 commit 전체 테스트
```

## 1. 환경안전보건관리자의 사고방식

### 1.1 회사 전체를 한 문장으로 판단하지 않는다

법령마다 규제 객체와 행위가 다르다. 다음 식별자를 분리한다.
- 법인, 사업장, 건물, 공정, 시설, 설비, 허가 단위, 저장 장소, 제품·혼합물, 작업, 근로자 집단, 폐기물 종류.
- 설치·이전·증설·구조변경·취급·저장·사용·가동·폐기·선임·교육·검사라는 **행위/사건**.
- 사업장 전체, 동일 장소, 배출구별, 개별 설비별, 계약·공사별 등 **법규별 적용 범위**.

예: '화성시의 제조업 사업장'이라는 정보만으로 위험물 허가, 폐기물 신고, 안전관리자 선임, 안전검사 여부를 한 번에 결론내지 않는다. 각 의무에 필요한 사실이 다르다.

### 1.2 법규 준수와 실제 위험을 두 축으로 관리한다

[법적 기준] 산안법 제36조는 유해·위험요인 파악, 위험성 결정, 개선대책 수립·이행을 요구한다. 제51조는 산업재해가 발생할 급박한 위험이 있는 때 즉시 작업중지·대피 등 필요한 조치를 요구한다.[S02, S04]

[설계 권고]
- `legal_status`: 적용·이행에 관한 상태.
- `physical_risk`: 현장의 위험성·긴급성에 관한 상태.
- `action_status`: 누가, 언제, 어떤 조치를 실행하고 효과를 확인했는가.

'허가증 확인됨'은 '안전함'과 동의어가 아니다. '법적 위반 판정 보류'도 '운영해도 안전함'을 뜻하지 않는다. 급박한 위험은 법률 해석 종료를 기다리지 않는 긴급 조치 경로로 전달한다. 시스템이 모든 미확인 사항을 자동 작업중지 명령으로 바꾸는 것 역시 금지한다.

### 1.3 의무 이행의 단계와 기관 처리를 분리한다

`작성 → 제출 → 접수 → 보완 → 수리/허가 → 조건 이행 → 설치/완공검사 → 가동 신고 → 운영/정기 검사`는 업무마다 별개의 단계다.

- 접수번호만 있는 것을 허가 완료로 표시하지 않는다.
- 허가증이 있더라도 현재 설치된 시설·물질·용량을 포괄하는지 확인한다.
- 법률상 수리 필요 신고, 자기완결적 신고, 수리간주가 있는 신고를 구분한다. 한 종류의 신고 규칙을 전체 신고에 복제하지 않는다.
- 수리간주는 법정 기간, 보완 요구·기간 연장 통지 등 해당 법률상 요건을 모두 확인해야 한다. 단순히 '접수 후 N일'만으로 완료 처리하지 않는다.
- 내부 관리자의 승인과 행정기관의 허가·승인은 서로 다른 엔터티다.

## 2. 사실과 증빙: '미확인'을 '위반'이나 '확인'으로 바꾸지 않는 기준

### 2.1 사실값과 검증상태를 분리한다

[설계 권고] 하나의 상태값으로 입력·확인·서류·현장을 표현하지 말고 다음 축을 둔다.

```json
{
  "fact_id": "F-001",
  "subject_id": "tank-A",
  "predicate": "actual_inventory",
  "value": "500",
  "unit": "L",
  "measurement_basis": "시점 실재고",
  "valid_from": "2026-10-01T09:00:00+09:00",
  "valid_to": "2026-10-02T09:00:00+09:00",
  "recorded_at": "2026-10-08T10:00:00+09:00",
  "assertion_source": "user_input",
  "user_attested": true,
  "verification_status": "unverified",
  "evidence_ids": [],
  "verification_scope": null,
  "conflict_ids": []
}
```

별도 속성:
- 사용자 입력 및 확인: 누가 무엇을 주장·확인했는지.
- 증빙 확보: 파일이 있는지.
- 증빙 검토: 진위·대상·시기·범위·본문을 확인했는지.
- 현장 확인: 누가 언제 어떤 시설과 상태를 확인했는지.
- 계산 결과: 어떤 검증 입력·산식·단위로 도출했는지.

사용자 확인 버튼은 `user_attested=true`만 바꾼다. 객관적 검증 완료로 승격하지 않는다. 서류 검증과 현장 검증도 일률적인 상하 서열이 아니다. 허가 존재는 행정 문서가, 현재 방호장치 상태는 현장 확인이 직접적인 자료다.

### 2.2 증빙 수용 조건

문서를 사실 근거로 연결하기 전에 다음을 확인한다.
1. 발급·작성 주체와 문서 종류.
2. 사업자/사업장/설비/제품의 식별 일치.
3. 발급일·개정일·효력기간·취소/변경 여부.
4. 첨부·허가조건·별지 등 결정적인 부분 누락 여부.
5. 해당 사실을 직접 증명하는 범위.
6. 다른 자료와 충돌 여부.
7. 검토자·검토일·원문 위치·파일 해시.

'문서 검토됨'을 '문서에 적힌 모든 사실이 현재 현장과 일치함'으로 확장하지 않는다.

### 2.3 부존재 증명은 별도 설계한다

```text
허가증 미업로드              → 허가 상태 미확인
API 검색 0건                → 해당 검색 범위에서 결과 없음
사용자 '허가가 없는 것 같다' → 미취득 진술, 추가 확인 필요
적용 대상·기한 도래 확인 + 신뢰 가능한 미취득/미이행 증거
                            → 해당 의무의 불이행 근거 검토 가능
```

허가·신고·선임·교육·검사 모두 같은 원칙을 쓴다. 내부 기록·기관 확인·해당 업무 책임자의 명시적인 미실시 확인 등의 조합을 **업무별 증거 정책**으로 정한다. 기관 검색은 검색 대상과 과거 기록·변경 이력을 얼마나 포괄하는지 확인하지 않으면 부존재 증거로 쓰지 않는다.

단, '법적으로 보존해야 하는 기록을 보존하지 않았다'는 별도 의무다. 이 경우에도 단순 미업로드는 기록 미보존을 증명하지 않는다. 현장·기록관리 확인 후 해당 의무를 독립 판단한다.

### 2.4 충돌 탐지의 정확한 단위

비교키:
`대상 + 사실 종류 + 측정/산정 기준 + 단위/조건 + 적용 범위 + 시간 구간`.

예:
- 이전 500L, 변경 후 800L: 시간 구간이 다르면 변경 사건.
- 탱크A 500L, 탱크B 800L: 대상이 다르면 별개 사실.
- 허가량 800L, 현재 재고 500L: predicate가 다르므로 충돌 아님.
- 최대 동시저장량 800L, 연간 사용량 800L: 산정 기준이 다르므로 같다고 병합하지 않음.
- 동일 탱크의 동일 시점 실재고 500L와 800L: 단위 변환·측정오차를 검토한 뒤 충돌 후보.
- 시점이 없는 500L/800L: 모순으로 확정하지 않고 날짜·대상 확인 요청.

시간은 원칙적으로 `[valid_from, valid_to)` 반개구간으로 관리한다. 허가 변경과 실재고 변경의 효력 발생 시점을 구별한다. 기존 값을 덮어쓰지 않고 이력과 변경 사유를 보존한다.

### 3.3 실제로 확인된 사례: 위험성평가

[법적 기준] 법률 제21374호 부칙은 기본 시행일 2026-06-01, 일부 조항은 2026-08-01, 위험성평가 관련 일부 제재 조항은 사업장 규모에 따라 2027-01-01/2028-01-01로 구분한다. 제36조 개정은 시행 이후 실시하는 위험성평가부터 적용하는 적용례가 있다.[S03]

2026-10-08 조회에서 확인:
- 산안법 제36조: 평가·개선대책 이행, 근로자 참여, 근로자대표 요구 시 참여, 공유, 기록·보존 등.[S02]
- 시행규칙 제37조: 최초평가 작업 시작 전, 다음 연도부터 매년 1회 이상 정기평가, 추가 위험 등 발생 시 관련 작업 시작 전 수시평가.[S05]
- 시행규칙 제37조의4: 실시 시기·담당자·참여 근로자/대표·공유 대상 결과사항 기록, 3년 보존.[S06]

2023년 매뉴얼은 기록·보존을 당시 시행규칙 제37조로 안내한다. 현재 이 조항은 제37조의4다. **옛 매뉴얼의 조문 번호를 현재 규칙에 그대로 연결하면 오류**다.[S07]

핵심: 문서 머리에 시행 2026-08-01이라고 표시돼도 모든 조항이 그날 처음 시행된 것은 아니다. 법령 MST + 조항별 시행 규칙 + 부칙을 연결한다. MCP 조회 결과도 원문 부칙과 대조해야 한다.

### 3.4 구현 순서

```text
검토 유형/행위 시점 확정
→ 후보 연혁과 공포 원문 수집
→ 조항별 시행·적용례·경과조치 읽기
→ 사업장 설치/허가/규모 조건으로 적용 버전 선택
→ 본문·별표·서식·고시가 맞는 버전인지 확인
→ 위반/제재 검토는 별도 시간 규칙으로 계산
```

일자 계산도 규칙별로 지정한다. '14일 이내', '1개월 이내', '착공 전날', '매년 1회'는 같은 산식이 아니다. 월말, 윤년, 공휴일, 초일 산입, 보완·연장 처리의 법적 기준을 검증하고 기한 산정 근거를 남긴다. 임의의 `+30일`을 `1개월`로 쓰지 않는다.

## 4. 지역·관할·사무위임

### 4.1 주소와 처분 권한을 분리한다

`사업장 주소/행정구역`, `조례 적용지역`, `특별대책지역·보호구역·설치제한지역`, `법정 권한자`, `수임/수탁 기관`, `실제 접수부서`, `업무 전결자`를 구분한다.

[법적 기준] 지방자치법 제117조는 조례·규칙에 의한 위임 등 근거를 둔다. 위험물안전관리법 시행령 제21조는 소방서장에게 권한을 위임하되, 둘 이상의 소방서 관할에 걸친 이송취급소 관련 예외를 둔다. 화학물질관리법 시행령 제22조는 업무에 따라 화학물질안전원장, 유역/지방환경청장 등에 나누어 위임한다.[S14~S16]

[설계 권고] 관할 resolver는 다음 경로를 반환한다.
`법률 권한 조항 → 시행령 위임 조항 → 조례/규칙의 특정 별표 행 → 날짜별 기관/구역 → 접수 안내`.

기관 홈페이지의 민원 안내는 실무 접수처 확인에 유용하지만 법정 권한의 유일한 근거로 쓰지 않는다. 위임과 전결도 동일하게 취급하지 않는다. 실제 사업장 위치와 업무·별표 행을 확인하기 전에는 '화성시 담당'처럼 단정하지 않는다.

### 4.2 화성시 출처 충돌 조사 결과

공식 시보·law.go.kr 현행 레코드·부칙을 대조했다.[S08~S10]

- 제2412호: 2025-06-30 일부개정. law.go.kr 부칙에서 2025-07-01 시행 확인. 시보 제119호 목차와 개정 건 식별도 확인했다. 이 보고서에서는 제119호의 해당 공포문·부칙 전체를 대조하지 않았다.
- 제2509호: 2025-12-31 전부개정. **시보 제244호 PDF 6쪽의 공포문, 7쪽 부칙에서 2026-02-01 시행을 직접 확인**했다.
- 현행 레코드 `ordinSeq=2048299`의 머리는 '[시행 2026.2.1.] [제2412호, 2025.12.31., 일부개정]'인데, 같은 레코드 부칙 마지막에는 '제2509호 전부개정'이 들어 있다.
- 따라서 서로 다른 개정 건 두 개가 존재하고, 현행 레코드의 번호/개정구분은 공포 원문·부칙과 불일치한다.
- **등록·연계·수집 중 어디서 발생한 오류인지 원인은 미확인**이다. 사용자의 로컬 수집본이 이 레코드와 동일한지는 직접 검증하지 않았다.
- 2509는 조례 번호이고 해당 시보는 제244호다. 조례번호와 시보호수를 구분한다.
- 제2509호 본문은 시장→구청장/읍면장/동장, 구청장→읍면동장 위임을 별표1~4에 연결한다. **별표의 EHS 업무별 권한 전체는 이번 조사에서 검토하지 않았으므로 실제 담당 기관은 아직 미확정**이다.

### 4.3 출처충돌 해결 프로토콜

1. 원문·API 응답·공포문·부칙을 모두 immutable 원본으로 보존.
2. 충돌을 `메타데이터`, `규범 내용`, `시행일`, `첨부 버전`, `관할` 중 하나 이상으로 분류.
3. 공포번호·개정구분·시행일·본문·별표의 식별키를 비교. 같은 날이라는 이유로 같은 버전으로 병합하지 않음.
4. 공포 원문과 후속 정정 공고·개정 이력 확인.
5. 확인한 필드에 대해 검토자가 `정규화 값 + 채택 근거 + 배제하지 않은 다른 출처`를 승인.
6. 본문·별표·관할 영향 범위를 좁혀 확인. 메타데이터 해결만으로 모든 별표 권한을 승인하지 않음.
7. 필요하면 지자체 법무·자치법규 담당 및 법령데이터 제공기관에 정정 요청. 자동 발송은 하지 않음.
8. 재수집 시 원본을 덮어쓰거나 충돌 기록을 삭제하지 않음.

'공식 API가 항상 공포 원문보다 정확하다', '공보라는 파일이면 모든 메타데이터가 무조건 맞다' 둘 다 금지한다. **쟁점별 원문·후속 정정·시점 일치가 판단 기준**이다. 해결된 충돌도 이력은 보존한다. 영향을 받지 않는 다른 규칙까지 일괄 중단할 필요는 없다.

## 5. 법령·고시·회신·지침의 법적 성격

### 5.1 파일 형식이나 기관 로고로 법적 효력을 판단하지 않는다

- 법률·시행령·시행규칙: 적용 범위·위임·부칙을 확인하는 규범.
- 조례·규칙: 지역과 상위법/위임 범위 확인.
- 고시·훈령·예규: 이름만으로 의무/권고를 구분할 수 없음. 상위법의 수권 조항, 위임 내용, 절차, 범위 및 해당 규정 성격 확인.
- 공보·시보: 공포 원문이 담긴 매체. 매체 자체가 독립적인 의무를 만드는 것은 아님.
- 행정처분·허가조건·개별 승인: 해당 대상과 효력 범위 안에서 직접 관리해야 하는 별도 근거.
- 법제처 해석·부처 회신: 해석·집행 방향 자료. 본문 법규나 허가증으로 대체하지 않음.
- KOSHA GUIDE·일반 기술 매뉴얼: 기술 권고/실무 자료. 별도로 법령·허가조건에 편입된 사항이 있는지는 확인.
- 회사 내부규정·ISO 요구·계약 요구: 법규와 구분된 관리 의무. 법률 위반 상태에 그대로 합산하지 않음.

[공식 실무 자료] 안전보건공단은 KOSHA GUIDE가 법적 기준이 아닌 기술적 권고 지침이며 법적 구속력이 없다고 명시한다.[S11]
[공식 실무 자료] 법제처는 정부유권해석이 법원의 사법해석과 달리 법적 구속력은 없으나 행정 운영의 통일을 위한 사실상 구속력을 가진다고 안내한다. 구체적 사실인정이나 이미 이루어진 처분의 위법 여부는 법제처 해석 대상이 아니라는 안내도 있다.[S12]

### 5.2 과거 회신 재사용 조건

회신의 `기관, 문서번호, 회신일, 질문 원문, 당시 법령 버전, 핵심 사실, 지역, 결론 조건, 후속 개정/판례`를 저장한다.

다음 중 하나라도 핵심 차이가 있으면 직접 적용하지 않는다.
- 법령 문언·별표·적용례가 변경됨.
- 대상이 단일물질에서 혼합물로 달라짐.
- 수량의 기준이 일평균에서 최대량으로 달라짐.
- 업종·설비·설치 시점·보호구역·허가 조건이 다름.
- 다른 권한 기관/지역의 회신이고 전국 공통 적용 근거가 없음.
- 질문 원문·전제 조건을 확보하지 못함.

유사 키워드 점수는 '읽어볼 후보'를 찾는 데만 사용한다. 현재 사업장에 적용된 결론은 별도의 검토 승인 대상이다. 회신이 실제 허가·승인 처분인지 단순 의견인지도 내용에 따라 확인한다.

## 6. 원본·OCR·별표·서식 검토 기준

### 6.1 여섯 단계로 분리한다

`발견 → 원본 확보 → 텍스트/표 추출 → 해당 규칙의 결정 항목 대조 → 규칙 구조화·승인 → 운영 판정 연결`.

2,623개 첨부 연결 기록은 unique 원본 수, 법규 수, 별표 수, 검토 완료 수와 다르다. 다음을 별도 집계한다.
- 원천 법규/개정 버전 수.
- 첨부 연결 edge 수.
- unique 파일 해시 수.
- 본문 삽입 이미지 수.
- 별표/서식 엔터티 수.
- 검토한 쪽/표/셀/규칙 수.
- 결정 항목 검수 완료 수.
- 미해결 OCR·누락·버전 충돌 수.

### 6.2 OCR 승인 단위

두 OCR이 같아도 공통 오인식이 있을 수 있다. [설계 권고] 최종 산식에 쓰는 항목은 원문을 육안 대조하고 담당 검토자가 승인한다.

결정 항목:
- 숫자·소수점·범위·단위·농도 기준.
- 이상/초과/이하/미만, 그리고/또는.
- 합산 범위·행/열 머리글·병합셀 의미.
- 비고·각주·단서·예외·별표 상호 참조.
- 품명·시설 유형·시행일·기한.

표 셀별 `원본 페이지/좌표, raw OCR 두 결과, 정규화 값, 셀 경계, 머리글 연결, 각주 연결, 검토자, 검토일`을 둔다. 표 구조가 불분명하면 수치가 읽혀도 계산 규칙 승인 불가.

'문서 전체 전수대조 완료'와 '특정 판정 규칙에 필요한 결정 항목 검증 완료'는 다르다. 좁은 범위 승인 자체는 가능하지만 적용 범위를 명시하고 다른 규칙에 재사용하지 않는다.

### 6.3 삭제 별표·본문 이미지

- 삭제 안내 7건: `deleted_marker`로 보존. 현행 의무/수치 검색에 포함하지 않음.
- 과거 기준일: 해당 별표가 유효하던 연혁 원본을 다시 찾음. 현행 '삭제' 이미지를 과거 규정 대용으로 쓰지 않음.
- 삭제되었다는 이유만으로 관련 의무 전체가 사라졌다고 결론내지 않음. 본문 이동·고시 위임·번호 변경·대체 별표 확인.
- 본문 이미지 2건: 별표 첨부 수집 성공과 별개. 본문 문단·표 위치에 연결하고 같은 수치/단위/각주 검수 수행.

### 6.4 별지 제1·2호 서식의 완료 기준

원본 파일 확보만으로 완료가 아니다.
`규정/버전 + 서식번호·제목 + 적용 대상 + 제출 기관 + 제출 사건/기한 + 필수 첨부 + 파일 열림 + 결과 화면·다운로드 연결`이 확인되어야 한다.

같은 '별지 제1호'는 법령마다 서로 다른 서식이다. 키는 `(법규 식별자, 버전, 서식번호)`로 둔다. 서식의 존재 자체로 제출 의무를 생성하지 않고 본문의 의무 조항과 연결한다.

### 6.5 수집 종료 기준

'인터넷의 관련 법규 전부를 찾았다'는 무한한 보증 대신, **선언된 업무·대상·날짜 범위의 근거 그래프가 닫혔다**는 기준을 사용한다.
- 적용 법률·하위법·필수 고시·조례·허가조건을 찾음.
- 모든 결정 조건의 위임/인용/별표/단서/부칙 연결을 추적함.
- 미해결 링크, 미확보 결정 첨부, 미검수 결정 셀, 출처 충돌이 없는지 확인.
- 공식 연혁·지역 자료·정정 공고 등 정한 검색 경로를 수행했고 범위를 기록.
- 외부에서 결정되는 사실/기관 재량은 '근거 수집 누락'과 분리하여 보류 항목으로 표시.

한 필수 연결이라도 빠지면 그 영향을 받는 규칙을 `근거 불완전`으로 표시한다. 다른 검토 완료 규칙까지 '모두 검토됨'으로 부풀리지 않는다.

## 7. 물질·수량: 증빙과 계산을 연결하는 기준

### 7.1 실제 제품 동일성

CAS는 성분 검색키이지 구매한 제품·혼합물 전체의 동일성 확정키가 아니다.

[설계 권고] 제품키 후보:
`제조사/공급사 + 제품코드/grade + 제품명 + MSDS 제출번호(해당 시) + 개정일/판 + 조성·물성 연결`.

동일성 관계를 `동일 제품`, `동일 성분`, `염/수화물 관계`, `동일 CAS이나 다른 농도/grade`, `혼합물`, `판정 불가`로 분리한다. 제출번호나 개정일 하나만으로 모든 동일성을 보증하지 않는다.

주요 증빙:
- 공급자 제품 MSDS 제1항(식별), 제3항(구성), 제9항(물성), 제16항(개정 등).
- 제조사 규격서/TDS, 실제 lot COA, 분석 성적서.
- 필요한 경우 해당 법령상 인정되는 시험·검사기관의 위험물 성상 시험.
- MSDS 조성은 함량 범위·영업비밀 대체자료 등이 있을 수 있어 전성분/정확 함량을 보장하지 않는다. 경계값을 가로지르는 범위는 추가 증빙 없이 확정하지 않는다.

### 7.2 API 역할

[공식 자료]
- KOSHA MSDS 조회 API는 공단 화학정보 목록·내용 제공. 자료는 MSDS 작성·검토의 참고용이라고 명시한다.[S17]
- 소방청 국가위험물 DB는 참고용이고 미검색 물질은 비위험물로 확인된 것이 아니라 미확인/미등록일 수 있다고 FAQ에 명시한다. 혼합물에 대해 시험 의뢰 안내도 있다.[S18, S19]
- 한국환경공단 화학물질 정보 API는 CAS·물질명·고유번호로 물질ID, 유사명, 물질분류 유형, 함량·예외·고시 정보를 제공한다.[S20]

규제목록 조회와 실제 구매 제품 동일성 증명은 서로 다른 작업이다. 포털의 '실시간 업데이트' 표시는 개별 물질 변경 즉시 반영 SLA나 웹훅 존재를 보장하지 않는다.

### 7.3 최대량과 단위

다음을 별도 사실로 둔다.
- 허가/신고량.
- 설계 최대량.
- 운영 가능한 최대 동시 저장/취급량.
- 시점 실재고.
- 일평균/연간 취급량.
- 폐기물 월평균 발생량·일련 공사 총량.

규칙에서 요구하는 `quantity_basis`를 골라 계산한다. 다른 기준으로 대체하지 않는다. 최대량을 현재 재고로 대체해서 허가 대상을 누락시키지 않는다.

질량↔부피 변환: `질량 = 부피 × 밀도`. 단위·측정온도·농도·제품 상태를 함께 확인한다. kg를 L처럼 쓰거나 밀도 1을 무조건 가정하지 않는다. 숫자는 부동소수점 임의 반올림 대신 decimal/정확한 단위계로 처리하고 비교 전 원값을 보존한다.

### 7.4 위험물 합산

[법적 기준] 위험물안전관리법 제5조제5항은 동일한 장소에서 둘 이상의 위험물을 저장·취급하는 경우 각 수량을 각 지정수량으로 나눈 값의 합이 1 이상이면 지정수량 이상의 위험물로 본다.[S13]

`합산 배수 = Σ(해당 품명 실제 수량 / 해당 품명의 법정 지정수량)`.

프로그램은 `위험물 품명 판정 → 지정수량·단위 확정 → 동일 장소 범위 확인 → 법적 수량 기준 확정 → 합산` 순서로 처리한다. '같은 사업장 주소'를 법률상 동일 장소로 자동 치환하지 않는다. 도면·허가 경계·시설 배치와 관할 검토가 필요하다.

1 미만이라고 모든 의무가 없다고 결론내리지 않는다. 위험물법 제4조의 지정수량 미만 위험물 관련 시·도 조례 등 다른 경로를 확인한다.

불확실한 수량 범위가 모두 문턱 위면 수량 조건만 참으로 볼 수 있고, 모두 아래면 그 조건만 거짓으로 볼 수 있다. 문턱을 걸치면 미확인이다. 이 방법은 규제 품명과 합산 범위가 확정된 경우에만 쓰며 최종 판정의 다른 미확인 조건을 없애지 않는다.

## 8. 예외 적용: 문장 검색과 대상 인정은 다르다

각 예외를 독립 rule로 만든다.

```text
예외 종류:
A. 조건 충족 시 법률상 자동 제외
B. 증명서/인증/다른 법령상 검사 등이 있어야 대체 인정
C. 기관 허가·승인·재량이 있어야 적용
D. 과거 시설 경과조치/기간 유예
E. 다른 의무로 갈아타는 특례
```

예외마다 `필수조건, 요구 증거, 승인기관, 효력기간, 대상 범위, 잔존 의무, 후속 의무, 법적 근거`를 저장한다.

- 예외조건 모두 충족하고 필요한 기관 승인까지 존재할 때만 적용.
- 하나라도 거짓이면 해당 예외 미충족.
- 결정적인 조건·승인이 미확인이면 자동 적용 불가.
- 기관이 '인정할 수 있다'는 문구를 사용자가 조건을 충족했다는 이유로 '면제됨'으로 바꾸지 않음.
- 한 설비에 대한 예외가 사업장 전체 의무를 없애지 않음.
- 예외가 불명확해서 판정이 보류된 경우, 원칙 의무를 안내할 수는 있지만 예외 부존재가 입증됐다고 표시하지 않음.

예: 자율검사프로그램은 내부 검사 계획서만 있다고 안전검사를 대체하는 것이 아니다. 법정 승인·유효기간·검사기록 등 요건 확인이 필요하다.[S22]

## 9. 결과 분류와 '명확한 법률 리스크' 게이트

### 9.1 세 개의 상호배타적 결과만으로는 부족하다

[설계 권고] 내부 상태는 최소 다음 축을 분리한다.

1. 적용: `해당 / 비해당 / 미확인 / 충돌`.
2. 이행: `확인됨 / 불이행 확인 / 아직 기한 전 / 미확인 / 충돌`.
3. 예외: `적용 / 미적용 / 미확인 / 기관 승인 필요`.
4. 근거: `완전 / 누락 / OCR 미검수 / 출처 충돌 / 해석 쟁점`.
5. 검토: `초안 / 검토중 / 승인 / 변경으로 재검토 필요`.

최종 표시 상태:
- **의무 이행 확인**: 해당 의무·기간·범위에 한정.
- **검토 범위 내 비대상**: 비대상 조건의 근거와 사실 확인.
- **향후/진행 중 의무**: 아직 기한 전, 허가 신청 중 등.
- **불이행 근거 확인**: 아래 게이트 충족.
- **판정 보류**: 부족한 자료·충돌·해석 등 이유 표시.

기존 세 분류를 유지한다면 이들은 결과 전체의 셋이 아니라 쟁점의 **복수 태그**로 쓴다.
`자료 부족`, `해석/기관 확인 필요`, `명확한 법률 리스크`.

자료 부족과 해석 쟁점이 동시에 존재할 수 있다. 쟁점을 나누면 허가 취득 여부는 자료 부족이고, 별도의 관할 해석은 해석 쟁점일 수 있다. 동일 결론에 필요한 필수 사실이 부족하면 그 결론을 '명확한 리스크'로 확정하지 않는다. '준수 확인'과 '비대상'을 세 리스크 태그에 억지로 넣지 않는다.

### 9.2 판정 게이트

```text
불이행 근거 확인 가능 =
대상·행위·범위 식별 완료
AND 적용 시점/지역 확정
AND 구속력 있는 의무 근거 확인
AND 필수 본문·별표·부칙·위임·결정 셀 검증
AND 적용 조건이 검증된 사실로 충족됨
AND 관련 예외·유예·대체 의무 검토 완료
AND 해당 기한 도래
AND 불이행 증거가 업무별 증거 정책 충족
AND 결론에 영향을 주는 사실/출처 충돌 없음
AND 승인된 판정 규칙 버전 사용
```

수동 최종 검토 승인 여부는 별도로 표시한다. 위 조건이 충족된 자동 평가 결과도 '자동 규칙 평가·검토 대기'로 보여 줄 수 있다. 내부 승인 없이 기관 위반 확정처럼 표시하지 않는다.

### 9.3 조건 논리

각 조건은 `참 / 거짓 / 미확인 / 충돌` 중 하나를 반환한다. 기본 단락 평가 원칙:
- AND: 검증된 필수 조건 하나가 거짓이면 그 적용조건 묶음은 거짓. 관련 없는 미확인 조건을 이유로 비대상 결론을 무조건 막을 필요는 없음.
- OR: 검증된 조건 하나가 참이면 해당 묶음은 참.
- 결정적인 조건이 미확인이면 미확인.
- 결론에 영향을 주는 충돌이면 충돌.
- 충돌이 비결정 조건에만 있고 결론이 바뀌지 않으면 그 사실을 경고로 남기고 영향을 명시.
- '참'과 '거짓'을 동시에 지지하는 증거를 임의로 최신/다수결로 골라 삭제하지 않음.

조건 증명의 최소 집합과 영향 없는 조건을 기록하는 `decision_trace`가 필요하다. 이렇게 해야 같은 입력·규칙·근거 스냅샷에 같은 판정이 나온다.

## 10. 대표 업무별로 승인해야 할 판정 규칙

아래는 개별 의무 분리의 실례다. 전체 EHS 규칙집이 아니며, 미확인으로 표시한 별표·고시가 남아 있는 규칙은 운영에서 확정판정에 사용하지 않는다. 조문은 2026-10-08 기준으로 MCP 조회했다. 개정 경계마다 재조회해야 한다.

### 10.1 안전관리자 선임

[법적 기준] 산안법 제17조, 시행령 제16조 및 별표3.[S21]
- 업종, 상시근로자 산정, 건설 여부/공사금액, 도급 관계가 적용 입력이다.
- 별표3 일부 제조업 등에서는 50명 이상 500명 미만 1명 이상, 500명 이상 2명 이상 등의 구간이 있다. 업종별 구간이 다르므로 '모든 회사 50명 이상'으로 일반화하지 않는다.
- 시행령 제16조제2항의 전담 조건과 별표3의 인원 조건은 별도로 계산한다.
- 선임, 전문기관 위탁, 증원·교체, 해임·위탁 해지는 별도의 보고 사건으로 관리한다. 제16조제6·7항에서 14일 보고를 확인했다.
- 공동선임·도급 특례는 대상·거리·합산 인원·금액 등의 조건을 모두 읽어 별도 예외로 관리한다.

증빙: 선임/위탁 문서, 자격 증명, 실제 업무·전담 배치, 보고 기록, 현재 재직/계약 상태.

[미확인] 시행령 별표3 원본 셀 전수 대조, 별표4 세부 자격, 시행령 제19조 위탁 범위, 각 보고 서식, 2027년 이후 별표 변동. 따라서 위 수치를 바탕으로 전체 업종 규칙을 자동 배포하지 않는다. 50명 미만 사업장도 다른 안전보건관리담당자 의무 등을 별도 확인해야 한다.

### 10.2 안전검사와 유해위험방지계획서

[법적 기준] 두 의무는 다르다.[S22]
- 안전검사: 법 제93조, 영 제78조, 규칙 제126조. 사용 설비 종류·규격·설치/차량등록일·건설현장 여부·기존 검사 이력·특례 등이 입력.
- 유해위험방지계획서: 법 제42조, 영 제42조, 규칙 제42조. 설치·이전·주요 구조 변경/착공 사건, 업종·계약전력·설비·공사규모 등이 입력.
- 검사 합격이 계획서 제출·심사 이행을 대신하지 않는다.
- 계획서 제출/심사 결과가 주기적 안전검사 합격을 대신하지 않는다.

확인한 예:
- 영 제78조: 정격하중 2톤 미만 크레인 제외 문구. 하지만 세부 대상 고시까지 확인해야 최종 대상 확정.
- 규칙 제126조: 설비별 최초 검사 기준일과 반복 주기가 다름. 건설현장 크레인 등과 PSM으로 확인된 압력용기에는 별도 주기가 있음.
- 규칙 제42조: 제조업 관련 계획서 제출과 건설 계획서 제출의 기한·서식이 다름.
- 법 제98조 자율검사프로그램: 근로자대표 협의·법정 승인·유효기간·기록 등 요구. 내부 자체점검과 같은 뜻이 아님.

증빙: 동일 설비 식별이 되는 검사 합격증/표시·검사 일자 또는 승인된 대체 검사 자료. 계획서는 대상 공정/설비/공사와 일치하는 제출본·접수일·심사 결과·변경본 및 후속 확인 자료.

[미확인] 세부 대상/제외 고시, 다른 법 검사 면제 세부 조건, 합격표시 별표16, 자체심사 범위 등. 이를 미검증 상태로 수치만 운영 rule에 넣지 않는다.

### 10.3 사업장폐기물배출자 신고

[법적 기준] 폐기물관리법 제17조, 시행규칙 제18조. 확인한 시행규칙 버전은 2026-10-02 시행 MST 290881.[S23]
- 일반 사업장폐기물과 지정폐기물의 처리계획 확인은 분리한다.
- 규칙 제18조에는 배출시설/특정 사업장 시설 운영 여부, 일평균 100kg·300kg, 일련 공사 5톤 등 서로 다른 적용 경로가 있다.
- 중간가공폐기물·폐지·고철·왕겨·쌀겨 등 제외 문구와 해당 예외를 같이 읽어야 한다.
- 기한도 경로별로 사업 개시/최초 배출 후 1개월, 예정 배출일(건설의 경우 착공일), 공동처리 관련 7일 등 다르다.
- 변경신고는 월평균/총배출량 증가, 신규 종류, 상호·주소·처리계획·공사기간 등 사건별 규칙으로 만든다.

중요: '일평균 100kg 미만'은 제18조의 특정 신고 경로에 관한 판단일 뿐, 모든 폐기물법 의무 비대상이 아니다. 다른 대상 경로 및 지정폐기물·건설폐기물 관련 특별 법령을 별도 확인한다. 시험 예시에서 건설 공사 폐기물을 일반 사업장폐기물 규칙 하나로 종결하면 안 된다.

증빙: 종류 판정/분석자료, 발생량 기록·산정 기간, 신고증명서·변경본, 처리계획·수탁자 관련 자료. 신고 미업로드는 신고 미실시가 아니다.

[미확인] 지정폐기물 확인대상·변경 기준 전체, 건설폐기물 별도 법률과의 세부 경계, 수리간주의 보완·연장 처리 및 실제 적용. 운영 rule 승격 전 확인한다.

### 10.4 대기·수질 배출시설

[법적 기준] 대기환경보전법 제23조·시행령 제11조, 물환경보전법 제33조·시행령 제31조.[S24]

판정 순서:
`배출시설 목록 해당 → 규모/형식 제외 확인 → 허가 트리거 확인 → 허가/신고 선택 → 설치/변경 조건 → 가동 개시 관련 의무 → 운영 중 측정·관리 의무`.

- 배출시설에 해당하지 않는 시설까지 '나머지 전부 신고'로 분류하지 않는다.
- 특정유해물질의 함량/발생 기준, 특별대책지역·설치제한지역, 상수원 관련 위치 등이 법규별 허가 트리거가 된다.
- 지도상 직선거리와 법령상 상류 유하거리를 동일하게 계산하지 않는다. 보호구역 경계·고시 버전과 실제 수계 확인이 필요하다.
- 변경허가/변경신고는 증설률뿐 아니라 기존 허가/신고 유형, 배출구별 산정, 용도·오염물질·시설 변경 등 해당 요건을 확인한다.
- 설치허가/신고와 대기 가동개시 신고(제30조), 수질 가동시작 신고(제37조)는 별도 의무다.
- 통합환경허가 적용 및 특례 여부를 선행 확인해야 다른 법 허가·신고 관계를 잘못 중복/누락하지 않는다.

증빙: 설치허가증/신고증명서·변경 이력·허가조건·도면·공정/원료 자료·시험 자료·가동 신고 및 이후 운영관리 기록.

[미확인] 배출시설 세부 별표, 특정유해물질별 수치, 종별 판정 별표, 실제 관할 위임의 개별 대상, 통합환경허가 관계 전체. 미검증 수치는 확정판정에 사용하지 않는다.

## 11. 구현 데이터 모델과 판정 순서

### 11.1 최소 엔터티

```text
Subject         대상/시설/제품/사업장 및 포함·허가 경계
FactAssertion   시간·범위별 사실 주장
Evidence        원본과 입증 범위, 검토 이력
LegalInstrument 법률·조례·행정규칙의 식별
LegalVersion    MST/공포번호/공포일/본문/부칙/첨부
LegalClause     조항호목과 효력·적용례
SourceConflict  필드·본문·시간·관할별 충돌
Rule            적용조건·예외·의무·기한·필수근거
Obligation      대상·기간·행위에 발생한 개별 의무

ReviewApproval  규칙/추출/사업장 판단별 승인
ChangeEvent     법령·사실·증빙·엔진 변경
CollectionRun   수집 job·페이지·상세·첨부·체크포인트
ReleaseManifest 검증한 배포물·데이터·규칙 버전
```

원본은 가급적 content-addressed 저장소에서 SHA-256 등으로 식별한다. 해시는 변조 탐지/동일 파일 구분이지 내용의 법적 진실성 보증이 아니다.

### 11.2 규칙 예시: 최종 배포용이 아닌 스키마 샘플

```json
{
  "rule_id": "EXAMPLE-LEGAL-001",
  "domain": "규칙 분야",
  "subject_type": "설비",
  "trigger": "설치/운영/변경 등 검증된 사건 유형",
  "effective_rule": {
    "clause_valid_from": null,
    "clause_valid_to": null,
    "transition_predicate_ids": []
  },
  "applicability_predicate_ids": [],
  "exception_rule_ids": [],

  "deadline_policy_id": null,
  "authority_rule_id": null,
  "quantity_basis": null,
  "aggregation_scope_rule_id": null,

  "required_annex_cells": [],
```

`null`을 기본값/0/비대상으로 바꾸지 않는다. 샘플 규칙은 계산·허가 판정에 사용하지 않는다.

### 11.3 실행 알고리즘

```text
evaluate(issue, immutable_snapshot):
  1. 대상/행위/시간/범위와 입력 충돌을 식별한다.
  2. 선언된 검토 범위의 법적 근거 그래프를 구성한다.
  3. 조항별 시행·경과조치에 맞는 버전을 고른다.
  4. 결정 근거 누락/미검수/출처 충돌을 분류한다.
  5. 적용조건을 참/거짓/미확인/충돌로 평가한다.
  6. 결정적인 적용조건이 거짓이면 제한된 비대상 결과를 만든다.
  7. 결정 조건이 미확인/충돌이면 판정 보류와 추가 확인항목을 만든다.
  8. 해당이면 예외·대체 의무·기관 승인을 평가한다.
  9. 의무 발생일·기한과 이행 사건을 계산한다.
 10. 완료증거와 불이행증거를 각각 평가한다.
 11. 기준을 충족한 상태만 표시하고 나머지는 보류한다.
 12. decision_trace, evidence_ids, rule/version IDs를 저장한다.
 13. 위험성·긴급 조치 경로는 병렬로 실행한다.
 14. 담당 검토자에게 관련 범위만 승인 요청한다.
```

선행조건이 불확실할 때도 결정과 무관한 비대상 조건이 이미 검증되어 있으면 불필요하게 전체를 보류하지 않는다. 반대로 필요한 예외·별표·관할 정보가 읽히지 않았으면 모델 문장만으로 결론을 채우지 않는다.

LLM 역할: 쟁점 분해·자료 검색 보조·추출 후보·설명 초안. 승인된 deterministic engine 역할: 수치·단위·기한·대상·예외 평가. 검토자 역할: 추출/규칙 승인·해석·증빙 충분성·기관 확인. LLM이 임의로 rule을 생성하고 즉시 운영 적용하는 경로는 막는다.

## 12. 32개 API 및 수집 운영의 완료 기준

### 12.1 API 등록부를 먼저 만든다

각 API별로 다음을 기록한다.
- 제공기관/업무 목적/현재 명세 URL 및 명세 버전.
- 서비스·endpoint·목록/상세/첨부 경로.
- 인증키 인코딩·필수 파라미터·검색 언어·동의어/식별자.
- 대상 식별 필드·공포/시행/개정/수집일 필드.
- 페이지 크기·정렬·totalCount·다음 페이지 조건.
- HTTP 오류와 payload 오류코드의 구분.
- 일/초/월 등 호출 한도 단위와 운영 승인 여부.
- timeout·재시도·체크포인트·스키마 변화 정책.
- 원본 보존 위치·이용허락·개인정보 포함 여부.
- 실제 정상 사례·0건 사례·오류 사례·부분 성공 사례.

32개라는 수는 서비스 수인지 endpoint 수인지 분리한다. 한 서비스의 17개 endpoint가 모두 '독립 API 연동 완료'인 것처럼 집계하지 않는다.

### 12.2 정상/0건/실패/불완전을 구분

```text
success_with_items       정상 응답 및 항목 있음
success_empty            명세에 맞는 정상 응답, 결과 없음
transport_error          네트워크/HTTP 오류
provider_error           제공기관 payload 오류
auth_error               인증/권한 문제
rate_limited             한도 초과
schema_error             응답 구조/필수 필드 변화
partial                  목록 일부·상세·첨부 누락
complete_for_scope       선언된 수집 범위 충족
```

어떤 상태도 직접 `법적 의무 없음`으로 변환하지 않는다. 의무 여부는 법규 rule 엔진의 결과다.

공식 소방청 API 명세에서는 목록 응답에 결과코드 `00`, 결과메시지, pageNo, numOfRows, totalCount, chemicalno 등이 있다.[S18] 이 필드 구성을 다른 31개 API에 추정 복제하지 않는다.

### 12.3 A01과 A07

- A01 0건: 정상 빈 결과 처리만 확인한 것. 실제 상세·첨부·후속 연결은 미검증. 별도의 공식 정상 데이터 식별자로 read-only 재검증한다.
- 정상 데이터가 공개 범위에 없으면 `정상 사례 검증 미완료`라고 표시한다. 제공기관 문서 fixture 기반 계약 테스트와 실제 라이브 검증을 분리한다.
- A07 간헐 오류: 시각·endpoint·파라미터의 민감정보 제거본·HTTP status·payload code·지연시간·시도번호를 기록한다. 재현 사례, 복구 사례, 재시도 종료 사례를 각각 확보한다.

### 12.4 재시도 정책

[설계 권고] API별 설정을 두고 기본 예시는 다음과 같다.
- timeout/네트워크/일시 5xx: 1초→2초→4초 등 제한된 exponential backoff+jitter. 실제 간격·횟수는 제공기관 정책과 부하에 맞춰 조정.
- 429: Retry-After가 있으면 우선 준수. 일 호출 한도 소진이면 같은 요청을 계속 재시도하지 않고 다음 허용 시점까지 보류.
- 인증 실패/필수 파라미터 오류/스키마 불일치: 무한 재시도 금지. 설정·명세 확인 필요.
- 재시도 횟수 소진: 실패/부분 성공을 보존하고 사용자에게 누락 영향 안내.
- 로그·URL·백업에 서비스키가 들어가지 않게 마스킹.

HTTP 200이어도 HTML 오류문이나 payload error일 수 있다. MIME·schema·업무 결과코드를 검증한다. 빈 문자열·null을 0으로 파싱하지 않는다.

### 12.5 페이지·상세·첨부

- 원문 응답을 보존하고 부모 목록→상세→첨부 관계를 기록.
- 단일 item/배열 item/null/빈 배열/중첩 링크를 명세와 사례로 확인.
- 알려진 totalCount에 도달했다고 끝내기 전에 unique ID 중복·페이지 누락·정렬/전체 수 변화 확인.
- 수집 중 데이터가 변하면 run-start snapshot을 지원하는지 확인. 지원하지 않으면 변동을 감지해 재조회/중복 제거하고 수집 일관성 한계를 기록.
- 상세 호출 성공과 모든 결정 첨부 확보를 별도 완료 상태로 둠.
- 본문 이미지, HWP/PDF 첨부, zip 내부 파일, 폐지/삭제/정정 자료를 별도 추적.
- checkpoint는 page/item 처리 후 원본 저장·연결 기록이 확정된 지점에 남김. 취소는 삭제가 아니라 resumable 상태.
- 같은 작업 재실행은 idempotent하게 새 버전/중복 연결을 구분하며 수동 검토·충돌 해결 이력을 덮어쓰지 않음.

### 12.6 완료의 증거

각 API마다 `정상 비어 있지 않은 사례 → 상세 → 다음 페이지 → 첨부 → 동일 대상 연결 → 오류 → 한도 → 중단/재개 → 변경/삭제` 중 **해당 API가 실제 제공하는 경로**를 검증한다. 제공하지 않는 경로는 '기능 미제공', 지원하지만 못 확인한 것은 '미검증'이다.

키 저장·시험 호출 성공은 `인증/연결 확인` 단계다. 법적 대상 식별과 end-to-end 증거 연결까지 통과해야 `운영 사용 검증 완료`다. 이번 보고서에서 32개 전체를 호출·검증하지 않았으며 A01/A07 상세 명세도 제공받지 않았다.

## 13. 검색 누락과 AI 입력 생략

### 13.1 키워드 검색을 근거 그래프 탐색으로 보완한다

검색 사전: 법령 정식명·약칭·옛 제명, 업종·시설 용어, 물질 동의어/CAS/고유번호, 허가·신고·선임·교육·검사 행위.

후속 탐색 edge: `정의 → 적용범위 → 의무 → 대통령령/부령 위임 → 고시/별표 → 예외/단서 → 부칙 → 지방 위임 → 서식 → 허가조건`.

국가법령정보 공동활용은 시행일/공포일 목록·본문, 연혁, 변경이력, 위임·인용 연계, 별표/서식 등을 별도 API로 제공한다.[S25] '목록 검색 하나'를 '전 법규 근거 검색'으로 보지 않는다.

위험 기반 우선순위는 검색 순서를 정하는 방법이지 필수 근거를 생략할 권한이 아니다. 관련성이 높더라도 버전/대상 불일치 자료는 결론 근거에서 제외한다.

### 13.2 AI가 실제 받은 부분을 기록한다

```text
retrieval_manifest:
  읽은 조항/별표/페이지/셀
  AI 입력에 포함한 구간
  생략한 구간과 이유
  생략 구간 중 결정 조건/예외 여부
  필수 근거 충족 여부
```

- 전체 파일을 수집했어도 AI에 전달하지 않은 부분을 읽었다고 쓰지 않는다.
- 요약만 전달했으면 요약의 검증·원문 연결·예외 보존 여부를 표시.
- 토큰 한도 때문에 단서/비고가 잘렸다면 해당 판단을 보류하거나 그 부분을 추가 검색해 읽음.
- 긴 문서 전체를 반복 전송하기보다 검증한 결정 조항·조건·각주를 구조적으로 선택하되 원문 접근을 유지.
- 출처 충돌은 retrieval에서 제거하지 않음. 충돌을 모델 설명문 하나로 해소하지 않음.
- 보고서에 근거별 '원문 검토됨/공식 텍스트 검토됨/OCR 결정 항목 검수됨/미검토' 표시.

## 14. 승인 범위·변경 관리·무효화

### 14.1 세 종류의 검토 승인을 분리한다

1. **추출 승인**: 특정 버전의 특정 조항·표 셀을 올바르게 읽었는가.
2. **규칙 승인**: 그 문언을 적용조건·예외·산식·기한으로 올바르게 옮겼는가.
3. **사업장 판단 승인**: 특정 대상·기간·사실 스냅샷에 해당 규칙 적용이 적절한가.

최소 approval key:
`법적 근거 버전/원문 해시 + 결정 셀/조항 + rule 버전 + 검증된 사실집합 + 대상/범위 + 기준일 + 엔진 버전`.

문서 전체 승인 하나가 미래의 모든 사업장 판정을 승인하는 구조는 금지한다. 동일 문서 안에서도 미검수 표와 검수 완료 조항을 분리한다.

### 14.2 무엇이 바뀌면 재검토할까

- 원문 byte 변경: 원본 변경 이벤트. 공백/메타데이터만인지 실제 규범 변경인지 비교. 의미 차이가 불명확하면 관련 승인 재검토.
- 숫자·단위·대상·예외·각주·시행일 변경: 해당 rule와 의존 결론 재검토.
- 아직 시행 전 개정: 현행 승인 즉시 폐기 대신 미래 적용 rule 검토 및 시행일 전환 예약. 실제 의존 관계에 영향 없으면 유지.
- 허가량·시설·물질/농도·업종·인원·장소·사용 상태 변경: 관련 사업장 결론 재검토.
- 승인/인증 유효기간 종료: 효력이 필요한 예외와 이행 판단 재검토.
- 관할 변경: 접수/보고 rule 재검토. 이미 유효한 허가 자체의 효력까지 자동 취소했다고 표시하지 않음.
- 계산엔진/추출 로직 변경: 영향 rule 재실행·회귀 테스트.
- 새 출처 충돌 발견: 영향 결론을 '재검토 필요'로 표시하고 자동 확정 중지.

'무효화'는 프로그램의 기존 승인 재사용을 막는다는 뜻이다. 법적 허가·인증 자체가 무효가 되었다고 선언하는 것이 아니다. 과거 승인과 결론은 당시 스냅샷으로 보존한다.

### 14.3 승인 책임 분리

[설계 권고] EHS 담당은 사업장 사실·서류·현장과 업무 적합성을, 해당 분야 법규 검토자는 규칙·해석을, 개발/QA 담당은 계산·수집·배포를 확인한다. 쟁점에 따라 변호사·노무사·안전/환경/소방 관련 전문가 및 관할기관 확인 경로를 연결한다. 모든 사안에 동일 전문가 한 명의 검토만 요구하거나 내부 승인을 기관 승인으로 표시하지 않는다.

## 15. 한국어 표시·배포·백업·운영 완료 기준

### 15.1 한국어 UI

- 내부 enum은 영문이어도 표시 문자열은 별도 i18n 사전으로 관리.
- 미등록 enum: '알 수 없는 상태: 관리자 확인 필요'처럼 안전한 한국어 fallback. raw 코드는 지원용 상세에만 구분 표시.
- 화면, toast, 빈 상태, 오류, 로그 다운로드, CSV/보고서, 팝업, 승인 문구를 E2E 확인.
- 영문 삭제 정규식으로 법령 원문·MSDS·제품명·CAS 등 원래 필요한 표기를 훼손하지 않음.
- 새 enum 추가 시 translation completeness 테스트 실패가 나게 함.

### 15.2 작성·검증·배포는 서로 다른 상태

```text
코드 작성됨
→ build 성공
→ 같은 commit 전체 테스트 성공
→ 같은 commit+데이터+규칙으로 staging E2E 성공
→ 승인된 배포물 생성
→ 운영 서버 배포
→ 실제 serving version 확인
→ 운영 smoke test 및 보고서 확인
```

'227개 통과 후 추가 변경'이라면 227개 결과는 이전 commit의 근거다. 변경 후 build만 성공한 것은 회귀 테스트 완료가 아니다. 최신 commit으로 전체 테스트·실제 화면·보고서·수집/복원까지 다시 확인한다.

배포 manifest:
`git commit/build ID + artifact digest + rule_set_version + data_snapshot_id + migrations + 테스트 실행 ID + 검토자 + 배포시각 + 현재 serving ID`.

서버 build ID가 검증한 ID와 다르면 완료 아님. 데이터 import가 별도 검증 공간에만 있으면 운영 데이터 갱신 완료 아님. 같은 hash인 파일이라도 실제 rule와 화면 연결 확인이 필요하다.

NIST SSDF는 릴리스 무결성 확인, provenance 및 안전한 개발/검증 관행의 참고 기준이다. 아래 배포 게이트가 한국 EHS 법률에서 직접 명시된 절차라는 뜻은 아니다.[S26]

### 15.3 수집 운영화

앱 기능으로 `범위 선택 → dry-run 계획 → 실행 → 진행 상태 → 중단 → 체크포인트 재개 → 실패 항목 재처리 → 차이 검토 → 승인 → 운영 반영` 흐름이 가능해야 한다.

오래 걸리는 작업을 브라우저 요청 하나에 묶지 않고 job queue·worker·run ID로 관리한다. 수집 완료와 운영 import 승인/완료는 별도 단계다. 실패 항목이 있는데 진행률 100%만 보고 완료라 쓰지 않는다.

### 15.4 백업의 재현성

복원해야 하는 항목:
- 질문·답변·사업장 사실 이력·문서 증빙.
- 법규 원문·공포 첨부·본문 이미지·별표·서식.
- OCR raw·셀 구조·정정/검수 결과.
- 버전·부칙·근거 관계 그래프.
- 충돌 기록·해결 근거·승인 이력.
- rule/engine/prompt/model 버전 및 당시 AI 입력 manifest.
- 수집 run/checkpoint·배포 manifest·필요한 설정과 migration.

테스트: 깨끗한 별도 환경에서 외부 API가 잠시 불가해도 저장한 스냅샷으로 **동일 deterministic 판정·근거 추적**이 재현되는가. 생성 AI의 새 문장까지 byte 동일하게 나오는 것은 보장하지 않는다. 이전 생성 답변을 그대로 보존해 당시 결과를 조회할 수 있어야 한다.

암호화는 '안전하게 보관'이라는 말 대신 실제 상태를 표시한다.
`전송 암호화`, `서버 저장 암호화`, `다운로드 백업 자체 암호화`, `키 관리 방식`을 별도 표기. 미확인/미암호화 상태를 숨기지 않는다. 암호화 백업의 키를 같은 zip에 평문 보관하지 않는다. 개인정보·건강자료·영업비밀의 접근권한, 최소수집·보존/삭제, 로그 마스킹을 별도로 설계한다. 모든 문서를 무기한 보존하는 방식은 피하고 법정 보존기간·보안정책에 맞춘다.

### 15.5 자동 업데이트

[설계 권고, 기관이 정한 갱신 SLA 아님]
- 공급자 제품 변경 MSDS/조성/규격서 수신 시: 해당 제품 rule·판정 재검토 큐.
- 법령/고시: 관심 목록 일 단위 변화 확인과 시행일 전환 점검.
- 공개 물질 DB: 관심 식별자의 수정일/내용 hash 비교. 날짜필드가 없으면 주기적 재조회·hash 비교.
- 재고: 입출고/운영 데이터 변경 시 관련 수량 rule 재계산.
- 시설: 설치/증설/이전 승인 사건과 실제 변경 완료 사건 모두 관리.
- 원문 변경은 자동 수집하되 의미 차이·예외·기관 허가를 자동 확정하지 않음.

자동 업데이트가 기관 허가·변경신고를 자동으로 끝낸다는 뜻은 아니다. 영업비밀 자료를 외부 AI 서비스에 보내는 정책도 승인·보안 조건을 별도로 정한다.

## 17. 인수 테스트: 최소 제안 세트

다음은 **시험 설계**이며 실행 결과가 아니다. 숫자 예시의 규제 품명/특정 업무는 해당 업무 원본 검증을 전제로 한다.

### A. 사실·증빙·충돌
1. 허가증 미업로드: '허가 상태 미확인', 무허가 금지.
2. 교육 파일 미업로드: 미실시 금지, 기록 확인 요청.
3. 사용자 확인 버튼만 클릭: 객관적 검증 상태 변화 없음.
4. 만료된 인증서: 과거 유효 이력 유지, 현재 예외 효력 재검토.
5. 다른 설비의 합격증: 동일 대상 연결 실패, 이행 미확인.
6. 시간 비중첩 500L→800L: 변경 이력, 모순 아님.
7. 동시 같은 탱크 재고500/800L: 충돌 후보/결정 영향 표시.
8. 허가량800L/재고500L: 서로 다른 fact, 충돌 아님.

11. 조항별 분리 시행: 문서 머리 시행일로 모든 조항을 전환하지 않음.
12. 의무 시행/제재 시행이 다름: 의무 판단과 제재 판단 분리.
13. 기존시설 경과조치: 설치·허가·변경일 사실이 없으면 보류.

15. 소방서 2개 관할 걸친 이송취급소: 단순 소방서장 자동 선택 금지.

17. 미래 처분 법령 미확정: 예상 기준으로만 표시하고 최종 처분시 재검토.

### C. 표·물질·수량·예외
18. OCR '미만'→'이하' 불일치: 결정 셀 검수 전 계산 금지.
19. 숫자 일치/표 머리글 누락: 동일하게 검수 보류.
20. 삭제 별표: 현행 규칙 생성 금지, 과거 버전 탐색.
21. 본문표가 계산에 필요하나 미수집: 근거 불완전.
22. 같은 CAS/제품 농도 다름: 동일 제품 자동 병합 금지.
23. MSDS 함량 범위가 법정 문턱을 걸침: 추가 자료 요청.
24. kg↔L 밀도/온도 조건 미확인: 확정 환산 금지.
25. 위험물 합산 배수 0.9999/1.0000/1.0001: 원값 decimal 비교, 임의 반올림 금지.
26. 합산 장소 scope 미확인: 문턱 계산만으로 최종 대상 확정 금지.
27. 지정수량 미만: 지자체 소량 위험물 조례 등 후속 경로 확인.
28. 예외 요건 충족 주장/법정 승인 없음: 예외 확정 금지.
29. 유효한 승인/대상 다른 시설: 다른 시설에 예외 확장 금지.
30. 안전검사 합격/계획서 이행 미확인: 계획서 별도 상태 유지.
31. 설치허가 확인/가동신고 미확인: 가동신고 완료 금지.

### D. 수집·표시·배포·복원
32. HTTP200 + 오류 payload: success로 집계하지 않음.
33. item 단일객체/배열/null: 명세별 normalize 후 누락 없음.
34. page 중복/전체 건수 변동: unique와 변화 감지, complete 과대표시 없음.
35. 상세 실패/첨부 성공 일부: 부분 수집과 영향 표시.
36. 429/일한도 초과: 무한 재시도 없음, 재개 가능한 보류.
37. cancel→resume: 이미 저장한 원본·검수·충돌 유지.
38. 새 enum: 한국어 fallback/번역완전성 테스트 실패 처리.
39. LLM input 예외 잘림: 관련 판정 보류.
40. 충돌 원문→재수집→교체→복원: 충돌 이력이 남음.
41. 227 tests 이후 commit 변경: 이전 test run을 최신 검증처럼 표시하지 않음.
42. staging/운영 serving ID 불일치: 배포 완료 금지.
43. 원문/OCR 포함 백업 복원: 동일 deterministic 판정·근거 링크 재현.
44. 암호화 미확인 백업: '암호화됨' 표시 금지.
45. 분류에 자료부족+해석쟁점 동시 존재: 복수 이유 저장, 명확리스크 오판 없음.
46. 결정에 무관한 부차 입력 미확인: 검증된 비대상 증명은 제한 범위에서 유지.
47. 원문 변경으로 영향 받은 rule만 재검토: 무관한 승인도 일괄 삭제하지 않음.
48. 급박한 위험 증거: 법규 검토 보류와 별도로 긴급 조치 안내/보고.

추가 필수: 업무별 문턱값 바로 아래/동일/바로 위, 기한 하루 전/당일/다음날, 예외 승인 유효기간 전/후, 원문 개정 전/후, 다른 지역/다른 대상. 이들은 원본 확인된 규칙마다 자동 생성한다.
