- 조사 기준일: 2026-10-08
- 성격: 공식 원문 기반 실무·구현 기준 보강 및 개발 에이전트용 지시문.
- 기존 명세는 보존한다. 이 문서는 `EHS_전체답변_상세구현명세_통합.md`의 동반 문서다.

## 1. 핵심 재평가

현재 가장 필요한 것은 법령 검색 결과 확대나 화면 개선보다 **무엇이 확인되어야 판정할 수 있는지, 무엇이 부족하여 보류하는지, 무엇을 확인하면 보류를 끝낼 수 있는지**를 시스템 객체로 만드는 것이다.

개발 완료의 분모를 테스트 수로만 잡으면 누락된 법적 예외·증거의 충분성·사업장 동일성·새 법령 버전·API 부분 실패·승인 우회 같은 위험이 가려진다. 따라서 다음 세 층을 나누어 관리해야 한다.

1. 소프트웨어 검증: 코드와 저장·복구·권한·API 상태가 의도대로 작동하는가.
2. 법적·실무 검증: 적용성·기산점·예외·의무 분리·증거정책이 원문 및 실무에 맞는가.
3. 실제 사업장 검증: 해당 사실·시설·제품·사람·기간·이행을 실제 자료로 확인했는가.

이번 문서는 두 번째 층을 보강하고 첫 번째 층의 인수 기준을 제안한다. 세 번째 층을 수행했다고 주장하지 않는다.

## 2. 추가 공식 조사에서 확인한 사항

### 2.1. 점검 이후 조치와 효과 확인이 필요하다

[법령 원문 확인] 중대재해 처벌 등에 관한 법률 시행령 제5조제2항은 안전·보건 관계 법령의 의무이행을 반기 1회 이상 점검하고, 직접 점검하지 않은 경우 결과를 보고받도록 한다. 미이행 사실이 확인되면 인력 배치·추가 예산 편성·집행 등 필요한 조치를 하도록 규정한다. 교육의 실시 여부 점검과 미실시 교육의 이행 조치도 별도다.

이는 해당 법령 적용 대상과 범위 안에서의 의무다. 모든 사업장·모든 EHS 법령에 같은 주기와 책임자를 일괄 적용하는 근거가 아니다.

[설계 권고] 문제 발견→보고→담당자·자원 배정→조치→완료 증빙→재확인의 lifecycle을 둔다. 완료 주장과 효과 확인을 구분한다. 업무관리 일정은 법정 기한과 다른 필드로 둔다.

출처: https://www.law.go.kr/LSW/lsSideInfoP.do?lsiSeq=277417&joNo=0005&joBrNo=00&docCls=jo&urlMode=lsScJoRltInfoR

### 2.2. 보존기간을 일괄 3년 또는 5년으로 만들면 안 된다

[법령 원문 확인] 같은 시행령 제13조는 규정된 조치 등의 이행사항을 서면 또는 전자문서로 작성하여 이행한 날부터 5년 보관하도록 한다. 조문에는 소상공인 제외와 대상 조치 범위가 있다.

[법령 원문 확인] 위험물안전관리법 시행규칙 제68조는 일반 정기점검 기록 3년, 구조안전점검 기록 25년 또는 해당 조건에서 30년을 규정한다.

[확인 범위 제한] 산업안전보건 근로자 교육기록의 일반적인 법정 보존기간은 이번 조사에서 근거를 확정하지 못했다. 참고양식이나 기관의 운영상 권고를 법정 보존의무로 바꾸지 않는다. 선임 서류 등 다른 기록의 보존규정을 교육기록 전체로 확장하지 않는다.

[설계 권고] `record_type + legal_basis + applicability + retention_start_event + retention_period + internal_policy`로 분리한다. 개인정보 최소 보존과 감사 이력 보존의 충돌도 검토한다.

### 2.3. 위반사실은 문서 유무가 아니라 특정 사실 묶음으로 관리한다

[MCP 원문 확인] 「환경오염물질배출시설 등에 관한 통합지도·점검규정」 현행 레코드 ID 2100000278872, 시행 2026-05-08, 훈령 제37호의 제13조는 점검 결과 법령 위반사항에 대한 위반확인서를 받고, 이를 6하 원칙에 따라 작성하도록 한다. 점검자 전원의 인적사항과 사본 교부를 규정한다.

같은 규정 제6조는 기관의 사업장 현황관리와 변경 허가·신고의 수정·보완을 규정한다. 제22조는 행정처분 이행 완료까지 이행 여부를 관리하고, 이행상태가 부실하면 관계규정에 따른 조치를 하도록 한다.

[범위 주의] 이 훈령의 해당 조항은 점검기관·공무원·자치단체의 절차를 정한 것이다. 민간 앱의 모든 내부 판단에 법정 위반확인서를 요구하는 근거가 아니다. 민간 검토 기록을 행정기관이 작성한 위반확인서로 포장하지 않는다.

[설계 권고] 내부 검토 기록에는 적어도 의무자·시설·장소·행위·시점·의무·기한·이행 상태·증거·예외 검토·검토자의 범위를 담는다. 증거가 없는 것과 적극적인 불이행 사실은 구분한다.

정확한 최신 웹 원문 URL은 이번 부모 세션에서 직접 열지 않았고 MCP 원문으로 확인했다. 이전 조사에서 보았던 2025년 훈령 제788호를 2026-10-08의 현행 규정으로 다시 인용하지 않는다. 후속 개발은 해당 ID 및 기준일로 원문을 재확인한다.

### 2.4. 공식 가이드북도 현행 법령의 대체물이 아니다

[공식 가이드 원문 확인] 고용노동부 「안전보건관리체계 구축을 위한 가이드북」 게시 페이지 등록일은 2021-08-29이다. 연결된 PDF는 154쪽이다. PDF 1~2쪽은 법적인 효력이 없는 참고자료임을 명시한다.

PDF 112~113쪽(인쇄 쪽수 111~112쪽)은 결과 지표만이 아니라 과정 지표를 설정하고, 전문성을 갖춘 점검팀이 면담·서류확인·현장점검으로 운영을 확인하며, 문제·개선방안을 보고하고 필요한 자원을 배정하는 절차를 제시한다.

PDF 114쪽(인쇄 113쪽)은 중대재해법 시행령 **입법예고안**을 인용한다. 따라서 이 가이드의 실무 방법은 참고할 수 있지만 법령 설명은 기준일 시행 조문과 따로 대조해야 한다. 첨부 URL의 `file_seq=20251100130`을 문서의 법적 내용이 2025년에 현행화되었다는 근거로 쓰지 않는다.

[설계 권고] 출처의 게시일·재등록일·문서 작성일·법령 인용 기준일을 각각 저장한다. 과정 지표에는 증거 미확인 해소율, 조치 재확인율, 변경 재검토 처리율, 오류 상태 분리율을 포함할 수 있다. 이는 프로그램 권고이지 법정 KPI가 아니다.

### 2.5. 위험물 선임·신고·대리자와 점검·제출은 따로 평가한다

[법령 원문 확인] 위험물안전관리법 제15조는 최초 선임, 해임·퇴직 후 30일 내 재선임, 선임한 날부터 14일 내 신고, 부재·공백 시 대리자 지정, 대행기간 30일 상한을 구분한다.

최초 선임과 해임 후 재선임은 같은 사건이 아니다. 재선임 기한 안이라는 이유로 대리자 지정 의무가 사라진다고 판정하면 안 된다. 신고 기록이 없다는 사실만으로 선임 자체가 없다고 확정할 수도 없다.

[법령 원문 확인] 법 제18조는 정기점검, 결과 기록·보존, 점검일부터 30일 내 결과 제출, 특정 시설에 대한 정기검사를 구분한다. 점검을 실시하고 제출만 늦은 사례와 점검 자체를 하지 않은 사례는 다른 의무·상태다.

[설계 권고] 조문 하나를 checkbox 하나로 만들지 않는다. 결과 제출 접수, 자격·교육·실제 업무수행 등 증거가 보여주는 범위를 제한한다.

### 2.6. 예외에 법에 없는 승인 요건을 추가하지 않는다

[법령 원문 확인] 위험물안전관리법 제9조제1항 단서는 변경허가 신청 때 화재예방 조치서류를 제출하는 경우 변경공사와 관계없는 부분을 완공검사 전에 미리 사용할 수 있도록 한다. 시행규칙 제21조는 관련 서류를 첨부해 신청하도록 한다.

확인한 두 조문에는 ‘가사용 승인서’가 법정 증빙이라는 문구가 없다. 별지 제16·17·27호 서식 처리란이나 추가 기관 절차까지 모두 확인한 것은 아니므로, ‘어떤 승인 절차도 존재하지 않는다’는 전면적 결론 역시 내리지 않는다.

[설계 권고] 확인한 법정 신청·첨부·사용 범위 요건을 평가하고, 조문·서식·추가 절차 원문을 확인하지 않은 승인서를 보편적 필수서류로 요구하지 않는다. 예외마다 승인·신고·신청·증빙 요건이 다르므로 공통 boolean으로 합치지 않는다.

### 2.7. ‘검사일’과 ‘확인증 발급일’은 실제 법정 기산점에 맞춰 구분한다

[법령 원문 확인] 위험물안전관리법 시행규칙 제70조는 정밀정기검사를 설치허가에 따른 완공검사합격확인증을 **발급받은 날부터 12년**, 최근 정밀정기검사를 **받은 날부터 11년**의 기간으로 규정한다. 중간정기검사도 최초 확인증 발급일과 최근 정밀·중간검사를 받은 날을 구분한다.

소방서장이 따로 지정하는 검사 시기와 구조안전점검 때 정밀정기검사를 함께 받는 조항도 있다.

[확인 범위 제한] 반복 검사의 ‘검사를 받은 날’에 해당하는 구체적인 업무 기록의 날짜를 기관 절차·고시·해석례까지 전수 대조하지는 않았다. 검사종료일과 확인증 발급일을 하나의 필드로 합치지 않는다. 이른 날짜에 내부 알림을 보낼 수 있지만 그것을 확정 법정 기한으로 출력하지 않는다.

### 2.8. 검사 신청과 합격 간주는 다른 상태다

[법령 원문 확인] 산업안전보건법 시행규칙 제124조제1항은 만료일 30일 전 신청서 제출을 규정한다. 제2항은 기관이 만료일 전후 각각 30일 안에 검사하도록 하고, **그 검사기간 안에 합격한 경우** 만료일에 검사를 받은 것으로 본다.

따라서 확인한 조문만으로 ‘신청만 하면 만료 후 30일 사용 가능’이라는 규칙을 만들면 안 된다.

[법령 원문 확인] 산업안전보건법 제95조는 미검사(면제 제외) 또는 불합격 기계의 사용 금지를 규정한다. 두 조문을 함께 검토하되 만료 후 신청만 있는 상태의 구체적인 사용 가능성을 이번 조사에서 해석례까지 확정하지는 않았다.

[정정] 보조 조사 초안의 ‘만료 후 30일 검사 창 안에서 신청 완료이면 유효 증빙 조건 충족’으로 읽힐 수 있는 문구는 폐기했다. 신청·실시·합격·간주를 분리하고 그 경계 사례는 추가 원문·기관 해석 확인 대상으로 남긴다.

다른 설비의 증명서가 제출되었다면 그 증명서는 현 설비의 증거로 부적합하다. 이 사실만으로 현 설비가 미검사라는 결론을 내리지 않는다.

## 3. 의무별 증거정책의 구성

아래는 법정 통일 서류 목록이 아니라 프로그램 설계 권고다. 개별 의무의 원문이 요구하는 법정 서식·신청·첨부·보존은 별도 속성으로 관리한다.

### 3.1. 필수 정책 필드

- `obligation_id`, `rule_version`, `basis_date`, `source_version`.
- 의무자·사업장·시설·제품·사람의 범위.
- 적용성 사실요소 및 검증 상태.
- 사건·기산점·기한·간주·연장 요건.
- 필요한 사실요소와 각 사실을 입증할 수 있는 경로.
- 단독으로 불충분한 자료.
- 이행 확인·불이행 확인·비대상 확인 기준.
- 보류 사유, 최소 추가 자료, 대체 확인 방법, 검토자.
- 법정 요건과 내부 증거정책의 구분.
- 승인 범위 및 변경 재검토 트리거.
- 제재·처분의 별도 근거와 확인 범위.

### 3.2. 교육

확인 대상은 대상자·교육 종류·시기·시간·내용·강사·방식·면제·감경이다. 출석명단은 참석 근거이지 모든 요소의 증거는 아니다. 법정 서식이 없는 경우 특정 기관 참고양식만 강제하지 않는다. LMS·전자기록·현장교육 보고서 등 허용 가능한 증거 경로를 둔다.

특별교육→채용·변경 교육의 간주와 그 역방향을 구분한다. 정기교육의 반기·연간 등 기간, 직무·고용기간별 시간을 기준일 원문과 별표로 확인한다. 미확인한 교육기록 보존기간은 내부 권고로만 설정한다.

불이행 후보는 교육 대상과 이행 내용의 실제 부족이 확인되는 경우다. 일부 기록 미제출·다른 교육시스템 보관 가능성이 남아 있으면 기록 부재만으로 미교육을 확정하지 않는다.

### 3.3. 안전관리자

선임·자격·전담·공동선임·위탁·실제 업무수행·보고·해임보고·교체명령을 분리한다. 발령·계약은 선임 사실, 자격증·경력은 자격, 조직도·업무분장은 전담 검토, 보고 접수는 제출 사실에 연결한다.

산업안전보건법 시행령 별표3·4 전체, 보고의 법적 수리 성격, 해임보고 신설 부칙의 적용시점은 확인 범위가 부족하다. 관련 부분을 완성된 production rule로 승인하지 않는다.

위험물 관리자는 최초 선임·재선임·신고·대리자·대행기간·실제 감독의 별도 rule로 관리한다. 14일·30일을 하나의 공통 기한으로 합치지 않는다.

### 3.4. 검사·허가

시설 동일성·적용 대상·기준일·예외·유효기간·실제 사용을 연결한다. 신청·접수·합격·부착·사용 여부를 각각 평가한다. 변경 이후 기존 증빙의 범위가 유지되는지 확인한다.

완공검사 확인증 분실이면 재교부·관청 또는 위탁기관 대장 확인 경로를 둔다. 특정 경로를 무조건 온라인으로 조회할 수 있다고 보장하지 않는다. 기관의 신청·발급·재교부 페이지 직접 확인은 일부 미완료다.

### 3.5. 환경·화학물질

사업장·허가번호·주소·시설 범위·조건·효력·변경 이력을 대조한다. 배출량과 처리량·저장량을 혼동하지 않는다. 배출 측정은 시료·위치·시점·방법·기관·기준의 동일성을 확인한다.

MSDS·CAS·소방 위험물·화학물질 규제 자료는 역할이 다르다. 제품 조성·물성·수량·장소를 확인하기 전 규제 지위나 지정수량 합산을 확정하지 않는다.

수량·단위·밀도·산정 기준·시간 범위·장소 범위를 증거에 연결한다. 합산 기준을 넘겼다는 계산은 대상성을 보여줄 수 있지만 미이행 증거 없이 위반을 확정하지 않는다.

## 4. 세 결과 분류와 보류 해제 설계

### 4.1. 확정 결과와 내부 상태

사용자에게 세 분류를 유지할 수 있더라도 내부에는 적용성·기한·이행·충돌·승인·조치·제재를 따로 둔다.

- 명확한 법률 리스크: 대상·시점·기준일 근거·예외·기한·불이행 증거·결론 영향 충돌 없음·승인 조건을 충족한 내부 준수평가 결과.
- 추가 확인·보완 필요: 빠진 사실, 증거 부족, 기준일·관할·해석 미확정, 승인 대기 등을 세부 code로 구분.
- 확인 범위 내 이행 또는 비대상: 이행과 비대상을 구분하고 평가한 의무·기간·시설의 범위를 밝힘.

‘법률 리스크’는 반드시 형사벌 가능성만을 뜻하지 않는다. 법적 의무 불이행과 직접 제재는 별도다. 내부 판단을 관청 처분·법원 판결로 표현하지 않는다.

### 4.2. 보류 해제와 시정 완료

증거 보류의 해제는 다음 어느 방향으로도 이동할 수 있다.

- 기존 이행 사실 확인.
- 비대상·예외 확인.
- 불이행 확인 및 검토·조치로 전환.
- 충돌 정리 후 여전히 다른 사실 부족.

실제 시정 완료는 새로운 교육·선임·검사·신고·시설 개선 등 수행과 효과 확인을 요구하는 별개 과정이다. 자료 제출이 과거 실체를 입증하는 경우와 새로운 의무 이행 자체인 경우를 구분한다.

공통 보류 해제 필드: reason code, 누락 사실, 최소 추가 자료, 대체 확인 경로, 담당 역할, 확인 후 분기, 법정/내부 기한, 승인 필요 여부.

## 6. API 내구성 보강

### 6.1. 실제 32개 등록부가 먼저다

서비스·endpoint·operation·adapter 개수를 구분한다. 실제 목록 없이 임의 32개를 생성하지 않는다. 각 operation에 검색키·단위·schema·성공/오류/0건 구조·상세/첨부·페이지·한도·기준일·시차·저장·재시도·재개·검증 범위를 기록한다.

‘서비스 연결’과 ‘operation 시험 완료’와 ‘전수 수집 완료’와 ‘법적 판정 사용 승인’은 다른 상태다.

### 6.2. 상태를 직교 속성으로 표현한다

- transport: 성공·인증오류·429/한도·timeout·네트워크·provider 오류.
- parse: 정상·schema 오류·형식 오류·미수행.
- cardinality: 데이터·정상 0건·알 수 없음.
- completeness: 완료·부분·미완료·평가 불가.
- freshness: 확인된 범위·오래됨·미확인.

HTTP 200의 provider 오류·로그인 HTML·오류 XML을 잡는다. 실패로 이전 정상 원문을 덮지 않는다. `last_attempt_at`, `last_success_at`, `last_nonempty_success_at`, `source_as_of`를 분리한다.

### 6.3. 재시도·회로차단·재개

[기술 자료 확인] Microsoft Retry는 일시적 오류와 지속적 오류의 구분, 정책별 대기, 지수 지연, idempotency, 중첩 retry 문제, 실패 로그와 실제 장애 조건 시험을 설명한다. Circuit Breaker는 장애가 예상되는 요청을 차단하고 복구를 탐색하는 패턴이다.

[설계 권고] 서비스별 timeout과 작업 전체 budget을 구분하고 20초 초과를 단계별 계측으로 진단한다. A08의 20초 초과는 마지막 보고 상태이며 현재에도 재현된다는 새 확인은 아니다.

429/한도·재시도·회로차단 상태와 재개 예정 시각은 재시작 후에도 보존한다. 한도 reset 시각이 미확인이면 자정이라고 단정하지 않는다. 실제 한도 소진 시험보다 fixture/fault injection을 사용한다.

checkpoint는 조회 조건·정렬/커서·완료 단위·실패 목록·원문·schema 버전을 저장한다. 원문 저장과 완료 표시를 원자적으로 처리하고 동일 처리 재시도 시 중복을 막는다. 원천 목록이 변하는 API에서 안정적인 snapshot 없이 전수 완전성을 보장하지 않는다.

### 6.4. cache와 법적 검증은 다르다

[기술 표준 확인] RFC 9111은 저장 응답의 freshness와 validator를 통한 재검증을 구분한다. ETag·Last-Modified·304를 사용하더라도 대응 저장 원문이 있어야 한다.

[설계 권고] 304를 새 0건으로 저장하지 않는다. cache 재검증은 법령 효력·추출 승인·사업장 판단 승인과 다른 상태다.

## 7. 승인·변경·보안·복원

원문 추출 승인, 규칙 승인, 사업장 판단 승인, 조치 종료 승인, 운영 배포 승인을 분리한다. 검토자 역할은 산업안전·환경·화학·위험물·법률 등 해당 전문성과 권한에 맞춰 지정한다.

법령·고시·별표·관할·시설·조성·수량·사실·추출기·산정 공식 변경의 영향 범위를 따라 재검토한다. 이전 승인 이력은 보존하되 새 버전의 승인을 자동 생성하지 않는다. checksum 동일성은 사실의 진실성·법적 유효성을 입증하지 않는다.

동시 수정·권한 우회·다른 사업장 접근을 시험한다. 명단·건강·인사·영업비밀·인증키를 로그·fixture·외부 AI에 그대로 전송하지 않는다. 외부 AI 처리위탁·국외이전 등의 개인정보 검토는 실제 계약·설정 확인이 필요하며 이번 조사에서 개별 운영 구조의 적법성을 확정하지 않았다.

백업은 실제 별도 환경의 복원 시험까지 구분한다. 원문·규칙·승인·작업 상태가 연결되어 복원되는지 확인한다. 복원된 과거 자료의 현재 최신성은 재확인하고 오래된 backup을 현재 검증 완료로 서비스하지 않는다.

## 8. 검증 지표와 인수시험 추가 권고

[공식 기술 프레임워크 확인] NIST AI RMF 1.0 MEASURE 2.1은 시험 세트·측정·도구를 기록하도록 하고, 2.3은 배포 환경과 유사한 조건에서 성능을 입증하고 기록하도록 한다. 이는 한국 EHS 법정 기준이 아니라 검증 설계 참고다.

이 조사에서는 2026년 TEVV-Athlon 초안 검색 결과도 확인했지만 아직 초안인 자료를 확정 표준으로 쓰지 않는다. 본 권고는 AI RMF 1.0과 공식 Measure 자료를 중심으로 작성했다.

### 8.1. 평가축

정확도 한 숫자 대신 거짓 위반 확정, 거짓 이행 확정, 거짓 비대상 확정, 불이행 탐지·검토 라우팅, 불필요 보류, 보류 해제조건, 버전 인용, 계산·기한, 권한 우회, 0건/오류 혼동, 재개 누락·중복을 분리한다.

분모·클래스 수·scope·기준일·dataset 버전을 공개한다. 분모가 0이면 산정 불가다. 가상 사례 100건에서 오류 0건이어도 실제 사업장 정확도 100%를 보장하지 않는다.

P0 오류 0건은 정의한 검증 세트에서의 초기 배포 조건으로 제안할 수 있지만 법정 수치나 달성된 결과가 아니다. 실제 사업장 검증 이전에는 실운영 성능으로 표현하지 않는다.

### 8.2. 추가 권고 시나리오 24건

아래는 기존 48개 인수항목을 대체하지 않는다. 아직 실행하지 않은 신규 후보 목록이다.

1. API 정상 0건과 provider 오류 HTTP 200을 구별한다.
2. 429 후 재시작해도 제한 상태가 보존된다.
3. 회로 open을 정상 0건으로 저장하지 않는다.
4. 목록 일부 상세 실패가 부분 성공과 실패 목록으로 남는다.
5. 첨부 미지원·첨부 없음·첨부 조회 실패를 구분한다.
6. 항목 저장 직후 강제 중단해도 checkpoint 재개 시 누락·중복이 없다.
7. 수집 중 원천 목록 변경을 감지하거나 완전성 미확인으로 보고한다.
8. 304에 대응 원문이 없으면 빈 정상 데이터로 확정하지 않는다.

10. 공개 인허가 0건을 무허가 확정으로 바꾸지 않는다.
11. 선임은 확인됐으나 신고 미확인은 하위 의무별 상태가 다르다.
12. 재선임 유예 중 대리자 미확인을 별도로 관리한다.
13. 정기점검 실시와 30일 제출을 독립 판정한다.
14. 최초 확인증 발급일과 반복 검사 사건일을 혼용하지 않는다.
15. 검사 신청만으로 만료 후 사용 가능을 자동 확정하지 않는다.
16. 다른 설비 증명서는 부적격 증빙으로 처리하되 미검사 확정은 하지 않는다.
17. 가사용에 확인되지 않은 승인서를 필수서류로 추가하지 않는다.
18. 교육 출석명단만으로 시간·내용·자격·형태를 모두 충족 처리하지 않는다.
19. 특정 참고양식 미사용을 법 위반으로 생성하지 않는다.
20. 직접 처벌 미발견을 의무 이행 또는 자격 정지 처분으로 바꾸지 않는다.
21. 법령·시설·조성 변경 후 과거 승인을 새 판단에 자동 재사용하지 않는다.
22. 가상 사례가 운영 사업장 검증 완료로 승격되지 않는다.
23. 시정 완료 후에도 과거 기한 위반 검토 이력이 남는다.

현재 대화에서 거론된 숫자와 상태는 다음과 같다.

- 254개 테스트가 있다는 보고.
- 32개 API를 연결하거나 관리한다는 보고.
- 기존 상세 명세의 48개 인수 항목.
- A07은 호출 제한 등의 상태 보존이 미완료라고 마지막 보고된 상태.
- A08은 20초 제한을 넘겨 재점검이 필요하다고 마지막 보고된 상태.
- 최신 변경 후 전체 테스트, 실제 화면, 운영 반영이 함께 확인되지는 않았다는 상태.

이것들은 이번 실행에서 검증된 결과가 아니다. 원래 로그, 현재 commit, 실행 명령, 테스트 파일, API 등록부를 실제로 확인하라. 오래된 보고가 현재에도 그대로 유효하다고 단정하지 마라.

다음 항목을 분리하여 현재 상태표를 작성하라.

1. 기획·명세 작성 완료.
2. 코드 작성 완료.
3. 빌드·정적검사 완료.
4. 해당 commit의 단위·통합 테스트 완료.
5. 장애·복구 시험 완료.
6. E2E 완료.
7. 가상 사례 인수시험 완료.
8. 실무자 검토 완료.
9. 실제 사업장 자료 검증 완료.
10. 운영 배포 완료.
11. 실제 serving build 확인 완료.

각 항목에는 대상, 현재 상태, 확인일, commit/build ID, 근거 파일 또는 로그, 남은 일, 담당자를 기록한다. 상태는 완료·부분완료·미완료·미검증·차단·범위제외로 구분하되 기존 앱 상태와 충돌하지 않는 명시적 매핑을 둔다. 범위제외는 승인된 사유가 있어야 한다.

254개 테스트의 일부 성공을 전체 완료로 바꾸지 말고, 변경 전 성공 로그를 변경 후 성공으로 재사용하지 마라. 테스트 개수, 테스트 파일 개수, assertion 개수, scenario 개수, 인수항목 개수를 혼용하지 마라. 48개 항목에 고유 ID를 부여하고 실제 시험 결과와 연결하라. 기존 항목은 숨기거나 덮어쓰지 말고 추가 항목에는 별도 ID와 버전을 부여한다.

저장소·API 등록부·실행 환경을 찾지 못하면 정확히 무엇이 없는지 기록하라. 가능한 설계·fixture·문서 작업은 계속하되 실제 구현·실행 결과를 꾸미지 마라.

### 1. 절대 지켜야 할 판정 원칙

다음 변환을 금지한다.

- 서류 미업로드 → 위반.
- 문서 검색 0건 → 의무 불이행.
- API 0건 → 해당 물질·시설 비대상.
- HTTP 200 → 정상 데이터.
- 시간 초과·호출 제한 → 정상 0건.
- 허가 신청 접수 → 허가 완료.
- 선임 신고 접수 → 자격·전담·업무수행까지 모두 충족.
- 검사 신청 → 검사 합격.
- 다른 설비의 합격증 → 현재 설비 적합.
- 출석명단 존재 → 대상자 전원 교육 충족.
- 교육기록 누락 → 실제 미교육 확정.
- 특정 양식 미사용 → 법 위반. 단 실제 법정 서식 의무는 별도로 확인한다.
- CAS 동일 → 제품·혼합물 동일.
- 지정수량 이상 → 곧바로 위반.
- 예외 문장 발견 → 모든 의무 면제.
- 허가 완료 → 가동개시·검사·선임·교육 등 후속 의무 완료.
- 현시점 시정 완료 → 과거 기한 위반 삭제.
- 과태료·형사벌 미확인 → 법적 의무 없음.
- 기술가이드 권고 미충족 → 법률 위반.
- 공식 사이트 게시일·첨부파일 재등록일 → 문서의 법령 내용이 현행.
- 코드 생성·스크린샷·서버 기동 → 운영 배포 완료.

불확실하다는 이유로 모든 항목을 끝없이 보류하는 것도 금지한다. 판단에 필요한 최소 사실과 보류 해제 조건을 지정하고, 빠진 사실이 해당 결론에 영향을 주지 않는다는 근거가 있는 경우에는 영향 없는 부분을 독립적으로 판정한다. 다만 법적 예외·범위가 미확인인데 임의로 영향 없다고 가정하지 마라.

### 2. 기존 앱 구조를 먼저 읽고 최소 변경으로 구현하라

기존 저장소의 도메인 모델, DB schema, migration, API adapter, rule engine, 테스트 설정, 접근권한, 저장·백업 구조를 확인한다. 기존 기능을 재작성하거나 새로운 프레임워크를 임의 도입하지 마라.

기존 이름이 아래 개념과 다르면 기존 이름을 유지하고 개념 매핑을 문서화한다. 이미 존재하는 기능은 재사용하되 실제 역할과 검증 범위를 확인한다. 구조 변경이 필요하면 이유, 변경 파일, 데이터 이행 방법, rollback 방법을 먼저 정리한다.

새 상태를 저장할 때 기존 boolean과 충돌하여 null이 false로 바뀌지 않도록 migration과 구버전 호환을 시험한다. 기존 승인 기록을 새로운 기준에서 승인한 것으로 소급하지 마라.

### 3. 사실·증빙·판정 상태를 서로 다른 축으로 관리하라

하나의 ‘확인됨’ 체크박스로 모든 상태를 합치지 마라.

#### 3-1. 사실 레코드

최소한 다음을 표현할 수 있어야 한다.

- fact ID, 사업장 ID, 장소 ID, 시설 ID, 제품 ID 또는 익명화된 사람 ID.
- 사실 종류와 값, 원 단위, 정규화 단위, 산정 기준.
- 사건 발생일·적용 시작일·종료일과 자료 수집일.
- 출처 문서·페이지·문장·표 셀 또는 시스템 기록.
- 사용자 입력 여부, 사용자 확인 여부, 자료 검토 여부, 현장 확인 여부.
- 측정값인지 계산값인지, 계산이면 입력값과 공식 버전.
- 추출 방식, OCR/AI 버전, 추출 신뢰 관련 정보.
- 충돌 후보, 검토 결과, 검토자, 승인 범위.
- 가상 데이터 여부와 사용 가능 환경.

입력자 확인을 객관적 자료 확인으로 승격시키지 마라. 자료 확인은 확인한 문서·범위·시점을 밝히고, 문서의 사실과 현장 실체를 구분한다. 승인 이벤트는 권한 있는 실제 검토자의 행위로만 생성한다.

#### 3-2. 증거 레코드

- 원본, checksum, 저장 위치, 수집 경로, 생성 주체.
- 문서 작성일·발급일·접수일·효력 시작일·종료일을 구분.
- 증거가 주장하는 대상, 기간, 사실요소.
- 완전성, 판독 가능성, 동일성 확인 상태, 진본성 관련 확인 범위.
- 문서가 보여주는 것과 보여주지 않는 것.
- 법정 보존 의무와 내부 보존 정책의 구분.
- 개인정보·영업비밀 분류, 접근권한, 외부 전송 허용 여부.

checksum 일치는 파일 무결성 확인이지 내용의 진실성 확인이 아니다. OCR confidence는 법적 판단 신뢰도로 사용하지 않는다.

#### 3-3. 판단 축

최소한 다음을 따로 저장한다.

- 적용성: 대상 / 비대상 / 미확인 / 충돌.
- 의무 발생·기한: 발생 전 / 진행 중 / 도래 / 경과 / 미확인.
- 이행: 이행 확인 / 불이행 확인 / 미확인 / 충돌.
- 법적 규칙 승인: 미검토 / 검토 중 / 승인 / 반려 / 재검토 필요.
- 사업장 판단 승인: 미검토 / 승인 / 반려 / 재검토 필요.
- 조치: 미착수 / 진행 / 완료 주장 / 재확인 완료 / 재발·재개방.
- 제재: 직접 제재 확인 / 재량 처분 가능 / 미확인 / 확인 범위에서 미발견.

‘미발견’은 ‘제재 없음’의 완전한 법률 의견으로 쓰지 않는다.

### 4. 날짜·기한·법령 버전을 별도 엔진으로 구현하라

법령명·조문번호만 저장하지 말고 실제 버전 식별자와 본문을 연결한다.

- 법령 ID, MST/버전 ID, 공포번호, 공포일.
- 조문별 시행일, 기준일, 개정 전·후 조문.
- 부칙, 적용례, 경과조치, 위임 고시, 별표·별지.
- 기준일에 시행 중인 조문과 시행 예정 조문을 분리.
- 출처 수집일, 내용 hash, 승인된 추출·규칙 버전.

법령 검색 머리의 시행일이 개별 조문 시행일과 다를 수 있다. 이번 조사에서 산업안전보건법 MST 283449의 웹 기본정보는 2026-06-01, MCP 기준일 머리정보는 일부 조항의 2026-08-01을 표시했다. 같은 법률의 단계 시행이므로 머리정보 차이만으로 오류라고 단정하지 말고 실제 조문·부칙·대상 규모로 확인한다. 일부 과태료 개정분의 2027년·2028년 단계 시행을 2026년 판단에 앞당겨 적용하지 않는다. 미대조한 과태료 금액은 확정 출력에서 제외한다.

행위일·시설 설치일·이전일·변경일·사용 개시일·선임일·해임일·점검일·검사일·확인증 발급일·신고 제출일·접수일·처리일·처분일은 독립된 날짜다.

조문이 ‘확인증을 발급받은 날’이라고 하면 검사일을 대입하지 말고, ‘검사를 받은 날’이라고 하면 발급일을 자동 대입하지 마라. 법령 문구와 기산점 event type을 같이 저장한다. 날짜 선택이 해석에 달려 있으면 해석 미확정 상태와 보수적 내부 알림을 분리하고, 내부 알림 기준을 법정 기한으로 표시하지 않는다.

‘14일’, ‘30일’, ‘6개월’, ‘매반기’, ‘연 1회’, ‘2년마다’는 다른 유형이다. 법정 기간 계산의 적용 근거, 초일·말일, 휴일 처리, 월말·윤년, 적용례를 확인하라. 월·년 기한을 30일·365일로 단순 환산하지 마라. 모든 기간에 영업일 계산을 일괄 적용하지 마라.

관련 날짜가 빠지면 ‘기한 확인 필요’로 남긴다. 행위 전 의무와 행위 후 신고 의무를 구분하고, 이미 완료한 행위의 기한 위반과 현재 진행 중인 시정 상태를 함께 보존한다.

### 5. 의무를 하위 단위로 쪼개고 증거정책을 붙여라

각 obligation/rule에 다음을 연결한다.

- 법적 의무자와 법적 근거, 기준일 버전.
- 대상 판정에 필요한 사실.
- 의무 내용, 의무 발생 사건, 기한 계산.
- 예외·면제·감경·간주·대체·연장·유예의 각각 다른 요건.
- 필요한 사실요소와 허용 가능한 증거 경로.
- 단독으로 불충분한 자료.
- 이행 확인 조건.
- 불이행 확인 조건.
- 비대상 확인 조건.
- 보류 사유 code와 보류 해제 조건.
- 검토자 역할과 승인 권한.
- 직접 제재·행정조치 등의 별도 연결과 확인 범위.
- 변경 시 재검토 트리거.

원본 증빙만을 유일한 방법으로 고정하지 마라. 법정 서식·원본 제출 의무가 있는 경우는 그 근거를 적용하고, 그렇지 않으면 기관 대장·재교부·전자기록·현장 확인 등 동등한 사실 확인 경로를 정책에 명시한다.

기관 대장 조회는 ‘누가, 어떤 시설/사람/기간/상태를, 어떤 시스템과 검색키로 확인했는지’를 남긴다. 공개 API나 공개 인허가 목록에 나타나지 않는 것만으로 관청이 발급·접수하지 않았다고 확정하지 마라.

모든 의무에 세 기관 부존재 확인이나 현장 방문을 필수로 붙이지 마라. 그것은 보편적인 법정 요건이 아니다. 의무의 성격·증거의 충분성·자료 범위에 따른 내부 정책과 법률 요건을 분리한다.

### 6. 우선 구축할 실무 증거정책

#### 6-1. 위험성평가

대상 공정, 작업, 유해·위험요인, 근로자 참여, 평가 결과, 위험 감소조치, 실행·효과 확인, 변경 후 검토를 연결한다. 문서가 존재하는 것과 실제 절차를 수행한 것은 다르다.

양식·서명·사진을 일률적인 법정 필수서류로 추가하지 않는다. 법령·고시상 요구와 회사의 증거 확보 권고를 구분한다. 평가 방법별 필수 사실을 정의하고 미확인 부분만 보완 요청한다.

평가 미실시, 근로자 참여 미확인, 조치 미이행, 기록보존 문제를 독립적으로 구분한다. 기존 명세의 산업안전보건법 제36조 및 시행규칙 제37조~제37조의4와 기준일 고시·부칙을 실제 원문으로 확인한 뒤 활성화한다.

#### 6-2. 산업안전보건 교육

정기·채용 시·작업내용 변경 시·특별·관리감독자 교육을 구분한다. 근로자 구분, 고용 기간, 작업, 교육 대상 사건, 대상 기간이 먼저 확인되어야 한다.

명단·시간·내용·강사 자격·교육 형태·면제 또는 감경 근거를 평가한다. 출석명단 하나로 전체 이행을 확정하지 않는다. 전자교육 로그·현장교육 일지 등은 법령상 허용 범위에서 사실요소를 확인하는 자료로 인정한다.

특별교육과 채용·변경 교육의 간주 관계는 방향성을 갖는 규칙으로 구현한다. 특별교육 이행으로 채용·변경 교육을 한 것으로 보는 규정이 있다고 해서 반대 방향도 인정하지 마라.

과거 분기 기준이나 구법 조문·별표 번호를 현재 규칙으로 복사하지 마라. 교육시간·내용·강사·원격교육 방식·인정 비율은 기준일 법령과 고시를 다시 확인하여 규칙에 넣는다.

교육기록이 없는 것과 교육을 하지 않은 사실을 구분한다. 자료의 누락·타 시스템 보관 가능성을 확인한다. 법정 근로자 교육일지 양식이나 일반 교육기록의 법정 보존기간을 확인 없이 만들어 넣지 마라.

#### 6-3. 산업안전보건 안전관리자

선임 인원, 자격, 전담, 공동선임, 도급·위탁 특례, 업무수행, 선임·변경 보고, 해임·해지 보고, 증원·교체명령 이행을 분리한다.

인사발령·계약·자격·조직도·업무기록·보고 증빙의 역할을 나누고, 보고 접수증으로 모든 실체 요건을 통과시키지 않는다. 반대로 접수증이 없다는 이유로 미선임을 확정하지 않는다.

시행령 별표3·4, 시행규칙 제11조, 부칙을 대조한다. 새로 추가된 보고 의무를 과거 사건에 소급하지 않는다. 보고가 수리를 요하는 신고인지 확인되지 않으면 접수·수리 요건을 임의로 덧붙이지 않는다.

#### 6-4. 산업안전보건 안전검사

대상기계·세부 규격·법적 의무자·다른 법령 검사에 따른 면제·자율검사 인정·설치·이전·주요 구조변경을 확인한다.

증명서의 설비명·형식번호·설치장소·합격번호·유효기간 등으로 동일 설비인지 확인하고, 필요시 현장 식별정보와 대조한다. 다른 설비의 증명서는 현재 설비의 증거로 부적합하지만, 그것만으로 현재 설비가 미검사라고 확정하지 않는다.

검사 신청, 검사 실시, 합격, 증명서 부착, 미검사 또는 불합격 상태의 실제 사용을 별개 의무·사실로 관리한다. 구조변경 뒤 안전인증이 별도로 생기는지 확인한다.

시행규칙 제124조의 검사 시기·간주 규정과 법 제95조 사용금지 규정을 함께 확인한다. ‘만료일 전후 30일 검사 창’과 ‘사용 가능 기간’을 동일시하지 않는다. 신청했다는 이유만으로 사용 가능을 자동 판정하지 않는다.

사용중지·잠금·표지는 현장 위험 통제와 관련된 증거이지 합격 증거가 아니다. 미검사 의무 문제와 불합격 기계 사용 문제를 분리한다.

#### 6-5. 위험물 설치·변경허가 및 완공검사

법 제6조와 시행규칙 제8조·별표1의2로 변경허가 대상 범위를 확인한다. ‘변경이 있었다’는 사실만으로 변경허가 의무가 생겼다고 판단하지 않는다. 시설별 별표의 전 범위를 확인하지 못한 경우 해당 시설 규칙은 비활성 또는 검토 대기 상태로 둔다.

허가 신청, 허가, 공사 완료, 완공검사 합격, 실제 사용을 분리한다.

법 제9조 및 시행규칙 제21조상 변경공사 중 가사용은 변경허가 신청·화재예방 조치서류·공사와 무관한 사용 범위를 확인한다. 확인한 조문에 없는 ‘가사용 승인서’를 보편적인 법정 필수서류로 만들지 마라. 별지 서식의 처리란과 추가 적용 절차가 있다면 원문을 확인하여 별도로 반영한다.

부분 완공검사는 그 검사 범위에만 효력을 연결한다. 다른 구역의 합격을 전체 시설 합격으로 확장하지 않는다. 확인증 분실은 재교부 또는 관청·위탁기관 대장 확인 경로를 안내한다.

#### 6-6. 위험물 안전관리자

최초 선임, 해임·퇴직 후 재선임, 선임 신고, 부재·공백 시 대리자 지정, 대리 기간, 중복선임과 보조자, 실제 감독·취급 참여를 분리한다.

법 제15조에는 재선임 30일, 선임 신고 14일, 대리 대행기간 30일 상한이 있다. 이를 하나의 ‘30일 유예’로 합치지 않는다. 최초 선임을 해임 후 재선임의 유예로 처리하지 않는다. 재선임 기한 안이라고 대리자 의무도 사라지는 것은 아니다.

자격 자료의 행정정보 공동이용 확인 경로를 포함하여 자격증 사본 미업로드와 미자격을 구분한다. 법령상 신고 상대와 지역 위임·위탁을 실제로 확인한다.

#### 6-7. 위험물 정기점검·결과 제출·정기검사·교육

법 제18조의 점검 실시, 결과 기록·보존, 점검일부터 30일 내 제출, 특정 대상의 정기검사를 다른 객체로 관리한다. 점검은 했지만 제출을 하지 않은 경우를 미점검으로 바꾸지 않는다.

시설 종류·수량·탱크 특성·대상 기간·기준일 규정을 확인한다. 점검 주기와 정기검사 주기를 혼용하지 않는다. 일반 정기점검 기록 3년과 구조안전점검 기록 25년 또는 적용 조건에 따른 30년을 일괄적인 3년·5년 보존으로 덮지 않는다.

시행규칙 제70조상 최초 정밀정기검사의 ‘설치허가에 따른 완공검사합격확인증 발급받은 날부터 12년’, 반복 ‘최근 정밀정기검사를 받은 날부터 11년’, 중간검사의 최초·반복 기산점을 구분한다. 검사일과 발급일을 모두 저장하고 특별 지정 시기·구조안전점검과의 연계를 확인한다. 반복 검사 기산점의 구체적 사건일 해석이 필요한 경우 원문·고시·기관 확인 없이는 법정 위반을 확정하지 않는다.

법 제28조 교육 의무 이행과 직접 처벌·행위제한 가능성을 분리한다. 직접 벌금 조항을 확인하지 못했다고 교육 의무가 없다고 판정하지 않는다. 제28조제4항은 행위제한을 ‘할 수 있다’는 규정이므로 교육 미이수만으로 자격 정지·처분 발령을 자동 생성하지 않는다.

#### 6-8. 대기·수질·폐기물·화학물질

시설·공정·물질·용량·처리량·배출량·폐기물 종류·발생량·보관·위탁 등 실제 사실을 먼저 연결한다. 허가·신고, 변경, 가동개시, 측정, 운영기록, 관리인 선임 등 후속 의무를 각각 평가한다.

허가증의 사업자·주소·시설 범위·조건·변경내역·효력을 현재 시설과 대조한다. 공개 인허가 목록은 보조자료이지 해당 사업장의 모든 허가와 최신 변경을 완전하게 보증하는 대장은 아니다.

측정 결과는 채취 위치·시간·조건·시료 동일성·방법·측정기관·적용 배출기준과 연결한다. 하나의 시험성적서로 모든 기간의 준수를 확정하지 않는다. 초과 수치가 있어도 단위·시험 조건·적용 기준을 확인한다.

실무 보강에 사용한 환경 통합지도·점검규정은 기관의 점검·확인·사후관리 절차를 참고하는 자료다. 해당 훈령의 점검기관 의무를 모든 민간 사업장의 법적 의무로 복사하지 마라.

미확인한 세부 별표·고시·숫자·예외는 별도 목록으로 남기고, 관련 규칙을 승인 없이 활성화하지 않는다.

### 7. 화학물질·제품·시설 동일성과 산정을 강화하라

물질은 명칭·CAS로 후보를 찾되 제조사·제품 코드·grade·MSDS 버전·조성·농도·물성·COA 등 실제 제품 특성을 연결한다. 성분 CAS 목록이 같아도 혼합비·물성이 다를 수 있다. 영업비밀 성분은 ‘없음’이 아니라 공개 범위 미확인으로 둔다.

소방청 위험물 자료, KOSHA MSDS 자료, 화학물질 관련 공공 API를 같은 분류표로 합치지 않는다. 각 API가 제공하는 필드·법적 목적·기준일·누락 가능 범위를 설명한다.

수량에는 단위, 측정·산정 기준, 저장/취급량 구분, 일 최대량/연간량/순간 재고 구분, 장소 범위, 적용 시점을 저장한다. kg↔L 변환에는 해당 제품·조건의 밀도 근거를 요구한다.

같은 장소의 지정수량 비율 합산을 적용할 때 ‘같은 장소’의 법적·공간 범위를 먼저 확인한다. Σ(실제 수량/지정수량) 결과가 1 이상이면 대상·허가 등 검토를 시작하는 것이지 위반 판정이 아니다. 지정수량 미만도 시·도 조례 등에 따른 별도 의무를 확인한다.

알려진 값과 범위만으로 결론이 확정될 수 있는 산정은 검증된 단조성·범위 논리와 근거를 사용하되, 누락된 물질이나 다른 장소를 임의로 0으로 놓지 않는다. 분류나 장소 범위가 불명확하면 관련 결론을 보류한다.

### 8. 관할·위임·출처 충돌을 별도 검토하라

중앙 법령에 적힌 권한자, 위임받은 지방기관, 위탁받은 검사·교육기관, 실제 접수기관을 구분한다. 기관명이 비슷하다고 동일 기관으로 처리하지 않는다. 한국소방산업기술원과 한국소방안전원은 역할이 다르다.

화성시 사무위임 조례의 기존 조사에서는 제2412호 머리정보와 제2509호 전부개정 공포 원문·부칙의 충돌을 확인했다. 제2509호는 2025-12-31 전부개정, 2026-02-01 시행이라는 공포 원문을 보존했다. 기존 원문근거 폴더와 통합 명세를 읽고 범위·확인 시점을 확인하라. 이는 현시점 API 메타데이터 문제가 여전히 지속된다는 새로운 검증 결과가 아니다.

새로 조회하여 충돌이 남아 있는지 확인하고, 조례 별표의 실제 EHS 업무별 수임기관을 확인한다. 공포번호 충돌이 모든 의무의 실체 요건을 뒤집는지, 접수·처분 권한에만 영향을 주는지 분리한다.

공식 출처가 충돌하면 원문과 머리정보를 모두 보존하고 충돌 종류·영향 의무·기준일·해소 방법을 기록한다. 관련 판단만 확정 차단하고 무관한 판단을 무조건 막지 않는다. 추정으로 메타데이터를 고쳐 쓰지 않는다.

### 9. 세 결과 분류의 내부 상태와 승인 조건을 명확히 하라

기존 앱의 세 분류가 있다면 이름을 확인하고 아래 개념과 매핑한다.

1. 명확한 법률 리스크.
2. 추가 확인·보완 필요.
3. 확인한 범위 내 이행 또는 비대상.

세 분류 아래에 내부 상태를 반드시 보존한다. 이행과 비대상을 서로 구분하고, 미확인·충돌·기한 진행·법적 해석 미확정을 구분한다. 사업장 전체에 ‘법적으로 완벽히 적합’이라는 무제한 결론을 만들지 않는다.

#### 명확한 법률 리스크의 확정 게이트

- 의무자·사업장·시설·행위 동일성 확인.
- 대상 요건 확인.
- 기준일 조문·별표·고시·부칙 확인.
- 적용 예외·유예·대체·간주 조건 확인.
- 의무 발생과 기한 도래·경과 또는 즉시 의무 위반 확인.
- 불이행 또는 금지행위의 충분한 증거 확인.
- 결론에 영향을 주는 출처·사실 충돌 없음.
- 승인된 규칙과 증거정책 사용.
- 해당 범위에 대한 권한 있는 검토자 승인.

게이트가 충족되지 않으면 정확한 누락 요건을 표시한다. 직접 제재 확인은 의무 불이행 판단과 별도다. 승인 대기인 기계 산출물은 ‘위반 후보/검토 대기’이며 확정 결과와 혼동하지 않는다.

내부 확정 판정은 회사의 준수평가 결과이며 행정기관의 처분·법원의 판결이 아니다. 승인했다고 법률 해석의 객관적 진실이 자동 보장되는 것도 아니다. 범위와 근거를 항상 보여준다.

### 10. 보류 해제와 시정 완료를 다른 절차로 구현하라

모든 보류 항목에는 다음이 있어야 한다.

- reason code.
- 빠진 사실 또는 충돌 요소.
- 요청할 최소 자료와 대체 확인 경로.
- 담당 역할.
- 확인 후 어떤 분기로 이동하는지.
- 검토 기한과 기한의 성격: 법정 / 내부 업무관리.

‘추가 자료 필요’만 출력하지 않는다. 예를 들어 ‘A탱크의 설치허가에 따른 완공검사합격확인증 발급일 또는 해당 대장 확인으로 최초 검사 기한 계산을 재개할 수 있음’처럼 구체화한다.

다음 두 흐름을 구분한다.

- 지식·증거 보류 해제: 이미 이행했던 사실이 확인되거나 비대상이 확인되거나 불이행이 확인되어 판정이 가능해짐.
- 실제 시정 완료: 미이행 의무의 후속 이행·위험 통제·검사·보고 등을 새로 수행하고 결과를 확인함.

자료 보완이 곧 시정 이행은 아니며, 조치를 했다는 주장이 곧 효과 확인은 아니다. 조치 책임자, 일정, 예산·인력, 임시 통제, 완료 자료, 효과 확인, 재검토자를 연결한다. ‘완료 주장’과 ‘재확인 완료’를 분리한다.

가능한 경우 조치 수행자와 종료 확인자를 분리한다. 다만 인력 사정에 따른 대체 승인 정책은 내부 통제 기준으로 명시하고 법정 독립심사 의무로 포장하지 않는다.

기한을 넘긴 뒤 제출·교육·검사한 경우 과거 기한 문제와 현시점 이행 상태를 함께 남긴다. 기록을 소급 수정하지 않는다.

### 11. 승인과 변경 영향 추적을 구현하라

승인 단계를 최소 세 가지로 분리한다.

1. 원문 추출 승인: 조문·표·주석·OCR 내용이 원문과 일치하는 범위.
2. 규칙 승인: 대상·산정·기한·예외·출처 연결의 타당성.
3. 사업장 판단 승인: 구체적 사실·증거에 해당 규칙을 적용한 결과.

최종 조치 종료 승인과 운영 배포 승인도 별도다.

승인에는 승인자·역할·시각·대상 hash/버전·범위·조건·의견을 기록한다. 작성자가 자기 승인했다는 시스템 가짜 이벤트를 만들지 않는다. EHS 분야별 유자격자·책임자·법률 검토자를 업무 성격에 맞게 지정하고 노무사 하나로 모든 환경·화학·위험물 심사를 대체하지 않는다.

사실, 물질 조성, 시설 범위, 수량, 법령, 별표, 고시, 관할, 추출기, 산정 공식이 바뀌면 의존 관계에 따라 영향 판단을 찾아 재검토 필요로 표시한다. 단순 수집 시각 변경과 법적 내용 변경을 구분한다.

원문 내용 hash가 같아도 OCR parser 또는 규칙 변환이 달라졌다면 해당 추출·규칙 검토가 필요할 수 있다. 이전 승인은 이력으로 보존하지만 새 버전을 자동 승인하지 않는다.

승인 후 평가를 임의 수정할 수 없게 하고 정정·재평가 이벤트로 연결한다. 동시 수정에는 버전 충돌 검사를 사용하고 오래된 화면·요청으로 새 판정을 덮지 못하게 한다.

### 12. 32개 API 등록부와 검증 지표를 작성하라

실제 목록을 확보하기 전에는 임의로 32개의 서비스명을 채우지 마라. data.go.kr 포털 페이지, 개별 서비스, endpoint, 작업(operation), adapter의 개수는 다를 수 있으므로 모두 분리한다.

각 API/operation에 최소 다음을 기록한다.

- 기존 Axx ID, 서비스명, 제공기관, 공식 안내 URL.
- endpoint와 operation, 프로토콜, 인증 방식.
- 인증키 참조 위치. 실제 비밀키는 등록부·로그에 쓰지 않는다.
- 요청 필드·단위·허용값·검색키·목록/상세/첨부 경로.
- 페이지 방식·총건수 의미·정렬·변경 여부.
- 응답 schema, 성공 code, 오류 code, 정상 0건 구조.
- 호출 제한, 한도 초기화 주기·시간대, 공식 근거 또는 미확인 상태.
- 출처 데이터 기준일·갱신 주기·시차·커버리지 한계.
- timeout/retry/circuit-breaker 정책과 concurrency.
- 저장 모델, 변경 감지, checkpoint, 재개 방식.
- 지원하지 않는 기능과 대체 경로.
- 법적 판정에 사용 가능한 필드와 사용하면 안 되는 추론.
- 최근 실제 성공·0건·오류의 별도 시각 및 redacted raw fixture.

검증 결과는 성공·실패·미검증·해당없음으로 관리한다. 해당없음은 서비스 구조상 지원하지 않는다는 근거가 있어야 한다. 한 건 성공했다고 상세·첨부·전수 수집까지 검증 완료로 표시하지 마라.

다음 지표를 가능한 operation별로 측정한다.

- 정상 데이터 조회 및 payload 구조.
- 정상 0건을 오류와 분리하는 능력.
- provider 오류 payload, 인증 오류, 429/한도 초과, timeout 처리.
- XML/JSON/HTML 혼입과 schema 변경 감지.
- 목록→상세→첨부 연결의 성공·누락·지원 없음 구분.
- 페이지 완전성·중복·누락 검출.
- 부분 실패 목록과 재수집 성공 여부.
- 프로세스 중단 후 checkpoint 재개.
- 동일 요청 재처리의 중복 방지.
- 이전 정상 데이터를 실패·0건으로 덮지 않는지.
- p50/p95 지연, 시도 수, 실제 호출 수, 한도 사용량.

실제 한도를 소진하거나 무리한 부하를 주어 장애를 만들지 마라. 오류·중단·schema 시험은 fixture·mock·fault injection으로 수행하고, live 시험과 시뮬레이션 시험을 구분한다.

### 13. 수집 상태를 구조적으로 분리하라

하나의 status 문자열로 모든 것을 표현하기보다 다음 축을 분리하라.

- transport: 성공 / 인증오류 / 호출제한 / timeout / 네트워크실패 / provider 오류.
- parse: 정상 / schema 오류 / 형식 오류 / 미수행.
- cardinality: 데이터 있음 / 정상 0건 / 알 수 없음.
- completeness: 완료 / 부분 / 미완료 / 평가 불가.
- freshness: 확인된 최신성 범위 / 오래됨 / 미확인.

HTTP 200 안의 오류 XML·오류 JSON·로그인 HTML을 잡아낸다. 정상 0건은 provider 성공 의미와 schema가 확인된 뒤에만 지정한다.

정상 데이터, 정상 0건, 실패, 부분 성공, 한도 초과, schema 오류를 상위 요약 상태로 매핑하되 직교 속성을 보존한다.

last_attempt_at, last_success_at, last_nonempty_success_at, source_as_of, raw_snapshot_id를 분리한다. 실패 시 이전 성공 자료는 보존하되 오래된 자료라는 상태를 표시한다. 새 검색 조건의 0건으로 다른 조건의 자료를 삭제하지 않는다. 원천 삭제·공개 중단은 식별키·변경정보와 확인 정책이 있어야 tombstone 처리한다.

API 실패가 판단에 필요한 핵심 근거 수집을 막으면 관련 판단은 보류한다. 이미 충분한 다른 근거가 있는 무관한 판단까지 일괄 실패시키지 않는다. 오래된 자료로 ‘현재 최신 확인 완료’를 주장하지 않는다.

### 14. 재시도·작업시간·회로차단·재개를 구현하라

provider별 timeout과 전체 작업 time budget을 분리한다. 대기·재시도까지 budget을 소비하므로 UI 요청은 빠르게 작업 ID를 반환하고 긴 수집은 작업 상태로 관리한다.

20초 초과를 무조건 timeout 숫자만 늘려 해결하지 마라. DNS/연결/응답/parse/상세 순회/첨부/저장 중 어느 단계인지 측정한다. 제한 근거를 확인한 뒤 짧은 요청과 background 작업을 적절히 분리한다.

일시적 오류만 재시도한다. 인증키·권한·잘못된 요청·schema 깨짐은 자동 무한 재시도하지 않는다. 429/503 등의 Retry-After가 있는 경우 그 의미를 처리하고 provider 규정에 맞춘다. 지수 backoff+jitter, 최대 횟수, 최대 대기, per-provider concurrency를 설정한다. 라이브러리 재시도와 상위 재시도가 겹쳐 호출이 곱해지지 않게 한다.

회로차단 상태는 closed/open/half-open과 열림 사유·재개 예정·probe 결과를 표현한다. 회로가 열려 있다는 이유로 데이터를 0건으로 기록하지 않는다.

quota 상태와 next_eligible_at은 재시작 후에도 보존한다. 한도 reset 시각을 모르면 임의로 자정이라고 단정하지 않는다. 제한·회로차단 정책이 서비스 전체인지 key/operation별인지 확인한다.

checkpoint에는 job ID, 조회 조건과 버전, 안정적인 정렬/커서, 마지막 완료 단위, 수집 원문 ID, 실패 단위, schema 버전, 시작 시점 조건을 남긴다. 가능하면 원문 저장과 checkpoint 갱신을 원자적으로 처리한다. 진행 중 page number만 저장하고 항목 저장 전에 다음 페이지로 넘기지 않는다.

수집 중 원천 데이터가 변하면 페이지 중복·누락 가능성을 평가한다. 안정적 snapshot/cursor를 제공하지 않는 API에 전수 완전성 보장을 만들지 않는다. 기간 중첩 재조회·dedup·총건수 비교 등 대안을 사용하고 남은 불확실성을 표시한다.

idempotency key는 provider·operation·정규화 조회조건·source ID·원천 버전 등 의미에 맞게 구성한다. 동일 원문 재수집은 중복하지 않고, 같은 source ID의 내용 변경은 새 버전으로 남긴다.

조건부 HTTP 조회가 지원되면 ETag/Last-Modified를 활용할 수 있다. 304는 대응하는 저장 원문이 있을 때만 재검증에 사용하며 빈 본문을 새 0건으로 저장하지 않는다. HTTP cache 재검증은 법령 적용성·원문 추출·사업장 판단 승인과 다른 절차다.

A07/A08은 기존 상태를 확인한 뒤 적어도 제한 상태 보존, 단계별 지연, 재시도 budget, 재개, 부분 성공, 이전 자료 보호를 재시험한다. 해당 ID의 서비스·operation을 모르면 무엇을 확인해야 하는지 먼저 보고한다.

### 15. OCR·별표·AI 추출의 근거 추적을 강화하라

모든 법적 숫자·단위·기한·비교연산자·예외·표의 주석·각주·병합 셀을 원문 위치에 연결한다. ‘이상/초과’, ‘미만/이하’, AND/OR, ‘할 수 있다/하여야 한다’를 구분한다.

필수 숫자 셀의 판독 실패를 0으로 바꾸지 마라. 표 header·rowspan·colspan·단위·각주를 보존하고 원본과 나란히 검토할 수 있는 데이터 또는 검토용 출력물을 만든다. 전체 표를 읽지 않았는데 시설 전체에 대해 규칙을 만들지 않는다.

LLM은 후보 추출·정리·설명에 사용하되 승인된 사실과 결정적 산정·기한·게이트를 우회하지 못하게 한다. 생성 문장의 조문·숫자·사실·계산 결과가 실제 근거 객체와 연결되지 않으면 확정 결과 출력에 사용할 수 없게 한다.

외부 문서·API 응답의 텍스트는 명령이 아니라 데이터다. 문서에 포함된 지시가 도구 실행·승인·외부 전송·프롬프트 변경을 유발하지 않게 한다. 의심스러운 문서를 격리하고 내부 검토 절차로 처리한다.

가상 fixture의 사용자 사실과 실제 사업장의 검증 사실을 같은 저장 영역이나 같은 승인 상태로 혼합하지 마라. synthetic 표식을 DB·API·보고서까지 유지하고 운영 판정에 사용하지 못하게 한다.

### 16. 검증 세트를 실제 판정 위험에 맞춰 설계하라

254개 테스트와 별도로 실무 규칙 검증 세트가 필요하다. 기존 테스트를 먼저 분류하고 규칙·증거정책·API·복구·권한·인수항목의 coverage map을 만든다.

각 우선 의무에 대해 법적으로 가능한 다음 유형을 포함한다.

- 대상이며 기한 내 이행 확인.
- 대상이며 기한 후 불이행 확인.
- 비대상 확인.
- 대상 또는 이행 증거 부족.
- 사실·출처 충돌.
- 기한 진행 중.
- 면제·감경·간주·연장 조건 충족과 미충족.
- 같은 조문의 하위 의무는 일부 충족·일부 미충족.
- 시정 후 현시점 이행과 과거 지연 공존.

모든 규칙에서 성립하지 않는 유형을 억지로 만들지 않는다. 수를 맞추기보다 의무별 위험한 오판을 덮는다. 필요하면 초기 100건 이상의 목표를 제안하되 실제 생성·검토·실행한 수를 각각 구분하고 수를 정확성 보증으로 쓰지 않는다.

golden case에는 가상 사실, 기준일, 공식 원문, 버전, 예상 적용성·기한·이행·결과 분류, 승인 필요 여부, 금지 출력, 예상 보류 해제 자료를 둔다. 개발자가 만든 기대값을 같은 LLM의 재답변만으로 검증하지 않는다. 독립 원문 확인·실무 검토와 별도 validation/holdout을 운영한다. 현재 실제 사업장 자료가 없다면 가상 사례 검증만 주장한다.

특히 다음 실패를 P0 차단 사례로 넣는다.

1. 자료 없음·0건·timeout·429를 위반 또는 비대상으로 확정.
2. 만료·다른 설비·다른 장소의 증빙으로 적합 판정.
3. 선임·신고, 점검·제출, 신청·합격 혼동.
4. 예외 관련 법정 요건 누락 또는 조문에 없는 승인서 추가.
5. CAS만으로 혼합물 위험물 판정.
6. 잘못된 기산점·소급 적용·시행 예정 조문 사용.
7. 권한 없는 승인, 변경 후 이전 승인 자동 재사용.
8. API 실패로 이전 정상 원문·사업장 판단 이력 삭제.
9. 다른 사업장 자료 접근·다운로드·재개·삭제.
10. 가상 사례를 실제 사업장 검증 완료로 보고.
11. 시정 조치로 과거 기한 문제 삭제.
12. 회로차단·한도 초과를 정상 0건으로 표시.

기존 48개 인수항목에는 연결 규칙, evidence policy, test ID, 자동/수동 여부, 실제 결과, 장애 fixture, 로그, commit을 연결한다. 새 실무 보강은 별도 인수항목으로 추가한다.

### 17. 수량보다 위험한 오류율을 측정하라

전체 정확도 한 숫자만 내지 마라. 다음은 초기 측정 설계 권고이며 법정 기준이나 달성된 결과가 아니다.

- 거짓 위반 확정률: 정답이 확정 위반이 아닌 사례 중 시스템이 확정 위반으로 낸 비율.
- 거짓 적합·비대상 확정률: 정답이 해당 확정 상태가 아닌 사례 중 시스템이 그 확정 상태로 낸 비율. 적합과 비대상은 별도 집계한다.
- 실제 확정 가능한 불이행의 탐지·검토 라우팅률.
- 판정 가능한 사례의 불필요한 보류율.
- 보류 사유·해제조건 정확성.
- 근거 연결 누락률과 잘못된 버전 인용률.
- 기한·산정 오류율.
- 승인·변경관리 우회 성공 건수.
- API 0건/오류/부분 성공의 혼동 건수.
- 중단·재개 후 누락·중복·이력 손실 건수.

분모, 제외 사례, 클래스별 사례 수, 데이터셋 버전, 기준일, 검토 방식과 실제 오류 사례를 공개한다. 분모 0은 0%가 아니라 산정 불가다. 작은 가상 세트에서 오류 0건이라고 실사업장 100% 정확도나 95% 신뢰도를 주장하지 마라.

초기 release gate는 검증 세트에서 정의한 P0 오류 0건과 모든 필수 시험의 실제 성공을 제안한다. 이는 제한된 시험 세트에서의 조건이며 실제 운영 무오류 보증이 아니다. 보류율·속도 목표는 baseline 측정 뒤 근거 있게 합의한다. 목표를 만족하도록 어려운 사례를 삭제하지 마라.

### 18. 보안·보존·백업·복원을 시험하라

문서·기관자료·교육명단·건강·인사자료·영업비밀·인증키의 분류와 최소권한을 적용한다. 사람 식별은 가능한 내부 ID로 연결하고 일반 로그·fixture·외부 AI 요청에서 개인정보와 비밀키를 제거한다.

외부 AI 제공자에 전송할 정보, 처리위탁·제3자 제공·국외이전 등 법적 성격, 보존·학습 설정은 실제 계약·설정과 개인정보 법령 검토로 결정한다. 모든 경우를 동의 하나로 해결했다고 가정하지 않는다. 이번 범위에 없는 법률 판단은 검토 항목으로 남긴다.

API URL query·Authorization header·원문 debug dump·에러 메시지·보고서에 key가 새지 않는지 시험한다. 인증키를 확인하기 위해 화면·로그에 출력하지 않는다.

업로드 파일의 유형·크기·악성 콘텐츠·파서 자원 사용을 통제하고, 다운로드 경로·외부 URL·다른 사업장 문서 접근을 제한한다. 첨부 경로 조작과 tenant 간 ID 대입을 시험한다.

backup에는 DB·원문·첨부·법령/규칙 버전·승인·작업 상태·키 참조 등 필요한 범위를 정한다. 비밀키의 복구는 권한 있는 별도 경로를 사용한다. 실제 별도 환경에서 복원하여 hash·연결·승인 이력·규칙 의존성을 확인한다.

복원된 과거 승인은 과거 이력으로 보존한다. 복원 시점 이후 변경됐을 수 있는 법령·사업장 사실·기관자료의 최신성은 재확인 필요로 표시한다. 오래된 backup을 현재 검증 완료 상태로 서비스하지 않는다.

RPO/RTO는 목표와 측정치를 구분한다. 실제 복원 시험을 하지 않았으면 ‘백업·복원 검증 완료’라고 보고하지 마라.

원본·개인정보를 무기한 append-only로 보관하는 정책을 만들지 않는다. 법정 보존·정당한 내부 보존·삭제·법적 보존정지 정책을 구분하고 개인정보 삭제와 감사 이력의 충돌을 검토한다. 감사로그는 변경행위·대상 참조·사유 중심으로 설계한다.

### 19. 법적 자료와 설계 권고를 분리하고 남은 검토를 숨기지 마라

근거 태그를 최소 다음으로 나눈다.

- 기준일 법령 원문 확인.
- 공식 행정자료 또는 기관 절차.
- 기술가이드·공식 권고.
- 2차 해설.
- 프로그램 설계 권고.
- 해석·원문 확인 필요.

공식 기관이 쓴 가이드라도 법적 효력이 없거나 입법예고안을 인용할 수 있다. 업로드 날짜가 최근이라는 이유로 그 가이드의 법령 설명을 현행 규칙에 직접 넣지 않는다.

아직 확인하지 못한 안전관리자 선임·자격 별표 전체, 교육내용 별표, 위험물 시설별 변경허가 별표 전체, 검사 고시 세부, 과태료 세부 금액, 지역 위임·위탁, 기관별 신청·재교부 절차는 실제 필요한 범위부터 공식 원문으로 채운다. 확인하지 못한 숫자·제재를 임의 완성하지 않는다.

korean-law-mcp나 검색이 실패하거나 미수록이면 법령·행정규칙·공보 원문으로 재확인한다. ‘미수록’은 ‘존재하지 않음’의 증거가 아니다. MCP가 오류라고 한 내용도 공식 원문 확인 전 자동 정정하지 않는다.

### 20. 권장 구현 순서와 단계별 종료 조건

#### P0-1. 현재 상태와 증거 모델

상태표, 기존 테스트·48개 인수항목 매핑, API 실제 등록부, 사실·증빙·이행 직교 상태, migration, 권한 경로를 먼저 만든다. 누락 입력이 false로 바뀌지 않고 가상 데이터가 운영 판단에 섞이지 않는 시험이 통과해야 종료한다.

#### P0-2. 판정 게이트·증거정책

우선 의무의 적용성·기한·하위 의무·증거정책·보류 해제·승인 게이트를 구현한다. 자료 부족에서 위반/적합을 확정하는 P0 사례가 차단되어야 종료한다.

#### P0-3. API 상태·A07/A08·재개

API 상태 분리, 이전 성공 자료 보호, 제한 상태 저장, 단계별 timeout, retry budget, checkpoint·idempotency를 구현한다. live 확인 가능한 범위와 fault injection 결과를 나눠 보고한다. API 정상·0건·실패·부분·중단·재개 시 데이터 손실이 없어야 종료한다.

#### P1-1. 의무별 확대·날짜·예외·관할

법적 원문이 충분히 확인된 의무부터 활성화한다. 핵심 별표·기산점·예외가 미확인인 규칙은 candidate로 남긴다. 사실·출처 충돌의 영향 범위를 시험한다.

#### P1-2. 승인·변경·조치 종료

추출/규칙/사업장 판단 승인과 재검토 영향 추적, 과거 위반·현재 시정 상태 공존, 조치 효과 재확인을 구현한다. 이전 승인 자동 재사용·권한 우회·동시 수정 덮어쓰기 차단을 시험한다.

#### P1-3. 검증·복원·운영 인수

golden case, 인수항목, 권한·백업·복원·E2E를 실행하고 실제 commit의 전체 시험을 다시 수행한다. 운영 배포는 별도 승인과 환경 권한을 확보한 뒤에만 수행한다. 설계 지시가 운영 배포 승인을 의미하지 않는다.

의존성을 지키면서 병렬 작업은 가능하지만 동일 schema·상태값·규칙 계약의 변경은 합의된 owner를 둔다. 단계 종료 근거가 없으면 다음 단계 진행과 별개로 그 단계를 완료라고 표시하지 않는다.

### 21. 실행·운영 반영 확인

실제 저장소의 명령과 환경을 사용한다. 존재를 확인하지 않은 npm script나 실행 명령을 만들지 않는다.

최종 검증에는 다음을 남긴다.

- commit, 변경 파일, migration 버전.
- 실행 명령, 환경, 시각, 성공·실패·skip 수.
- 테스트와 인수항목 매핑 및 실패 원인.
- 가상/fixture/live/실사업장 시험의 구분.
- build ID, 배포 ID, backend serving ID, frontend build ID(해당 시).
- cache·이전 server가 아닌 실제 새 버전을 확인한 방법.
- rollback 지점과 남은 차단 사유.

코드 마지막 변경 뒤에는 영향 시험과 최종 전체 시험을 해당 commit으로 다시 실행한다. 운영 환경에 접근하지 못하면 로컬 또는 staging 검증까지만 완료라고 한다. 화면에 동작이 보이는 것과 실제 자료·판정·승인 상태가 저장되는 것을 구분한다.

### 22. 반드시 남길 산출물과 최종 보고 형식

최소 다음 문서·기계 판독 결과를 기존 프로젝트의 관리 방식에 맞게 남긴다.

1. 통합 완료·미완료 상태표.
2. 도메인 상태·증거·의무·기한·승인 모델 명세.
3. 우선 의무별 evidence policy와 원문 근거.
4. 세 분류 게이트와 금지 판정 사례.
5. 보류 사유·해제 조건·대체 확인 경로.
6. 32개 API 실제 등록부와 operation별 검증 결과.
7. A07/A08 재점검 및 장애·재개 로그.
8. 254개 기존 테스트와 48개 인수항목의 추적표.
9. 추가 golden case·P0 시험·오류 지표 보고.
10. 승인·변경·조치·백업·복원 시험 결과.
11. 미확인 법령·해석·별표·관할·자료와 다음 조치.
12. 배포 또는 미배포 범위와 현재 serving 버전 확인 결과.

최종 답변은 다음 순서로 작성한다.

- 실제 확인한 현재 상태.
- 이번에 변경한 것.
- 직접 실행하여 확인한 것.
- 아직 미검증 또는 차단된 것.
- 법률 검토가 남은 항목.
- 실제 사업장 자료가 필요한 항목.
- UI/UX를 보류한 범위.
- 다음 단계와 종료 조건.

‘모두 완료’, ‘32개 API 검증 완료’, ‘254개 테스트 통과’, ‘48개 인수항목 충족’, ‘법적으로 적합’, ‘운영 반영 완료’를 해당 증거 없이 쓰지 마라. 현재 가능한 검증을 끝까지 수행하고, 부족한 맥락과 승인만 정확히 남겨라.
