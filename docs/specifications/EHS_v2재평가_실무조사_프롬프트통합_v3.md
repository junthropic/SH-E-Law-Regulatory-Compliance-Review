# EHS v2 재평가·실무 조사·다음 실행 프롬프트 통합 v3

법률 조사 기준일: 2026-10-08.

## 0. 이 문서를 사용하는 방법

CODEX에 이번 문서 **하나만** 전달해도 된다. 본문은 조사·정정·미확인 범위이고 부록은 실제 실행 지시다. 부록을 한 번 실행한다. 이전 v2 프롬프트와 이번 부록을 중복 실행하지 않는다.

별도로 제공되는 `EHS_CODEX_다음실행프롬프트_v3.md`는 부록과 동일한 실행 지시다. 통합본과 별도본이 동시에 제공되면 지시는 한 번만 수행한다.

이번 보강 방향은 UI 기능 확대가 아니다. 기존 화면·동선은 완전히 동결하고 **기존 검토와 v2의 연결, 권한·기간 경계, 영속 수집·재개, 실행 가능한 법적 정책, 실무 인수·보안·복원**을 보강한다.

## 1. 결론: 지금은 실무를 지원하는 격리 검증 단계다

첨부 v2 보고서는 이전 숫자를 단순 반복하지 않고 실행 결과·소스 식별·남은 범위를 구분한 점에서 진전이 있다.

다만 다음 명제는 서로 다르다.

- 282개 기술 시험과6개 E2E가 통과했다.
- 새 v2 판정 모델이 기존 검토의 실제 경로에 연결됐다.
- 43개 법적 의무가 실행·원문·기간·예외까지 검증됐다.
- 실제 사업장에 적용할 수 있다.
- 운영 앱에 반영됐다.

v2는 첫 명제를 격리 환경에서 보고했다. 나머지는 아직 완료되지 않았다.

따라서 지금 실무자는 이 프로그램을 **쟁점·자료 요청·공식 근거·보류 사유를 구조화하는 보조도구**로 사용할 수 있지만, ‘명확한 법률 리스크’나 ‘적합’ 결과를 실제 사업장 결재의 유일한 근거로 사용하면 안 된다. 실제 자료의 외부전송 통제도 모든 경로에서 강제된 것은 아니므로 민감자료 투입은 해당 통제가 먼저 검증돼야 한다.

### 이번에 확인한 것과 하지 않은 것

확인한 것:

- 첨부 `Pasted text.txt` 전체.
- `docs/implementation-v2/` 보고·상태·정책·인수·API 등록부와 관련 코드 일부.
- 동결 스냅샷12개 파일의 hash 대조 결과.
- 기본 v2 등록·HTTP 권한·bootstrap·기간 비교·worker 공백·backup/restore의 정적 구조.
- 공식 법령·공공데이터포털·공식 기술 문서.

하지 않은 것:

- 이번 조사에서의282개 시험·6개 E2E 재실행.
- 현재108개 소스 전체 재해시 또는 HEAD의 새 실행 확인.
- 이번 조사에서 A07/A08 API 실호출.
- 운영 서버 접속·재시작·배포·사업장 판단·코드 수정.

이번 문서는 후속 개발 지시와 조사 산출물이다. 후속 구현·시험이 끝났다는 증거가 아니다.

## 2. v2 기준선과 우선 공백

### 2.1 기준선

첨부 보고의 최종값:

- HEAD `e770bdefb32fbb6a010b435f372f2d13c9fb384f`.
- 미커밋 작업 소스 digest `58adb10c72f45450a365ea5d1aed9ea61ede26ee1941b62f7a149deb59bc14d2`.
- 수정 전254개, 최종282개 시험.
- 격리·합성·모의 provider 기반6개 E2E.
- 32개 서비스·52개 operation.
- 기존 AC48개: 부분검증19, 미검증29.
- 추가 V2-24개: 부분검증14, 미검증10.
- 총72개 중 완전한 법적·실무 인수 승인으로 처리된 항목은 없다.
- 8개 그룹·43개 의무 후보, 실제 법적 승인·운영 활성화0.

이번 문서의 정적 대조는 보고 숫자의 실제 재실행 검증과 구분한다.

### 2.2 코드에서 확인된 연결 문제

1. **v2 기본 비활성은 안전장치다.** `server/app.ts`는 명시적 `complianceGrants`가 있어야 v2를 등록하고 `server/index.ts` 기본 부팅에는 이를 주지 않는다. 연결을 위해 실제 사용자 모두에게 admin 권한을 주면 안 된다.
2. **legacy와 v2 사이에 실제 업무 변환기가 필요하다.** 기존 자연어 입력·사실·문서·검토와 v2의 fact/source/policy/decision/evidence가 대응돼야 한다. 기존 confirmed·verified·approved는 새 입증·승인이 아니다.
3. **기간 경계가 다르다.** legacy 사실 비교는 끝 제외, v2 날짜 범위는 끝 포함이다. 같은 날짜를 그대로 복사하면 변경 이력과 충돌이 혼동된다.
4. **작업 일지가 worker는 아니다.** `CollectionJournal`의 저장·cancel·checkpoint가 있어도 durable job dispatch·process lease·restart·자동재개가 완성된 것은 아니다.
5. **backup은 평문이며 별도 구조다.** v2 backup의 `encrypted:false`는 실제 상태다. 기존 UI backup과 통합되지 않았고 DB rollback 뒤 파일 원본이 남을 수 있다.
6. **외부전송 flag만으로 전송 차단이 구현되지 않는다.** 기존 AI/OCR/업로드 등 실제 호출 경로를 강제해야 한다.

### 2.3 bootstrap·HTTP 승인 검증을 정확히 해석

`server/app.ts:159–175`의 bootstrap은 cookie와 CSRF를 발급한다. 이 코드 자체에는 실제 검토자 신원·역할·사업장 권한 부여가 없다.

`tests/compliance-v2.test.ts:226–243`의 확인된 v2 HTTP 시험은 bootstrap cookie를 얻은 뒤 위조 bearer로 GET을 요청하여403을 기대한다. cookie는 포함됐고 GET은 쓰기 CSRF 요구 대상이 아니다.

따라서 이 시험은 v2 위조 token 차단의 근거이지, bearer-only로 세션을 우회했다는 근거나 전체 승인 E2E의 근거가 아니다. cookie/CSRF/권한의 조합별 통합 시험을 새로 수행해야 한다.

작성자·추출 검토자·규칙 검토자·사업장 판단자·조치 검토자를 실제 서버 principal에 연결하되, 실사용자 provision이 없으면 가상 principal의 격리 시험까지만 완료한다.

## 3. 실무자는 앞으로 어떻게 사용해야 하는가

현재 사용과 v3 연결 후 사용을 혼동하지 않는다. 아래는 **권장 업무 계약**이며 이미 구현됐다는 설명이 아니다.

### 3.1 질문은 사실 확정이 아니라 검토 접수다

예: ‘위험물안전관리자가 퇴직했고 후임을 뽑고 있습니다. 아직30일 전이면 문제없나요?’

프로그램은 다음을 분해해야 한다.

- 제조소등·대상 시설·의무자 확인.
- 퇴직일과 현재 안전관리자 상태.
- 후임 선임 실체·자격·선임일.
- 선임 신고 여부·대상·접수 자료.
- 대리자 지정·실제 대행·대행기간.
- 실제 취급·감독 상태.

‘아직30일 전’은 모든 의무의 적합을 뜻하지 않는다. 재선임 기한과 그동안의 대리자·감독 의무는 별도다.

### 3.2 자료 업로드는 주장과 증거의 연결이다

원본 checksum은 무결성을 확인하지만 내용의 진실성·실제 이행을 확인하지 않는다.

선임서, 신고 접수 자료, 점검 기록, 허가 자료의 대상·기간·발급자·수량 개념을 각각 확인한다. 특정 서류 한 종류를 보편적 필수 증거로 강제하지 않고 검토된 기관 기록·전자기록·현장 확인 등 대체 경로를 둔다.

서류가 없으면 기본값은 보류다. 법적 대상·기한·불이행 사실이 입증됐을 때만 위험 후보를 만들고 독립 판단 승인 후 기존 확정 분류에 투영한다.

### 3.3 한 질문을 하위 의무별로 종결한다

예: 후임 선임은 확인됐지만 신고는 늦었거나 미확인일 수 있다.

- 선임 실체: 확인 또는 보류.
- 자격: 확인 또는 보류.
- 신고: 기간·접수·효력 별도.
- 대리: 지정·대행기간 별도.
- 과거 미이행: 현재 선임과 공존 가능.

자료를 보완해서 보류를 해제하는 것과 새 시정조치를 실행해서 현재 상태를 바꾸는 것은 다르다. 과거 판단을 지우지 않는다.

### 3.4 자료 요청은 최소 단위로 구체화한다

‘추가 자료 필요’만 출력하지 않는다.

- 무엇이 미확인인지.
- 어떤 대상·기간의 자료인지.
- 대체 확인이 가능한지.
- 누가 확인해야 하는지.
- 자료가 들어오면 어떤 의무가 다시 평가되는지.

정확히 모르는 날짜를 오늘로 채우거나 기본 자격을 있다고 가정하지 않는다.

### 3.5 현재 화면은 그대로 둔다

기존 질문·자료·검토·문서·승인 흐름을 유지한다. 새 internal outcome·hold·trace·freshness는 백엔드에 보존하고 기존 지원 분류와 데이터 필드로 안전하게 전달한다.

완료된 job을 현재 UI가 자동 표시하지 못한다면 관리 API/CLI와 기존 재조회 경로의 검증 범위를 나누고 미연결을 기록한다. 이를 해결하기 위해 새 버튼·설정·자동 polling을 프론트에 추가하지 않는다.

## 4. 법률 조사 보강: 기간을 숫자만으로 계산하면 안 된다

[정부 원문·MCP 확인] 행정기본법 제6조①은 특별규정이 없으면 민법 준용을 정하고,②는 권익 제한·의무 지속기간에 초일 산입·말일 휴일 만료 기준과 국민에게 불리한 경우의 단서를 둔다.

[정부 원문·MCP 확인] 민법 제155·157·159·160·161조는 다른 정함, 초일·오전 영시 예외, 말일 종료, 달력 계산, 해당일이 없는 달, 토요일·공휴일을 구분한다.

### 개발 반영

- 신고·제출 기한과 의무 지속기간을 동일 profile로 취급하지 않는다.
- 조문에 특별 기준이 있으면 우선한다.
- 해임일·선임일·점검일·검사일·확인증 발급일은 서로 다른 사건이다.
- 내부 경보 날짜와 법정 기한을 분리한다.
- 실제 시각·timezone·calendar·holiday 자료와 검토 상태를 version으로 남긴다.
- 매반기·연1회·반복 주기의 기술 지원과 개별 법적 해석 승인을 구분한다.
- ‘연1회’를 calendar-year 또는 rolling12개월로 무조건 활성화하지 않는다.

### 미확정

위험물 개별 의무의 구체적인 초일·휴일 profile, 대리 대행기간의 계산, 일반 보존기간의 정확한 기산 기준을 이번 조사만으로 전부 승인하지 않았다. 법률 본문 숫자를 확인한 것과 실제 법정 종료일을 확정한 것은 다르다.

## 6. A07/A08: 폐기물 수탁업체 실무 사례

### 6.1 공식 서비스의 범위

[공식기관] A07 ‘한국환경공단_폐기물 처리업체 정보 조회 서비스’는 업체의 업종·업체명·전문분야·위치·관할지역/관할청 정보를 조회한다.

[공식기관] A08 ‘한국환경공단_사업장폐기물 행정처분 정보 조회서비스’는 업체명·사업자등록번호·업종·처분기관·처분일·시작/종료일·위반내역 등을 제공한다. 안내문은 관할관청의 관리·규제를 별도로 설명한다.

[정부 원문·MCP 확인] 폐기물관리법 제17조①3호는 위탁·수탁 기준·절차와 일부 배출자의 처리과정 확인을 구분한다. 지정폐기물의 처리 전 확인·수탁확인서 등도 별도 조건이다. 이번에는 제17조를 확인했으며 시행규칙상 세부 대상·절차·예외 전수 확인은 남아 있다.

## 7. 영속 수집과 UI 동결을 함께 만족시키는 방식

[공식 기술자료] async request-reply는 작업 접수와 장시간 처리를 분리하고 상태 위치·중복 요청 처리를 정하는 접근이다. background job은 재시도·멱등성·checkpoint·취소·실패 복구가 필요하다.

[설계 권고] 이번 코드에는 다음 두 경로를 구분한다.

1. 관리 API/CLI: job ID·status·partial·재개·pause/cancel.
2. 기존 UI endpoint: 기존 동기 응답 계약을 유지하는 façade.

기존 client가 job polling을 구현하지 않았는데 endpoint를 갑자기202로 바꾸면 UI 파일을 건드리지 않았더라도 UX가 깨진다. 새 async API와 legacy compatibility를 분리해야 한다.

### 반드시 검증할 실패

- 접수 DB 저장 전 응답.
- 응답 유실 뒤 중복 요청.
- 페이지 저장 직전/직후 강제 종료.
- 두 process가 같은 작업을 동시에 claim.
- lease가 만료된 옛 worker의 늦은 결과.
- quota 차단과 재시작.
- cancel 직후 결과 도착.
- 목록 성공·상세 실패·첨부 실패.
- 304지만 저장 원문이 없음.
- 원천 목록 변동·총건수 변경.
- 검색0건을 삭제로 오인한 tombstone.

정상0건·부분 결과·실패·미지원·기관 원천 삭제를 별도 상태로 유지한다.

A07 지연 중 전체 앱의 전역 busy lock을 잡아 기존 저장·검토를 막지 않게 한다. 긴 외부 네트워크 호출은 DB write transaction 밖에서 수행한다.

## 8. SQLite·backup·외부전송의 공식 기술 보강

### 8.1 SQLite

[공식 기술자료] SQLite는 여러 reader를 허용하지만 동시에 writer는 하나다. WAL은 읽기와 쓰기의 동시성을 개선하지만 다중 writer를 허용하는 장치가 아니다. 특정 read snapshot을 write로 승격하는 경우 BUSY_SNAPSHOT도 고려해야 한다.

[설계 권고] 짧은 transaction, 조건부 claim, lease/fencing, 공유 quota, bounded busy retry를 사용한다. process-local mutex로 다중 process 안전성을 주장하지 않는다. 네트워크 파일시스템 WAL은 별도 제약이 있다.

### 8.2 backup과 원본의 실제 일관성

[공식 기술자료] SQLite online backup API는 일관된 DB backup을 위한 수단이다. 사용 중인 binding이 제공하는 실제 API와 방법을 확인해야 한다.

[정적 코드 확인] v2 backup/restore는 원본 base64·객체·참조·승인 이력을 다루지만 plain JSON이고 UI backup과 별도다. restore는 DB savepoint 안에서 원본 파일을 쓴다. DB rollback이 파일 rollback까지 보장하지 않는다.

[설계 권고] staging/generation·restore ID·복구 일지·publication 상태를 둔다. 실패 후 해당 복원에서 새로 만든 미참조 staging 원본만 정리한다. 다른 평가가 참조하는 기존 파일을 지우지 않는다.

[정적 코드 확인] 일반 request bodyLimit2MiB, legacy restore100MiB override, multipart file20MiB는 다른 제한이다. v2 backup/restore HTTP route는 현재 직접 등록되지 않았다. 이후 통합 시 base64 증가·전체 원본량·object 개수·per-route 제한을 시험해야 한다.

### 8.3 권한·암호화·키 관리

[전문단체 권고] OWASP는 기본 거부·요청별 권한 검사·최소권한·민감자료 보호·검증된 암호 방식·키 lifecycle 분리를 권고한다.

[설계 권고] 암호화 상태는 실제 bytes와 일치해야 한다. 암호키를 backup과 함께 평문으로 저장하지 않는다. checksum은 내용 진위·기밀성·승인을 보장하지 않는다.

이는 한국 EHS 법령의 보편적 암호화 형식이나2인 승인 법정 의무를 선언한 것이 아니다. 실제 개인정보·영업비밀·계약·국외이전 적용은 별도 검토한다.

### 8.4 전송 허용 flag의 강제 적용

[설계 권고] AI/OCR/embedding/파일/도구/HTTP egress를 inventory하고 실제 호출 전에 정책을 강제한다. 자료가 금지됐는데 요약·base64·prompt cache로 우회하지 않게 한다.

격리 provider mock에 금지자료를 넣고 outbound 호출0을 assertion한다. flag 저장시험만으로 보호 완료라고 하지 않는다. 허용 unknown은 전송 차단이며 로컬 평가·허용 공개 조회는 가능한 범위에서 유지한다.

정적 확인 당시 `createApp()`은 명시적인 `complianceGrants`가 있어야 v2 route를 등록했고 기본 entrypoint는 이를 주지 않았다. 이 격리는 의도된 안전장치다. 연결하려고 production 기본 활성화나 dummy admin을 넣지 않는다.

기존 리뷰 객체와 v2 객체의 대응을 정한다.

- 기존 fact→v2 fact.
- 기존 document/raw→v2 evidence/source.
- 기존 rule/citation→승인 상태를 보존한 v2 policy/source.
- 기존 review/case→v2 decision.
- 기존 reviewer 이름·confirmed·verified·approved→출처를 보존한 과거 주장/이력.

기존 승인이나 입력완성 flag를 새 법적 승인으로 승격하지 않는다.

각 변환에는 legacy ID·버전·내용 hash, v2 ID·버전, 변환기 버전, 데이터 손실·미매핑 필드, 재검토 사유를 남긴다. 동일 원본 재변환은 중복 생성하지 않고 실제 내용 변경은 새 버전으로 남긴다.

## 3. 기간 경계를 명시적으로 변환하라

현재 legacy 사실 비교는 `[from,to)` 끝 제외이고, v2의 날짜 범위는 `[from,to]` 끝 포함이다. 같은 문자열을 복사하면 경계일의 변경을 충돌로 오판하거나 하루를 누락할 수 있다.

다음을 별도 type 또는 검증 가능한 계약으로 둔다.

- 날짜만 있는 민사적/업무상 날짜와 시각을 가진 timestamp.
- timezone 또는 지역 날짜 기준.
- closed/half-open.
- 열린 종료일과 미확인 종료일.
- 사실의 유효기간과 이번 평가 범위.

날짜 단위로 의미가 확인된 경우에만 포함 종료일을 다음 날짜의 제외 경계로 변환한다. 시각 단위 자료를 무조건 하루 더하지 않는다. UTC와 Asia/Seoul 변환으로 날짜가 이동하는 경우를 시험한다.

열린 legacy 기간을 v2 필수 종료일에 맞추려고 오늘을 실제 종료일로 만들어 넣지 않는다. 평가 기준일로 범위를 잘랐다면 실제 종료일이 아니라 평가 창을 제한했다는 메타데이터를 둔다. 원래 사실은 보존한다.

반드시 시험한다.

- AC06: 비중첩 500L→800L은 변경 이력.
- AC07: 동일 대상·동일 산정·중첩 기간의 500/800L은 충돌 후보.
- AC08: 허가량800L/재고500L는 다른 사실.
- 동일일 시작·종료, 자정, 월말, 윤년, 열린 종료, 날짜 형식 오류.
- 변환 왕복과 원래 비교 결과의 의미 보존.

## 4. 기존 흐름과 v2를 연결하되 계약을 깨지 마라

v2를 별도 파일로 만든 것과 실무 흐름에서 사용하는 것은 다르다. 최소 한 개의 기존 자연어 검토 흐름이 자료·사실·판정·문서·검토 이력까지 v2 객체를 참조하도록 연결한다.

우선 격리 환경의 shadow 평가로 기존 결과와 v2 결과를 비교한다. 차이마다 이유를 남긴다. ‘기존과 다름’은 그 자체로 오류가 아니며 더 안전한 보류나 하위 의무 분리 때문일 수 있다.

기존 response의 필수 필드·enum·성공/오류 형태를 보존한다. 새 내부 상태를 기존 화면에 지원되지 않는 category로 보내지 않는다. 기존 세 분류는 projection이고 `outcome`, `legalEffect`, `approval`, `holds`, `trace`, `freshness`는 내부 진실로 보존한다.

특히 v2의 `fulfilled`·`out_of_scope`는 현재 기존 `human_review` 분류 아래 있을 수 있다. 이것을 미이행이나 영구 미검증으로 바꾸지 말고, 승인 여부·내부 결론·화면 projection을 각각 설명한다. UI label은 변경하지 않는다.

새 모델 오류·미승인 규칙·자료 부족 시 legacy 경로로 우회하여 확정 위반을 내는 fallback을 금지한다. v2 미확인 상태를 기존 ‘추가 자료 필요/사람의 판단 필요’ 계약으로 안전하게 전달한다.

문서·저장·export에도 정확한 평가 ID·버전·기준일·승인 범위를 연결한다. 이전 화면이나 오래된 요청의 승인이 최신 자료에 덮이지 않게 한다.

## 5. 신원·권한·HTTP 승인 경로를 실제로 시험하라

기존 `/api/bootstrap` 세션은 정적 코드상 세션·CSRF를 제공하지만 실제 검토자 ID·역할·사업장 권한을 입증하는 모델은 아니다. 유효한 cookie를 가진 모든 사용자를 승인자로 간주하지 않는다.

검토자 이름, 요청 body의 역할, legacy approved, fixture token을 실제 권한으로 사용하지 않는다.

서버가 검증하는 principal·tenant·synthetic scope·역할·권한·유효기간·철회 상태를 명시한다. 세션 request-security와 업무 승인 권한을 분리한다. 실사용자 provision 정보가 없으면 실제 권한자 연결은 차단 상태로 남기고 격리용 principal만 사용한다.

현재 v2 HTTP 시험은 확인된 범위에서 위조 bearer를 차단하는 GET 중심이다. 이것을 저장·승인·평가·거절·변경·복원 전체 HTTP 검증으로 확대하지 않는다.

전체 앱 부팅 방식과 같은 구조에서 시험한다.

- grants 없음: v2 기본 비활성.
- 유효 세션만 있고 업무 권한 없음.
- 유효 bearer만 있고 cookie 없음.
- cookie·bearer는 유효하지만 쓰기 CSRF 없음/오류.
- cookie·CSRF·업무 권한 모두 유효.
- 위조·만료·철회된 principal.
- 다른 tenant·synthetic 영역.
- 작성자 자기 승인.
- source→policy→decision→action의 역할 분리.
- 오래된 version/hash 승인.
- 동시 승인·수정 충돌.
- 다른 원문·첨부·문서 ID 접근.

Fastify hook 등록 순서와 encapsulation의 실제 결과를 app.inject 및 격리 HTTP 시험으로 확인한다. 정적 코드만으로 CSRF 우회가 있다거나 없다고 단정하지 않는다.

검토 대기·반려·보완 요청·승인 철회 이벤트가 미구현이면 권한 있는 actor가 수행하는 backend lifecycle을 추가한다. event 이력을 지우지 않는다.

## 6. 실제 실행 가능한 정책을 작은 묶음부터 완성하라

43개 후보에 공통 설명을 붙이는 작업을 반복하지 마라. 기존 식별자에 맞춰 첫 묶음은 다음 여섯 하위 의무를 우선한다.

- `hazmat_manager.replacement`.
- `hazmat_manager.appointment_report`.
- `hazmat_manager.deputy`.
- `hazmat_manager.deputy_period`.
- `hazmat_check.record_retention`.
- `hazmat_check.result_submission`.

이는 우선 구현 범위이며 운영 승인 목록이 아니다. 최초 선임·실제 감독·교육·정기검사 등 나머지 하위 의무를 삭제하거나 충족으로 간주하지 않는다.

각 정책을 실행 predicate와 근거 객체로 작성한다.

- 대상 시설·의무자·기간.
- 필요한 fact key와 최소 증거.
- 법적 scope와 증거 미확인의 구별.
- 기산 사건·기간 profile.
- 면제·유예·간주·연장·잔존 의무.
- 이행·불이행의 독립 근거.
- 보류 code·최소 추가 자료·대체 경로.
- 조문·항·별표·부칙·원문 위치·버전.
- 검토 상태와 승인 권한.

법적 대상은 프로그램의 boolean 허가 여부 하나로 결정하지 않는다. 허가 미확인은 미확인이다. 무허가로 확인되더라도 사업장 전체를 비대상으로 종료하지 말고 관련 저장·취급/허가 쟁점으로 라우팅한다. 허가 면제·협의 간주·이동탱크 등은 해당 법적 근거와 사실로 평가한다.

재선임 30일, 신고 14일, 대리자 지정, 대행 30일 상한을 합치지 않는다. 재선임 기한이 남았다고 대리자 의무를 없애지 않는다.

정기점검의 실시·기록·보존·제출·정기검사를 분리한다. 시행규칙 제68조의 기록 항목 충족만으로 점검 실체·실시자 자격·참관·고시상 방법 전체를 승인하지 않는다.

기록 보존을 전부3년으로 고정하지 않는다. 시행규칙 제68조②는 구조안전점검 기록25년, 제65조①3호 기간이 적용되는 경우30년, 그 밖의 정기점검 기록3년으로 구분한다. 기록 종류·특례 적용·보존 기산 근거를 확인하고 정책을 분기한다. 미확인인 구조안전점검을 일반 기록으로 낮추지 않는다.

2021-10-21부터 적용되는 점검결과 제출 의무는 점검일과 부칙 적용례를 연결한다. 제출일이 이후라는 이유로 개정 전 점검에 소급하지 않는다. 개정 전 제18조②가 정기검사였던 조문 번호 이동도 보존한다.

정기검사 50만L 대상과 점검결과 제출 대상을 혼동하지 않는다. 공칭 탱크 용량·현재 재고·허가상 최대량은 다른 사실이다. 필요한 수량 개념을 원문으로 정하고 근거가 부족하면 보류한다.

정책 상태는 최소 작성 후보→실행 가능한 후보→원문 대조→독립 자동 검증→분야 검토 대기→실제 승인으로 분리한다. AI나 개발자가 사람의 법적 승인 이벤트를 만들어 마지막 단계로 넘기지 않는다. 가상 principal의 시험 승인은 가상 영역에서만 사용한다.

## 7. 법적 기간 profile과 반복 기간을 보강하라

행정기본법 제6조와 민법 제155·157·159·160·161조를 함께 읽는다. 특별 규정, 제출기한, 권익 제한·의무 지속기간의 차이를 구분한다.

모든 EHS 기한에 일괄적으로 초일 포함 또는 제외·휴일 연장 또는 미연장을 적용하지 않는다.

profile에는 다음을 둔다.

- 적용 의무·특별규정.
- 사건 type·사건 날짜.
- 제출기한/지속기간/주기/보존기간의 성격.
- 일·월·년·반기·연간·반복 방식.
- 초일·말일·휴일 처리.
- 시간대·휴일 calendar 버전.
- 법적 근거·해석 검토·승인 상태.
- 계산 결과와 내부 알림의 구별.

법적 해석이 미확정이면 기한 엔진은 `unknown`과 필요한 검토를 반환한다. 편의상 선택한 profile을 법정 기한으로 확정하지 않는다.

매반기·연1회·직전 사건부터 반복되는 기간의 기술 모델과 계산 시험을 구현한다. ‘연1회’의 법적 의미가 미확정인 의무에 calendar-year/rolling12개월 중 하나를 법정값으로 임의 활성화하지 않는다.

기산점은 확인증 발급일·검사일·선임일·퇴직일·점검일을 구분한다. date-only 값에서 금일 중 기한을 이미 경과로 바꾸지 말고 종료 시점·분석 기준시각을 확인한다.

내부 보수적 경보는 구현할 수 있지만 법적 경과·위반과 별도다.

현재 단일 exception=true로 결론이 pending에 남거나 전체 의무가 사라지는 식의 공백이 있는지 확인한다.

효과를 구분한다.

- 비대상.
- 특정 의무 면제.
- 교육시간 등 감경.
- 다른 이행을 통한 간주.

## 9. 영속 작업 ID·worker·자동 재개를 구현하라

기존 CollectionJournal을 실제 durable job lifecycle에 연결한다. 메모리 Promise·Set·timer만으로 작업을 관리하지 않는다.

작업에는 다음을 둔다.

- job ID, tenant·synthetic 영역, 요청자와 권한 범위.
- provider·operation·정규화 query·parser/schema 버전.
- idempotency key 및 동일 key/다른 payload의 충돌 정책.
- queued/running/waiting_retry/waiting_quota/paused/cancelling/cancelled/succeeded/failed 등의 명시적 상태.
- 부분 완전성·정상0건·오류를 별도 축으로 관리.
- 생성·시작·heartbeat·종료 시각.
- lease owner·만료·monotonic fencing token.
- cursor/page·원문 snapshot·상세/첨부 실패 목록.
- next eligible 시각 또는 미확인 표시.
- retry 횟수·총 budget·처리량·종료 사유.

새 관리 API는 검증 후 202와 작업 ID·상태 위치를 반환할 수 있다. 기존 동기 클라이언트 endpoint를 갑자기 202 계약으로 바꾸지 않는다. 아래 호환 façade와 구분한다.

API가 작업을 접수했다고 저장하기 전에 202를 보내지 않는다. DB 저장 실패는 접수 성공이 아니다. 응답 유실 뒤 같은 요청을 반복해도 기존 job을 반환한다.

재시작 후 마지막 committed checkpoint에서 재개한다. 재시도·취소·완료·quota waiting을 상태 전이 검증으로 관리한다. 종료 상태를 오래된 worker가 running으로 되돌리지 못하게 한다.

## 10. SQLite 다중 worker·quota 경쟁을 시험하라

동일 DB에 두 독립 process가 동시에 job을 claim하는 시험을 한다. 두 객체나 메모리 mutex만의 시험으로 다중 process 검증을 대신하지 않는다.

짧은 transaction 또는 조건부 UPDATE로 lease를 claim하고 fencing token을 검증한 worker만 결과·checkpoint·종료를 commit한다. heartbeat와 lease 만료 뒤 이전 worker의 늦은 응답 저장을 차단한다.

HTTP 호출이나 60초 대기를 SQLite write transaction 안에서 하지 않는다. SQLITE_BUSY·BUSY_SNAPSHOT에 bounded retry·명시적 오류 처리를 둔다. WAL이 다중 writer를 허용한다고 가정하지 않는다. 네트워크 파일시스템의 SQLite WAL을 무조건 지원한다고 표시하지 않는다.

provider/key/operation의 실제 제한 범위를 확인해 quota·동시 호출 lease를 공유한다. in-memory 직렬화만으로 여러 process의 한도가 지켜진다고 주장하지 않는다.

429가 오면 공유 차단 상태를 갱신하고 반복 hammering하지 않는다. 수동 해제는 권한·기관 확인 근거·사유·이전/이후 상태·시각을 기록하며 무조건 호출 성공으로 바꾸지 않는다.

pause/cancel 도중 새 결과가 오면 정책에 따라 부분 원문을 보존하고 checkpoint 일관성을 지킨다. 소비자 하나가 취소했다고 공동 사용 중인 다른 tenant 작업을 취소하지 않는다.

exactly-once 외부 호출을 보장한다고 주장하지 않는다. 중복 가능한 실행을 가정하고 저장 효과를 idempotent하게 만든다.

## 11. 기존 동기 흐름을 위한 backend façade

공식 async request-reply 방식은 legacy client가 처리하지 못할 수 있다. 기존 화면을 수정하지 않는 조건에서 다음을 분리한다.

- 새 관리용 async API/CLI는 job ID·status를 사용한다.
- 기존 endpoint는 기존 response schema·enum·오류 계약을 유지한다.
- 짧은 시간 안에 끝난 결과는 기존 형식으로 반환한다.
- 늦거나 제한된 작업은 허용된 기존 오류/추가확인 형태와 partial 결과로 반환하고 backend job은 정책에 맞게 계속하거나 pause한다.
- 완료 후 재조회·기존 캐시 경로가 기존 화면에서 실제 작동하는지는 격리 브라우저 E2E로 확인한다.

기존 계약에 pending이나 partial을 표현할 길이 없다면 상태를 위조하지 말고 관리 API에서만 새 기능이 검증됐다고 기록한다. UI 변경이 필요한 부분은 차단 목록으로 남긴다.

worker가 긴 외부 요청을 기다린다고 전체 앱의 jobs/mutations busy lock을 계속 점유하여 모든 검토·저장·승인을 막지 않게 한다. 필요한 대상·operation·짧은 DB mutation 단위로 충돌을 관리하고 기존 업무의 안전한 동시성을 시험한다.

## 12. A07/A08을 실무 수탁업체 확인 흐름으로 검증하라

등록부 기준 A07은 `waste-companies`, A08은 `waste-sanctions`다.

- A07: 처리업체 업종·업체명·전문분야·위치·관할 자료.
- A08: 업체명·사업자등록번호·업종·처분기관·처분일·시작/종료일·위반내역 자료.

이 둘을 업체명만으로 자동 join하여 ‘위탁 가능/불가능’을 확정하지 않는다. 사업자등록번호·시설 주소·허가번호·대상 시설·상호 변경·지점·처리업종 등을 실제 payload와 증빙 범위에 따라 대조한다.

실무 검토 객체는 다음을 연결한다.

- 배출자의 대상 폐기물·양·위탁 시점.
- 수탁 후보 업체/시설 동일성.
- 허가·신고·재활용 등 법적 지위와 대상 범위.
- 허용 폐기물 종류·처리방법·능력과 계약 범위.
- 행정처분의 대상·기간·효력·후속 변경 확인 범위.
- 자료별 기준일·조회조건·coverage 한계.
- 빠진 자료와 대체 확인 경로.

폐기물관리법 제17조·하위법의 대상·절차를 확인한다. API 목록으로 모든 위탁·수탁 기준 준수를 입증할 수 있다고 가정하지 않는다.

A07 timeout/A08 성공, A07 성공/A08 실패, 정상0건, 같은 이름 다른 사업자, 같은 사업자 다른 시설, 과거 종료 처분, 현재 효력 불명 처분, 허가증 종류 불일치를 가상 fixture로 시험한다.

처분 기록이 있다고 모든 위탁을 무조건 금지하지 않는다. 0건이라고 모든 처분이 없다고 보증하지 않는다. 처리업체 목록에 있다고 실제 허가가 유효하거나 해당 폐기물을 받을 수 있다고 확정하지 않는다.

## 13. 목록→상세→첨부의 전체 수집 그래프를 연결하라

원문 저장·페이지 결과·checkpoint의 commit 일관성을 보장한다. 파일시스템 원문과 DB가 다른 저장소라면 staging·상태·복구 일지를 두고 논리적으로 완료된 원문만 근거로 사용한다.

원천 목록 변동·페이지 중복·총건수 변동은 완전성 경고다. 안정 snapshot 없는 offset API에서 전수 누락0을 보장하지 않는다. 내용 변경은 새 버전으로 보존한다.

304는 대응 저장 원문과 query/validator가 맞을 때만 재검증한다. 원문이 없으면 재조회하거나 명시적 실패로 처리한다. 빈 본문을 새 정상0건으로 저장하지 않는다.

tombstone은 검색0건 하나로 만들지 않는다. 확인된 원천 삭제·공개중단·비공개·일시 오류를 구분하고 과거 법적 판단의 근거를 즉시 지우지 않는다.

## 14. 외부전송 플래그를 실제 egress 통제로 바꿔라

중앙 gateway 또는 각 호출 직전 강제 검사로 scope·민감도·허용 목적·제공자·동의/기타 적법 근거의 검토 상태를 확인한다. 요청 body에서 flag를 바꾸어 우회하지 못하게 한다.

허용 false/unknown은 실제 전송을 막는다. 차단 후에도 로컬 결정적 평가·허용된 공개 법령 조회·증거 보완 흐름은 가능한 범위에서 계속한다. 금지 문서의 요약이나 base64 전송으로 우회하지 않는다.

deny 자료를 넣은 mock provider 시험에서 outbound 호출 수 0을 assertion한다. 로그·에러·queue·dead-letter·prompt cache에도 원문·개인정보·키가 남지 않게 한다.

이는 프로그램 통제 지시다. 실제 외부 AI 계약·위탁·국외이전 적법성은 별도 검토이며 테스트 통과로 법률 승인을 만들지 않는다.

## 15. 백업을 실사용 크기·권한·암호화·복원 실패까지 보강하라

현재 v2 backup은 원본 base64를 포함한 `encrypted:false` JSON이고 기존 UI backup과 연결되지 않았다. 이 상태를 암호화된 안전한 통합 backup으로 표현하지 않는다.

기존 backup/restore와 v2 tables·originals·승인·의존성·invalidations·jobs·quota·schema를 inventory하여 포함/제외 범위를 정한다. API 키·token·암호키는 평문 backup에서 제외하고 별도 권한 있는 복구 경로를 둔다.

DB와 원본 snapshot의 일관성을 확보한다. 활동 중 WAL DB 파일만 단순 복사한 것을 충분한 snapshot이라고 가정하지 않는다. 실제 SQLite binding의 backup API 또는 검증된 snapshot 절차를 사용한다.

파일 암호화가 필요하면 검증된 라이브러리의 인증 암호 방식과 별도 key 관리, key ID·format version·nonce·인증 tag·크기 제한을 사용한다. 키를 backup과 함께 넣지 않는다. checksum만으로 진본성·기밀성을 입증하지 않는다. 평문형 지원은 명시적인 제한·검토 정책으로 두고 무조건 허용 기본값으로 만들지 않는다.

기존 JSON 입력·출력 계약과의 호환성을 먼저 읽고 backend version dispatcher/관리 CLI로 연결한다. UI parser를 변경하지 않는다. 암호화 wrapper가 기존 흐름에서 실제 처리되지 못하면 관리 경로 완료와 화면 경로 미연결을 구분한다.

bodyLimit·multipart 제한·base64 증가·전체 원본량·object 개수를 시험한다. 현재 일반 bodyLimit2MiB, legacy restore100MiB override, 업로드20MiB라는 서로 다른 제한을 하나로 오해하지 않는다. v2 backup/restore는 현재 HTTP route에 직접 등록되어 있지 않으므로 없는 route의 장애를 이미 재현했다고 주장하지 않는다. 새 연결 route는 제한을 명시하고 전체 앱 limit를 무작정 높이지 않는다.

restore 절차는 적어도 다음을 갖춘다.

1. 별도 staging/generation 및 restore ID.
2. tenant·synthetic·schema·hash·인증 검증.
3. 안전한 경로·전체 크기·원본 연결 검사.
4. 참조 검증·DB import.
5. publication/완료 상태.
6. crash 복구·재개 또는 안전 rollback.
7. 미참조 staging 원본의 제한된 정리.

DB rollback이 파일시스템 rollback을 의미하지 않는다. DB 실패 뒤 새로 생성한 staging 파일만 추적하여 정리한다. 다른 판단이 참조하는 기존 원본이나 동일 hash 파일을 삭제하지 않는다.

실제 빈 격리 DB+원본 폴더에서 복원하고 중간 실패를 주입한다. 복원 도중 상태를 현재 검증 완료로 서비스하지 않는다. 과거 승인 이력은 남기되 현재 최신성·권한·적용 범위는 재검토한다.

암호키 유실·오류키·tampering·DB 오류·disk full·프로세스 중단·원본 누락·다른 tenant·기존자료 존재·대용량을 시험한다. 운영 backup 복원을 수행했다고 주장하지 않는다.

### V3-E. 실무 인수·상태표

4개 가상 수직 시나리오와 관련 기존·신규 인수항목이 실제 로그에 연결되고72개 전체 추적이 남는다. 실제 사업장·전문가 법적 승인·운영 배포가 미수행이라는 범위가 보존된다.

전체 작업이 길어도 가능한 구현·검증을 지속하라. 중간 보고에서는 단계별 sourceDigest·성공·실패·차단·다음 조치를 남긴다. 승인·자료가 없다고 실행 가능한 다른 작업까지 멈추지 않는다.

## 20. 산출물과 최종 답변

`docs/implementation-v3/` 등 기존 관리 방식에 맞는 별도 위치를 만들고 v2 산출물을 덮지 않는다.

필수 산출물:

1. v3 현재 상태·변경 전후 source manifest·UI freeze.
2. legacy↔v2 field/period/projection 계약.
3. principal·권한·세션/CSRF 행렬과 실제 HTTP 결과.
4. 선택 정책6개의 실행 계약·원문·정정·승인 상태.
5. deadline profile·반복기간·exception effect 명세와 시험.
6. durable job·lease/fencing·quota·checkpoint·cancel 전이.
7. A07/A08 수탁업체 확인 사례 및 모의/live 범위.
8. 32서비스·52operation 수집 그래프·fixture·검증 공백.
9. egress inventory·deny 시험.
10. backup/restore format·key 참조·크기·일관성·복구 시험.
11. 72개+V3 인수항목 추적과4개 실무 시나리오.
12. 실행 로그·실패 기록·재실행·미측정 지표.
13. 실제 사업장·법적 승인·운영 배포의 차단/범위제외 기록.

최종 보고는 다음을 구분한다.

- 실제 확인한 기준선.
- 새로 구현한 연결.
- 직접 실행해 성공한 항목.
- 실패와 수정 후 재시험.
- 아직 미구현·미검증·해석 미확정.
- 원문·실무자·실제 사업장·운영 승인이 필요한 항목.
- UI/UX 변경0의 실제 확인.
- 운영 배포·재시작0의 범위.
- 다음 단계의 구체적인 종료 조건.

기술 완료와 법적·사업장 승인 완료를 혼합하지 않는다. 전체72개 인수,43개 정책,52개 operation,실제 사업장 적합성,운영 serving을 증거 없이 완료라고 하지 마라.
