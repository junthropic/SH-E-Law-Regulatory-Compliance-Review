# 발견 사항

현장에서 바로 풀지 못한 문제만 적는다. 개인 자료 유출 가능성, 법적 오해를 부르는 표시, 데이터 손실처럼 심각한 것은 이 파일에 적기 전에 사용자에게 먼저 알린다.

각 항목: 어떤 조건에서 무엇이 보이는가 → 놔두면 어떻게 되는가 → 왜 지금 못 푸는가 → 풀 방법.

## 열려 있음

### 같은 PC의 다른 프로그램이 브라우저 쿠키를 얻으면 사용자 대신 API를 부를 수 있다
- 조건: 서버가 켜져 있는 동안, 같은 Windows 사용자의 다른 프로그램이 브라우저의 `she_session` 쿠키와 CSRF 값을 읽을 수 있을 때.
- 놔두면: 그 프로그램이 검토 조회·삭제·백업 같은 요청을 사용자처럼 보낸다. 범위는 같은 PC·같은 사용자 안이다.
- 왜 지금 못 푸는가: 사용자가 이번 버전에서는 고치지 않고 다음 버전에서 고치기로 정했다(알고 감수한 위험).
- 풀 방법: 세션 수명을 짧게 하거나 요청마다 바뀌는 값에 묶는 방식을 다음 버전에서 정한다.

### 실행 토큰이 서버가 켜져 있는 동안 재사용된다
- 조건: 런처가 준 `#launch=` 조각이 시작 정보나 브라우저 기록에 남고, 같은 Windows 사용자의 다른 프로그램이 그 값을 읽을 때.
- 놔두면: 읽은 쪽이 서버가 꺼질 때까지 새 세션을 받을 수 있다.
- 왜 지금 못 푸는가: 위와 같다. 다음 버전에서 고치기로 했다.
- 풀 방법: 첫 `bootstrap` 성공 뒤 토큰을 폐기해 한 번만 쓰이게 한다. 다시 열기(브라우저 새 창)와의 관계를 정해야 한다.

### 연결 목록 개수가 사용자가 말한 숫자와 다르다
- 조건: 코드의 연결 목록을 세면 법제처 인증값 1개 + 서비스 28개(공공데이터포털 26, 도로명주소 2)인데, 사용자는 "법제처와 세부 API 키 32개"라고 말했다. 2026-10-08의 과거 보고서에도 "32개 서비스"로 적혀 있어, 그 뒤 목록이 줄었거나 세는 방식이 달랐을 수 있다.
- 놔두면: 사용자 안내문과 실제 화면의 키 개수가 어긋난다.
- 왜 지금 못 푸는가: 어느 쪽이 맞는지 사용자가 확인하지 못했다. 안내문은 코드 기준으로 쓰고 "목록은 바뀔 수 있음"으로 둔다.
- 풀 방법: 사용자가 최신 목록을 확인해 코드나 안내문을 맞춘다.

### 개발자 키를 지우면 공개 법령 번들을 갱신할 방법이 없다
- 조건: 구현을 마친 뒤 `.env`의 개발자 법제처 키와 GitHub 비밀값 `LAW_OC`를 지웠을 때.
- 놔두면: `public-law-sync`·`source-probe` 워크플로와 `npm run sync`가 법제처를 부르지 못해, 새 앱 버전에 넣을 번들을 만들 수 없다. 번들이 낡으면 모든 사용자가 이전 시행일 기준 근거로 시작한다.
- 왜 지금 못 푸는가: 키를 지우는 것은 사용자가 정했지만 지운 뒤의 갱신 방법은 사용자가 나중에 따로 정하기로 했다.
- 풀 방법: 후보는 (가) 키를 지우지 않고 CI 비밀값으로만 유지, (나) 번들 갱신용 별도 키를 두되 저장소에는 넣지 않음, (다) 사용자 PC에서 각자 수집하고 번들은 없앰. 사용자 결정이 필요하다.

### 후보 계층을 기본 경로에 연결하면 `clear_risk` 막음이 풀린다
- 조건: 후보 계층(컴플라이언스·기존 자료 연결 등)을 기본 경로에 연결할 때. 후보 계층의 평가기는 승인 상태 항목에 `clear_risk`를 낼 수 있다.
- 놔두면: 연결하지 않으면 문제가 없다. 연결하면 법적 판단으로 읽힐 수 있는 결과가 기본 앱에 나온다.
- 왜 지금 못 푸는가: 연결 전에 풀어야 할 조건이 남아 있다. 기본 표의 암호화·소유권 구분, 보호 사례 결과가 평문 표로 복사되는 문제, 내보내기 점검이 옛 검토와 검토자용 묶음을 놓치는 문제, 화면 잠금을 풀어야 하는 수동 보완·독립 검토 화면, 전문가 검토와 활성화.
- 풀 방법: 사용자가 연결 여부를 정한 뒤, 위 조건을 하나씩 해소한다.

### 로컬 Windows에서 127.0.0.1 listen이 간헐적으로 EFAULT로 실패한다
- 조건: 서버를 띄워 통신하는 시험 6개(V6-E01 두 건, V6-E03, V8-H08, V8-H09, V8-X12). 같은 증상으로 V8-N01도 한 번 실패했다. Claude Code 안에서 처음 돌렸을 때는 6건이 모두 실패했고, 전체를 다시 돌렸을 때는 V6-E01 두 건, V6-E03, V8-H09, V8-N01의 5건이 실패했다. 한편 Claude 밖 PowerShell에서 시험 파일 3개만 돌리면 29개 중 27개가 통과하고 2개(V6-E01의 문서 추출 시험 30초, V8-H09 60초)가 시간 초과로 실패한다. 실패할 때는 `listen EFAULT 127.0.0.1` 미처리 오류가 같이 나온다.
- 놔두면: 이 PC에서 `npm run check`가 코드와 무관하게 거짓으로 실패한다. 새 문제로 오해해 멀쩡한 코드를 고칠 수 있다.
- 원인: 아직 확정하지 못했다. 같은 시험이 Claude 밖에서는 대부분 통과했으므로 Claude의 샌드박스만이 원인은 아니다. 이 PC에서 포트를 열 때 간헐적으로 실패하는 현상으로 본다.
- 풀 방법 후보: (가) 같은 시험이 GitHub Actions의 Linux·Windows에서 통과하는지 대조한다(지금은 CI가 꺼져 있어 아래 항목을 먼저 정해야 한다). (나) 이 PC의 보안 프로그램·방화벽이 로컬 포트 열기를 막는지 확인한다. (다) 같은 시험을 여러 번 돌려 실패가 특정 시험·시각에 몰리는지 본다.

### GitHub Actions의 "Build and test" 워크플로가 꺼져 있다
- 조건: 저장소의 `Build and test`와 `MSIX package and install test` 워크플로가 수동으로 비활성화되어 있다(`disabled_manually`). 문서 정비 커밋을 push했는데도 `main`에서 이 워크플로가 돌지 않았다.
- 놔두면: PR과 `main`에 자동 시험(Linux + Windows)이 걸리지 않아, 위 통신 시험 대조와 화면 잠금 시험 확인을 CI로 할 수 없다.
- 왜 지금 못 푸는가: 켜는 것은 저장소 설정 변경이고 Actions 사용 시간(Windows는 두 배)이 든다. 일부러 꺼 두었을 수 있어 사용자 결정이 필요하다.
- 풀 방법: 켜기(`gh workflow enable`)와 켜지 않고 수동 실행(`workflow_dispatch`)만 쓰는 방안 중에서 사용자가 정한다.

### 의존성 보안 점검(`npm audit`)에 14건이 남아 있다
- 조건: `npm audit` 결과가 낮음 1, 보통 6, 높음 7건이다(심각 0). 직접 의존성은 `@fastify/static`, `@modelcontextprotocol/sdk`, `fastify`, `kordoc`, `korean-law-mcp`, `vite`, `zod`이고 나머지는 이들에 딸려 오는 의존성이다. 점검 시점의 건수라서 바뀔 수 있다.
- 놔두면: 알려진 취약점이 있는 버전을 계속 쓴다. 서버는 `127.0.0.1`에서만 받고 설치판은 MCP 등을 꺼 두므로 영향 범위는 이 PC 안으로 한정되지만, 건별로 실제 영향을 따져 본 것은 아니다.
- 왜 지금 못 푸는가: 사용자가 지금은 고치지 말고 기록만 하기로 했다. `@fastify/static` 관련 3건은 점검 도구가 주요 버전이 다른 6.12.0을 제안해 그대로 따를 수 없고, `vite`는 화면 빌드를 건드려 화면 잠금에 영향이 갈 수 있다.
- 풀 방법: 건별로 실제 영향을 분류하고, 자동 수정이 가능한 간접 의존성(`npm audit fix`)부터 정한 뒤 직접 의존성은 시험을 돌려 가며 올린다. `vite`는 화면 빌드 설정과 잠금에 닿는지 먼저 본다.

### 설치 후 스크립트가 실행되지 않은 패키지 2개(`onnxruntime-node`, `protobufjs`)
- 조건: 두 패키지는 설치 후 스크립트를 가진 선택 의존성이고 `kordoc`(문서 추출)이 쓰는 `@huggingface/transformers`를 통해 들어온다. 사용자 확인으로 설치 때 이 스크립트가 실행되지 않았다. 이 PC의 `npm` 설정은 `ignore-scripts`가 꺼져 있다.
- 놔두면: 해당 패키지의 네이티브 기능이 빠진 채 설치되었을 수 있다. 이 앱의 문서 추출이 이 기능에 기대는지는 확인하지 못했다.
- 왜 지금 못 푸는가: 사용자가 지금은 고치지 말고 기록만 하기로 했다. 스크립트가 실행되지 않은 이유도 확정하지 못했다.
- 풀 방법: 스크립트 없이도 문서 추출 시험(`V6-E01`)이 통과하는지 먼저 본다. 필요하면 해당 패키지에만 스크립트를 허용할지 정한다. 새 스크립트를 허용하는 일은 보안 규칙과 맞물리므로 사용자 승인 후에 한다.

## 알고 감수함

### 공개 법령 자료는 평문으로 저장된다
- 공개 자료이고 사용자가 만든 자료가 아니라서 범위를 의도적으로 좁혔다. 새 표를 추가할 때마다 암호화 대상인지 따져야 한다.
