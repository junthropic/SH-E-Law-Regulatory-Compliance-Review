## 2. 도메인 계약과 기존 구조 대응

기존 Fastify·SQLite·Zod를 유지하고 `server/compliance-v2.ts`에 별도 버전 모델을 추가했다. 기존 `confirmed`, `verified`, `approved`를 새 객관 입증·권한 승인으로 자동 변환하지 않는다.

이번 작업의 변경 파일은 v2 도메인·API·기한·정책 후보·수집 일지 모듈, `server/public-api-transport.ts`, `server/public-apis.ts`, `server/intake.ts`, `server/app.ts`, v2 시험 4개 파일, 공개 API/질문 분석 E2E, 감사·격리 검사 스크립트, `vitest.config.ts`, `AGENTS.md`와 관련 명세·보고서다. 현재 Git diff에 보이는 그 밖의 화면·기존 변경은 이 작업 전부터 있던 것으로, 이번 변경 목록에 포함하지 않는다.

v2 사실 범위는 날짜 단위의 시작·끝 포함이다. 기존 사실 비교 모듈은 끝 제외 기간을 사용한다. 서로 자동 이식하지 않으며 연결 어댑터에서 이 차이를 명시적으로 변환해야 한다.

원본 hash는 무결성만 확인한다. 원본 내용의 진실성·실제 이행은 독립 검토가 필요하다. `userAttested`나 원본 업로드만으로 승인이 생기지 않는다. 모든 가상 fixture의 tenant·synthetic 표식은 API·DB·판정·백업에 유지된다.

### 저장 이행·복구

- v2 테이블: `v2_migrations`의 버전 2, `v2_entities`, `v2_approvals`, `v2_dependencies`, `v2_invalidations`. 기존 저장소 `user_version=1`을 올리거나 기존 boolean을 변환하지 않는 추가형 구조다.
- `createApp`의 서버 측 `complianceGrants`가 명시적으로 주어진 경우에만 `/api/compliance-v2`를 등록한다. 운영 기본 실행에는 grants를 넣지 않았고 v2 승인 경로를 활성화하지 않았다.
- 수집 일지 테이블은 새 공개 API 검색 경로 사용 시 생성된다. 이번에는 격리 데이터베이스에서만 실행했다.
- 운영 이행 전 데이터베이스·원본·설정 백업 및 복원 시험, 권한 주체 연결, 기존 검토 어댑터 검증이 필요하다. 과거 승인은 이력으로만 유지하며 새 승인을 만들지 않는다.
- 롤백은 이전 서버 소스·빌드·DB 백업으로 돌아가는 절차로 준비한다. 추가 테이블이 기존 자료를 대체하지 않으므로 데이터 삭제를 롤백으로 사용하지 않는다. 이번에는 운영 데이터 이행과 롤백 실행을 하지 않았다.
- v2 백업은 원본 bytes·객체 버전·참조·과거 승인 포함, 인증 토큰 제외, **암호화하지 않은 JSON**이다. UI의 기존 백업과 자동 통합되지 않았다. 별도 DB 복원 시 모든 현재 승인을 재검토로 남긴다. 해시·대상·참조를 먼저 검사하고 DB 작업은 트랜잭션으로 처리한다. 파일시스템까지 완전한 원자적 복원은 아니며 중간 DB 오류 시 미참조 원본 파일이 남을 수 있다.

## 3. 판정 게이트·보류 해제·권한

참/거짓/미확인/충돌 4값을 사용한다. AND의 결정적 거짓, OR의 결정적 참은 무관한 미확인 입력과 독립적으로 계산한다. 적용 대상 미확인, 만료·다른 설비 증빙, 규칙·근거 미승인, 변경된 참조, 기준일 불일치, 예외 미확인, 기산점 미확인은 확정 리스크를 차단한다.

| 기존 결과 분류 | v2 조건 | 내부 결과의 추가 구별 |
|---|---|---|
| 추가 자료 필요 | 보류 조건 존재 | 적용·이행·기한·출처 중 어떤 조건인지와 대체 확인 경로를 함께 반환 |
| 사람의 판단 필요 | 보류는 없지만 판단 승인 전, 또는 비대상·이행 확인 | `risk_candidate` / `out_of_scope` / `fulfilled`를 별도 내부 값으로 보존 |
| 명확한 법률 리스크 | 대상·불이행·기한·예외·근거·사실 입증을 통과하고 별도 판단 승인 | 수량 조건 일치만으로 생성하지 않음 |

새 지시의 비대상/이행 확인과 기존 세 분류의 차이를 숨기지 않았다. 화면 동결 때문에 내부 결과를 추가했고 화면 분류를 바꾸지는 않았다. 운영 사용 전 결과 계약의 최종 매핑을 검토해야 한다.

| 보류 코드 | 한국어 의미·해제 조건 |
|---|---|
| FACT_MISSING | 해당 대상·기간의 필요한 사실을 증빙, 허용된 기관 대장/전자기록/현장 확인 등으로 입증 |
| FACT_CONFLICT | 어떤 값·기간·대상이 충돌하는지 대조하고 해당 사실 버전을 재검토 |
| POLICY_CHANGED / BASIS_CHANGED | 최신 정책·원문·추출 버전에 맞춰 영향을 받은 판단만 재검토 |
| RULE_UNAPPROVED | 미확인 요건을 해소하고 권한 있는 규칙 검토자가 해당 버전 승인 |
| BASIS_INCOMPLETE | 원문·결정 셀·효력·출처 충돌을 해당 적용 범위에서 확인 |
| SCOPE_DATE / RULE_DATE | 기준일·판단 기간·규칙 효력기간의 관계 확인 |
| DEADLINE_UNKNOWN | 실제 기산 사건·발생일·검토된 기간 계산 근거 확보 |
| DECISION_REVIEW | 예외, 이행 상충 또는 기한 진행 여부를 실무자가 검토 |

보류 응답에는 필요한 항목, 대체 확인 경로, 담당 역할을 붙였다. 특정 양식이나 3개 기관 부존재 확인을 보편적 법정 요건으로 추가하지 않았다. 승인 역할은 서버가 제공하는 bearer-token 해시의 principal에서만 결정한다. 요청 본문의 역할·작성자 이름이나 기존 검토자 이름으로 권한을 얻을 수 없다. 추출 검토, 규칙 검토, 사업장 판단, 조치 검토를 분리하고 자기 승인·오래된 버전 승인·동시 수정 덮어쓰기를 차단한다. 이 독립 승인 방식은 내부 통제 설계이며 보편적인 법정 2인 승인 의무라는 뜻이 아니다.

조치 완료는 과거 판단을 수정하지 않는다. 완료 주장만으로 종료하지 않고 별도 효과 증빙과 독립 확인이 필요하다. 과거 승인 이력을 지우지 않고 변경 영향을 받은 연결만 현재 승인 무효 상태로 둔다.

## 4. 증거 정책·기간 계산·원문 확인

`policy-candidates.json`에 위험성평가, 교육, 안전관리자, 안전검사, 위험물 허가·완공, 위험물 관리자, 점검·제출·검사·교육, 환경 분야 **8개 그룹·43개 하위 의무 후보**를 정리했다. 필요한 사실·단독 불충분 자료·대체 확인 후보·미확인 범위를 연결했다. 이는 완성된 실행 정책 43개가 아니며 **운영 활성화·실제 검토 승인 0개**다.

이번 직접 확인은 위험물안전관리법 [제15조 본문](https://www.law.go.kr/LSW/lsSideInfoP.do?lsiSeq=259933&joNo=0015&joBrNo=00&docCls=jo&urlMode=lsScJoRltInfoR), [제18조 본문](https://www.law.go.kr/LSW/lsSideInfoP.do?lsiSeq=259933&joNo=0018&joBrNo=00&docCls=jo&urlMode=lsScJoRltInfoR)의 하위 의무 구분까지다. 하위법·별표·부칙·지역 권한·구체적 기간 계산을 모두 확인한 것이 아니다. 참고 문서의 다른 조사 결과를 이번 직접 확인으로 바꾸지 않았다.

기한 계산기는 사건 종류, 사건일, 일/월/년, 초일 포함 여부, 휴일 정책과 그 근거를 명시한다. 검사일 대신 발급일을 자동 대입하지 않는다. 월말·윤년을 달력으로 처리한다. 근거가 미검토이면 날짜를 확정하지 않는다. 매반기·연 1회·법령별 반복기한·적용례 자동화는 아직 미구현이며 계산기 시험 통과는 법률 기간 계산의 승인으로 볼 수 없다.

화성시 사무위임 조례(일련번호 2048299)는 이번 목록·상세 응답에서도 공포번호 2412·공포일 2025-12-31·시행일 2026-02-01, 규칙(2048313)은 784·2026-01-13·2026-02-01로 반환됐다. 기존 조사에서 나타난 공보와의 차이를 해소했다고 처리하지 않았다. 전체 공보·별표의 결정 셀 대조와 실제 시설별 권한 판단은 남아 있다.

법률 검토가 남은 것은 교육시간·내용·강사·간주 방향, 관리자 선임·자격 별표, 안전검사 대상·면제·고시, 위험물 변경허가 시설별 별표, 기록 보존·제출·검사별 기산점, 환경 업무별 기준·예외·허가 조건, 조문별 단계 시행, 지역 위임/위탁/전결 구분, 제재 금액·재량 처분 범위다. 미확인 숫자·승인서를 만들어 넣지 않았다.

## 5. API 호출·상태·재개

`api-registry.json`은 소스의 서비스와 operation별 endpoint·입력·인증키 파라미터·어댑터·검색 결과 역할·실제 표본·과거 저장 상태·제한시간을 연결한다. 키 값은 포함하지 않는다. 계정별 quota, 초기화 시각, 모든 기관의 최신 사용조건·원천 갱신 시차는 아직 확정하지 않았다.

이번 A07·A08 정책은 요청당 60초, 최초+재시도 최대 2회, 5–7초 재시도 간격, 완료 후 최소 2초 간격, 같은 서비스 직렬 처리, 대기열 4건 한도, 전체 180초 예산이다. 단순히 시간을 늘리는 것과 별도로 중복 요청 합치기·일시 오류만 재시도·제한 상태 영속을 적용했다. 재시도 횟수가 1회뿐이므로 여러 단계 지수 backoff는 아직 필요하지 않으며 횟수 확대 시 재설계해야 한다.

- 429/Retry-After, HTTP200 내부 quota 오류를 성공 0건과 분리한다. 일일 한도 초기화 시각이 미확인인 경우 임의 자정 해제를 만들지 않는다.
- 키 해시별 차단 상태·다음 가능 시각을 저장하고 새 전송기에서도 읽는다. URL·API 키·기관의 원문 오류 메시지를 저장하지 않는다.
- 응답 헤더 대기, 본문 수신, 파싱을 계측한다. DNS/TLS/연결시간은 헤더 대기와 합쳐져 있으며 완전한 단계별 독립 제한시간을 구현한 것은 아니다.
- 2026-10-08 20:02 KST 부근 두 서비스 성공 후, 20:14–20:17 측정에서 A07 실패·A08 재시도 성공. 후속 A07은 헤더 수신 전 60,011ms씩 두 번 제한 초과. A08은 첫 헤더 대기 60,018ms 실패 후 두 번째 요청의 헤더 107ms·본문 2ms·파싱 0ms였다. 네트워크/기관 응답 전 단계 지연이며 DNS·TLS·기관 중 어느 원인인지는 이 계측만으로 구별할 수 없다.
- 요청당 60초와 총 126.136초는 다른 값이다. 키 읽기·대기·재시도 시간이 전체 측정에 포함된다. 두 표본으로 평균 장애율이나 p95를 추정하지 않는다.

수집 일지는 시도/성공/비어 있지 않은 성공 시점, 0건/알 수 없음, 파싱 상태, 부분 완전성, 이전 결과 최신성을 분리한다. 페이지 결과와 checkpoint는 한 트랜잭션에 저장하고 실패 시 함께 롤백한다. 같은 페이지의 같은 내용은 중복 저장하지 않고 내용이 달라지면 별도 snapshot으로 남긴다. 총건수 변동·페이지 중복을 기록하고 offset API에 전수 완전성을 부여하지 않는다. 새 조회의 0건이나 실패가 다른 조회의 이전 성공 원문을 지우지 않는다.

**남은 API 개발:** 장시간 수집의 작업 ID 즉시 반환·백그라운드 실행·자동 페이지 재개, 모든 상세/첨부 수집과 일지 연결, 32개 전체 operation 오류·스키마·단위·갱신조건 검증, 동시 여러 프로세스의 quota 공유, 기관 확인에 따른 일일 제한 수동 해제 관리 경로, 조건부 HTTP/304와 저장 원문 연결, 원천 삭제의 tombstone 정책. 현재 `CollectionJournal.cancel`과 재개는 서비스 계층이며 운영 관리 화면이나 완성된 수집 worker가 아니다.

## 6. 직접 실행한 시험과 남은 인수

`execution.json`에 실제 명령·격리 경로·시간·로그·실패한 중간 시도를 남겼다.

- `npm run check`: TypeScript·서버 빌드·Vite·Vitest. 최종 282개 통과, 실패 0개.
- `npm run test:e2e`, `test:e2e:intake`, `test:e2e:additional`, `test:e2e:verification`, `test:e2e:dossier`, `test:e2e:public`: 격리 DB·합성 증빙·모의 공식 API 응답, 6개 명령 통과.
- 신규 28개 시험: 4값 판정, 자료 부족, 승인 분리, 버전 변경 영향, 다른 설비/tenant/가상 영역, 만료 증빙, 기한 사건·시행 예정 근거, 조치 후 과거 판단 보존, 원본 포함 복원과 손상 차단, 영속 한도, 원자적 checkpoint·중단/재개·이전 자료 보존, 9개 설계 사례.
- 중간 E2E 실패는 이미 제거된 버튼, AI 설정 펼침 상태, 이전 timeout 문구에 대한 시험 가정 때문이었다. 화면을 되돌리지 않고 시험을 현재 인터페이스에 맞췄다. 실패 기록을 최신 성공으로 덮어 쓰지 않는다.
- 추가 전체 검사에서 일일 quota 무기한 보류값을 시간 합산으로 만들 때 정수 상한을 넘길 수 있는 오류를 발견했다. 무기한 표식을 직접 저장하도록 수정하고 시각이 변하는 회귀시험으로 확인했다. 시험 대상 검색도 `tests` 폴더로 한정하여 격리 복사본이 중복 실행되지 않게 했다.
- 원본 포함 v2 복원은 별도 테스트 DB에서 확인했다. 운영 백업을 복원한 것은 아니다. v2 역할 API의 위조 토큰 차단을 시험했지만, 실제 사용자 계정 프로비저닝과 모든 승인 API의 E2E는 남아 있다.

`test-inventory.json`은 수정 전/후 시험을 이름·파일·결과로 보존한다. `acceptance-map.json`의 AC01–AC48과 V2-01–V2-24는 원문을 그대로 유지하며 신규 시험 ID와 연결했다. 연결된 작은 기술 시험만으로 전체 법적 인수항목을 완료 처리하지 않았다. 기존 254개의 의미별 전수 coverage 연결은 추가 검토가 필요하다.

`metrics.json`의 9개 설계 사례 결과 불일치와 승인 전 확정 리스크 발생을 계수한다. 개발자가 만든 기대값이므로 독립 법률 golden set, 실제 오탐·미탐률, 출처 정확도, 검토자 일치율, 운영 지연 p95는 **측정하지 않음(null)** 이다. 9/9를 법률 정확도 100%로 표시하지 않는다.

## 7. UI·운영 보존

`ui-freeze.json`은 기존 동결 스냅샷 12개 파일(화면 소스 9개, 배포 파일 3개)을 SHA-256으로 대조한다. 요청받지 않은 문구·메뉴·레이아웃·GPT 모델 선택·설정 화면을 바꾸지 않았다.

운영 4317 서버를 새 코드로 재시작하지 않았다. frontend는 기존 `index-BivsNquf.js` 관측, backend 전용 build ID 확인 API가 없어 새 소스의 serving 여부를 증명할 수 없으며 이번 변경은 미배포가 확실하다. 반복 접속 감시를 재개하지 않았다. 운영 파일이 아닌 별도 디렉터리에서 서버·프론트 빌드를 만들고 임의 포트로 E2E를 수행했다.

## 8. 다음 단계와 종료 조건

1. **P0 계약 연결:** v2 모델을 기존 검토·문서·백업에 연결하는 어댑터, 실제 역할 부여 경로, 구버전 null/boolean 호환·승인 API의 전체 E2E. 종료 조건은 잘못된 입력·권한·버전으로 확정 판단을 만들 수 없다는 통합 시험이다. 현재 P0-1 전체 완료는 아니다.
2. **P0 증거 정책:** 후보 43개를 의무별 필요한 사실·기한·예외·출처·충분/불충분 증거 조건의 실행 정책으로 작성하고 원문 대조. 검토된 범위만 독립 검토자가 승인한다. 하나의 합성 정책 게이트 시험으로 실제 정책 전부를 대신하지 않는다.
3. **P0 API 재개:** 작업 ID/worker와 영속 checkpoint 연결, quota 해제의 검토 기록, 작업 중 프로세스 종료·재시작 시험, operation별 fixture 확대. A07/A08의 기관 지연 자체를 없앴다는 종료 조건은 만들지 않는다. 제한된 실패 처리와 데이터 보존을 검증한다.
4. **P1 날짜·예외·관할:** 반복 기한·방향성 간주·잔존 의무·조문별 부칙·위임 그래프, OCR 결정 셀을 원문과 연결. 자료 부족과 실제 법적 충돌을 분리하여 영향 범위만 보류한다.
5. **P1 실무 검수:** 업무별 독립 golden/holdout, 48+24개 인수의 전수 추적, 실제 권한자 검토. 실제 사업장 정보가 없으면 합성 사례의 기술 검증까지만 기록한다.
6. **운영 인수:** 실제 배포 승인 후에만 백업·migration·배포·backend/frontend build ID·롤백을 확인한다. 이번 지시는 운영 배포 승인이 아니므로 이 단계는 범위제외다.

실제 사업장 검증을 하려면 적어도 사업장·시설 식별, 실제 공정/물질·제품/량·기간, 설치·변경·사용 사건일, 허가·신고·검사·선임 등의 증빙 또는 해당 대상의 기관 확인 기록이 필요하다. 이것이 없는 상태에서 모델이나 공공 목록으로 실제 사실을 만들어 채우지 않는다.
