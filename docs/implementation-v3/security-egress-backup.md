# 권한·전송·복원 검증 범위

## HTTP 신원과 검토 역할

호스트가 제공한 token의 해시로 principal을 찾는다. request body의 역할·tenant·이름은 권한으로 쓰지 않는다. principal의 시작·만료·철회 상태를 확인한다. HTTP 경로는 유효기간 없는 grant를 거절한다. 로컬 cookie/CSRF와 업무 역할 인증을 모두 통과해야 저장·승인할 수 있다.

| 검증 | 기대 | 시험 |
|---|---|---|
| grants 없음 | v2 endpoint 미등록 | V3-H03 |
| cookie만 / bearer만 | 각각 업무 권한 없음 / 세션 없음 | V3-H01 |
| cookie+bearer, CSRF 누락·오류 / 다른 Origin | 차단 | V3-H01 |
| 위조·만료·철회 / 다른 tenant·synthetic | 차단 | V3-H01 |
| 작성자 자기 승인 / 이전 버전 승인 | 차단 | V3-H02 |
| 원문→증빙→사실→정책→판정→조치 | 가상 작성·독립 검토 역할로 HTTP 실행 | V3-H04 |
| pending·반려·보완 요청·철회 | 이벤트 보존, 관련 승인 재검토 | V3-H02 |
| 원문 변경 | 관련 판단·조치만 무효화; 무관한 증빙 승인 보존 | V3-H04 |
| 복원 | backup_operator 필요, 원래 승인 이력과 현재 재검토 구분 | V3-B01~04 |

승인 저장은 savepoint 안에서 버전·의존성 검사와 이력 저장을 수행한다. 실제 사용자 provision 및 두 독립 승인 프로세스의 모든 경쟁 조건은 별도 인수 대상이다. 로컬 세션 전체를 법적 승인자로 간주하지 않는다.

## 외부 전송 경로 inventory

| 경로 | 전송되는 내용 | 이번 통제·한계 |
|---|---|---|
| server/ai.ts → OpenAI Responses | 질문·답변·선택 문서 발췌·법령 근거 | 호출 직전 request/document/source 해시, tenant·synthetic·목적·제공자·만료 검사. false/unknown 차단. 검토 전체는 로컬 경로로 계속 가능 |
| server/intake.ts extractIntake | 자연어 질문의 정제문 | extract 목적을 별도로 검사. review 허용을 재사용하지 않음 |
| v3 공개 API worker | 100자 이내 검색 조건·허용 필터 | 접수 전 및 worker 호출 전 query 해시와 제공자별 허용 검사. 호스트의 현재 principal을 다시 확인 |
| 기존 intake execute / MCP query | 질문에서 파생된 검색·도구 인수 | 가상 v3 앱에서는 출처·동의 연결이 없는 경로를 차단. 전체 도구별 허용 연결은 미완료 |
| server/sources.ts·reference-collection.ts | 고정 법령명·지역·법령 식별자·공개 원문 URL | 공개 법규 수집. 사용자 문서 원문 업로드 경로로 쓰지 않음. 모든 간접 호출의 민감정보 분류는 추가 검토 필요 |
| OCR·문서 파서 | 로컬 파일 | 현재 로컬 추출. 외부 OCR/embedding 경로는 구현하지 않았으며 사용 가능하다고 표시하지 않음 |
| 외부 파일 업로드 | 없음 | 현재 경로 미구현. 로컬 자료함 업로드는 PC 내부 저장 |
| OAuth token·모델 목록 | 인증 교환·모델 조회 | 자료 제공 동의와 다른 제어 경로. 인증값을 자료 백업·작업 payload에 넣지 않음 |
| epeople | 공개 승인 경로·사용자 보유 회신 | 실제 계정 수집 승인 없음. 이번 실행 없음 |

V3-E01은 실제 AI 함수 직전 `fetch` 호출 0회를 검사한다. V3-E02는 목적·제공자·tenant·첨부의 허용을 분리한다. V3-E03은 원본→요약/base64 파생 관계를 따라 원본 금지를 우회하지 못하는지 확인한다. 파생 관계가 등록되지 않은 임의 재작성 내용의 출처를 자동 탐지하는 기능은 없다. 아직 앱의 모든 파생물 생성 경로가 이 등록기에 연결된 것은 아니다.

`externalAllowed`의 미확인·거절 원본은 별도 전송 허용 이벤트만으로 우회할 수 없다. 현재 구현은 과거 버전의 금지까지 보수적으로 검사하므로 정당한 재승인 해제의 버전별 정책도 추가 설계 대상이다.

작업에는 원문 문서·토큰 대신 credential hash 참조와 제한된 검색 조건만 기록한다. 단, 승인된 검색어와 필터가 영속 queue에 저장되므로 검색어에 포함될 수 있는 개인정보의 완전한 제거·암호화까지 완료했다고 할 수 없다. 실운영 전 민감도 분류와 queue 전용 보호·보존 정책이 필요하다. 외부 제공의 실제 계약·위탁·국외이전 적법성은 시험으로 승인하지 않는다.

## 암호화 백업과 복원

관리 경로만 `/api/management-v3/backup`, `/restore`를 제공한다. 기존 UI의 backup/restore JSON 계약과 버튼은 그대로이며 기존 평문 백업을 암호화된 것으로 표시하지 않는다. 새 암호화 envelope를 기존 UI parser로 직접 가져오는 동선은 연결하지 않았다.

포맷: `she-backup-v3`, 버전 3, AES-256-GCM, 32바이트 별도 키, key ID, 12바이트 nonce, 인증 tag, scope·알고리즘·작성시각을 AAD로 묶는다. 키는 백업에 포함하지 않는다. 테스트 키만 생성했고 실제 키 보관·회전·복구 정책은 운영자 결정이 필요하다.

| 포함 | 제외·한계 |
|---|---|
| 해당 tenant·synthetic의 v2 전체 버전·참조·과거 승인·invalidations·원본 | API 키, OAuth, 백업 암호키 |
| v3 링크·trace·검토 이벤트·jobs·단위 결과·작업 이력·egress/파생 관계 | 다른 영역의 데이터·전체 계정 quota 관리 이력 |
| 연결된 기존 review·선택 문서 원본·근거·확보된 별표 바이너리 | 미연결 legacy 자료·raw API 임시 응답 |
| 미확보 별표 원본 목록 | 원본이 없는데 복원 완료로 표시하지 않음 |

`node:sqlite`의 실제 online backup API로 DB snapshot을 만들고, 원본 내용 해시를 확인한다. 활동 중 WAL 파일만 복사하지 않는다. 원본 삭제·변경을 만나면 백업 실패로 처리하며 완전한 것으로 내보내지 않는다.

평문 payload 상한 64MiB, 복원 HTTP bodyLimit 100MiB, v2 객체 10,000개, v2/별표 원본 각각 512개, 단일 v2 원본 20,000,000바이트. 기존 문서 업로드 20MiB와 정확한 수치가 다르므로 경계 파일은 별도 확인해야 한다. V3-B03은 실제 원본 3MiB가 base64·암호 envelope를 거쳐 일반 2MiB 제한을 넘는 HTTP 왕복을 검사한다. 최대 64MiB 경계·모든 파일 개수 조합을 부하시험한 것은 아니다.

복원은 빈 격리 DB에만 가능하다. 별도 staging/restore ID → 인증·scope·해시·참조 검사 → DB import → 원본 publication → commit 순으로 처리한다. 실패 시 새로 만든 파일만 정리한다. 이미 있던 같은 hash 파일은 교체·삭제하지 않는다. 복원된 jobs는 paused, 외부 제공 허용은 false, 법적 승인은 현재 재검토 상태다. 과거 승인 이력과 내부 판단 trace는 남긴다.

V3-B02는 4개 단계에 저장 오류를 주입한다. 실제 디스크를 가득 채우는 시험은 하지 않았다. V3-B04는 별도 프로세스를 publication 직후 비정상 종료시켜 DB rollback·복구 일지·새 원본 정리·재복원을 확인한다. 기존 사용자 서버·터미널을 종료한 것이 아니다.

운영 중 다른 복원 프로세스와의 동시 관리, 심볼릭 링크를 통한 모든 파일시스템 공격, OS 장애 시 fsync 내구성, 운영 암호키 유실 복구는 추가 검증 대상이다. 이 한계를 삭제하거나 완료로 바꾸지 않는다.
